# 消息队列（MQ）面试学习笔记（二）：消息模型与投递语义

> 本章目标：理解 Queue、Topic、Partition、Consumer Group、ACK、Offset，以及至少一次、至多一次、恰好一次语义。

## 1. Queue、Topic、Partition、Consumer Group

不同 MQ 术语不同，核心含义相近。

| 概念 | 含义 | 常见 MQ |
|---|---|---|
| Queue（队列） | 消息的逻辑容器，常用于任务分发 | RabbitMQ、RocketMQ |
| Topic（主题） | 一类消息的逻辑分类 | Kafka、RocketMQ、RabbitMQ |
| Partition（分区） | Topic 的并行存储/消费单元 | Kafka；RocketMQ 对应 MessageQueue |
| Consumer Group（消费者组） | 共同消费同一份消息的消费者集合 | Kafka、RocketMQ、Redis Streams |

Kafka 视角：

```text
Topic: order-created
├─ Partition 0：消息 0、1、2、3……（分区内有序）
├─ Partition 1：消息 0、1、2、3……（分区内有序）
└─ Partition 2：消息 0、1、2、3……（分区内有序）

Consumer Group: order-service
├─ Consumer A → Partition 0
├─ Consumer B → Partition 1
└─ Consumer C → Partition 2
```

**分区是吞吐与并行度的基础，也是顺序性的边界。**

【面试考点】

- Topic 用于分类；Partition 用于扩展吞吐；Consumer Group 用于横向扩展消费。
- 一个分区在同一个消费组中，同一时刻只能分配给一个消费者。
- Kafka 一个消费者组的有效消费并发度不超过分区数。

【高频追问】

- Topic 有 3 个分区、消费者组有 5 个消费者，实际有几个在消费？
  - 最多 3 个，另外 2 个空闲。
- 消费者数量少于分区数会怎样？
  - 一个消费者可分配多个分区，能消费但并行度不足。

【容易答错的坑】

- 错误：增加消费者数量一定能提高吞吐。
- 正确：还受队列/分区数量、单条消息耗时、下游资源限制。

## 2. Push 与 Pull 消费模型

### Push：Broker 主动推送

```text
Broker → 主动投递消息 → Consumer
```

消费者实现简单、低延迟，但 Broker 若推送过快，可能压垮慢消费者。因此需要预取数量、消费限流等机制。

RabbitMQ 对应用层表现接近 Push 模型。

### Pull：消费者主动拉取

```text
Consumer → 拉取请求 → Broker → 返回一批消息
```

消费者可按自身处理能力拉取和批量处理，更易实现流控。Kafka、RocketMQ 本质上以 Pull 为主。

Kafka 常用长轮询避免空拉取：消费者发起拉取后，Broker 在有数据或等待超时后返回。

【面试考点】

- Push 的风险是消费者处理不过来；Pull 的优势是消费者自主控制节奏。
- 实际产品常是混合形态，不能只从客户端 API 表象判断。

【高频追问】

- Kafka 为什么用 Pull？
  - 便于消费者批量拉取、按自身能力控制速率，适合高吞吐日志流场景。

【容易答错的坑】

- 错误：Pull 就一定延迟高。
- 长轮询和批量拉取可同时兼顾较低延迟与高吞吐。

## 3. 广播消费与集群消费

### 集群消费

同一消费者组共同分担消息，一条消息只被组内一个实例消费。

```text
Topic → Group A
          ├→ Consumer A
          └→ Consumer B

每条消息 → A 或 B 其中一个
```

适合：订单处理、发货任务、异步执行等“只执行一次业务动作”的场景。

### 广播消费

不同消费者组独立订阅，每组都收到完整消息流。

```text
OrderCreated
├→ 库存组：消费全量
├→ 营销组：消费全量
└→ 通知组：消费全量
```

适合：业务事件通知。

【面试考点】

- 消费者组是隔离消费进度与消费语义的单位。
- 通常用“不同 Group”实现跨业务广播，而非在一个 Group 内复制消费。

【高频追问】

- 两个不同服务能否使用相同 Consumer Group？
  - 通常不能。它们会竞争消息，造成每个服务只拿到部分数据。不同业务应使用不同 Group。

【容易答错的坑】

- 不要把“广播模式”误解为同一组内每个实例都消费一次；那会造成重复业务执行。

## 4. ACK 与 Offset：消息何时算消费完成

### ACK：确认机制

消费者处理成功后向 Broker 确认：消息可以删除或标记完成。

```text
Consumer 获取消息 → 执行业务 → 业务成功 → ACK → Broker 确认完成
```

若消费者在 ACK 前宕机，Broker 会认为消息未完成，随后重新投递。这是“至少一次”语义产生重复消费的根源。

RabbitMQ 常见手动 ACK；自动 ACK 的可靠性较弱。

### Offset：消费进度

Kafka 的消息一般不会因单个消费者消费成功而立即删除。消费者组记录已处理到哪个位置（Offset）。

```text
Partition： [0] [1] [2] [3] [4]
已提交 Offset = 3
表示：0、1、2 已确认完成；下一条从 3 开始消费
```

**先处理业务、再提交 ACK/Offset，是避免消息丢失的通用原则。**

【面试考点】

- ACK 用于确认消息处理结果；Offset 用于记录消费位置。
- 自动提交 Offset 可能在业务还未真正完成前推进进度，导致消息丢失。
- 手动提交 Offset 可能在提交失败或消费者宕机后导致重复消费。

【高频追问】

- 为什么不能先提交 Offset 再处理业务？
  - 提交后进程宕机，Broker 会认为消息已完成，业务未执行，产生消息丢失。
- 业务成功但提交 Offset 失败，会怎样？
  - 消息会再次被投递，产生重复消费；因此消费者必须幂等。

【容易答错的坑】

- 错误：手动 ACK/提交 Offset 就能完全消除重复消费。
- 正确：它主要减少丢失风险，重复消费仍是常态，必须做幂等。

## 5. 三种投递语义

### 5.1 At most once：至多一次

消息可能丢失，但不会重复。

典型做法：先提交 Offset/ACK，再执行业务。若处理前宕机，消息不会再来。

适用：允许少量丢失、但不能重复的非关键数据，例如部分实时指标。

### 5.2 At least once：至少一次

消息不会轻易丢失，但可能重复。

典型做法：业务成功后再 ACK/提交 Offset；确认前发生故障就重新消费。

**这是绝大多数业务 MQ 场景的默认可靠策略。**

### 5.3 Exactly once：恰好一次

从业务结果看，一条消息的效果只生效一次。

端到端严格 Exactly Once 很难，因为消息系统、消费者、数据库是多个独立系统，任一节点都可能在“处理成功”和“确认成功”的间隙故障。

工程上的常用答案：

```text
至少一次投递 + 消费端幂等 = 业务效果上的恰好一次
```

| 语义 | 丢失风险 | 重复风险 | 常用方式 |
|---|---:|---:|---|
| 至多一次 | 有 | 无或极低 | 先确认后处理 |
| 至少一次 | 极低 | 有 | 先处理后确认 |
| 恰好一次 | 极低 | 业务上消除 | 幂等、事务、去重 |

【面试考点】

- “消息恰好投递一次”与“业务效果恰好生效一次”不是同一个概念。
- 面试中优先回答：业务系统通常采用**至少一次 + 幂等消费**。

【高频追问】

- Kafka 的 Exactly Once 是否代表写数据库也绝不重复？
  - 不代表。Kafka 事务主要覆盖 Kafka 内生产/消费链路；写外部数据库仍要依赖数据库事务、唯一约束或幂等设计。

【容易答错的坑】

- 错误：开启 MQ 的 Exactly Once 配置后，消费者无需幂等。
- 正确：涉及外部数据库、HTTP 调用、发券/发短信等副作用时，仍必须保证业务幂等。

## 6. 幂等消费：重复执行，结果不变

幂等指同一个操作执行一次或多次，最终结果一致。

例如“订单 1001 支付成功”：

- 非幂等：每收到一次消息都给余额加 100 元。
- 幂等：仅当订单状态从 `UNPAID` 成功更新为 `PAID` 时执行后续入账。

常见实现方式：

| 方式 | 实现 | 适用场景 |
|---|---|---|
| 数据库唯一索引 | `message_id` 或业务唯一键唯一 | 入库、创建记录 |
| 条件更新 / 状态机 | `where status = 'UNPAID'` | 订单、支付状态迁移 |
| 去重表 | 记录已消费消息 ID | 通用消息去重 |
| Redis 去重 | `SET key value NX EX` | 高并发、短期去重 |
| 天然幂等操作 | 设置最终值而非累加 | 更新状态、覆盖写 |

推荐优先级：**业务唯一键 + 数据库唯一约束/条件更新**。Redis 去重通常只能作为性能优化或辅助，不能单独承担强可靠去重。

【面试考点】

- 幂等的关键是“业务结果不重复”，不是简单地“不让消息再来”。
- 业务唯一键比 MQ 的 Message ID 更可靠，因为同一业务事件可能因重发而具有不同消息 ID。

【高频追问】

- Redis `SETNX` 成功后消费者宕机怎么办？
  - 若先写去重标记再执行业务，会造成业务未执行但后续消息被跳过；需将关键幂等保证落在数据库事务/状态机，或精细设计标记状态与补偿。

【容易答错的坑】

- 错误：收到重复消息直接 return 就是幂等。
- 前提是你能可靠判断它重复且此前业务确实成功；否则可能把未成功的业务误判并丢弃。

## 7. 消息顺序：全局有序与局部有序

### 全局有序

所有消息严格按照产生顺序消费。

实现代价高：通常意味着单队列/单分区/单消费者，吞吐量严重受限。

### 局部有序（业务常用）

只保证同一个业务键内有序，例如同一订单、同一用户、同一账户。

```text
订单 1001 的消息 → 固定路由到 Partition 2 → 单线程顺序处理
订单 1002 的消息 → 固定路由到 Partition 0 → 单线程顺序处理
```

**面试中应优先选择“按业务键分区的局部有序”，而不是追求全局有序。**

【面试考点】

- Kafka 只保证分区内有序；RocketMQ 的顺序消息也通常是队列级有序。
- 同业务键使用一致的分区键（如 `orderId`）才能进入同一分区。
- 多线程异步处理、重试和分区迁移都可能破坏消费顺序。

【高频追问】

- 为什么同一个订单按 `orderId` 分区后仍可能乱序？
  - 若消费者拿到消息后再异步提交线程池、并发重试，应用层仍可能改变完成顺序；应对同一业务键串行化。

【容易答错的坑】

- 错误：MQ 能保证全局顺序。
- 正确：大多数 MQ 只提供队列或分区内顺序；全局有序通常吞吐代价很大。
