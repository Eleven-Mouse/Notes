# 消息队列（MQ）面试学习笔记（三）：可靠性与一致性

> 本章目标：建立“消息从生产到消费”的可靠性视角，掌握消息丢失、重复消费、可靠投递、事务消息与最终一致性的回答框架。

## 1. 可靠性全链路：消息会在哪些环节丢失

一条消息的完整路径：

```text
生产者
  ↓ ①发送与网络
Broker
  ↓ ②持久化与副本
消费者
  ↓ ③处理业务与确认
数据库 / 外部服务
```

消息丢失通常发生在三个阶段：

| 阶段 | 典型原因 | 核心解决方向 |
|---|---|---|
| 生产端 | 发送失败未感知、网络超时、未确认 | 发送确认、重试、Outbox |
| Broker | 未落盘即宕机、副本未同步、磁盘故障 | 持久化、同步刷盘、复制机制 |
| 消费端 | 先确认再执行业务、自动提交进度 | 先执行业务，成功后 ACK/提交 Offset |

**可靠性不是一个开关，而是生产端、Broker、消费端三段共同成立。**

【面试考点】

- 回答“如何保证消息不丢失”必须按生产端、Broker、消费端分别展开。
- 端到端可靠不等于零重复；提高可靠性通常会增加重复消费概率。

【高频追问】

- 为什么“至少一次”投递往往会带来重复消费？
  - 因为业务成功后、确认成功前发生故障时，Broker 会重新投递，无法区分业务是否已完成。

【容易答错的坑】

- 错误：开启消息持久化就能保证不丢消息。
- 正确：生产者可能根本没发送成功，消费者也可能过早确认；持久化只覆盖 Broker 阶段。

## 2. 生产端可靠投递

### 2.1 发送确认与重试

生产者不能只调用 `send()` 就认为发送成功，必须以 Broker 的确认结果为准。

```text
Producer → 发送消息 → Broker
Producer ← 成功确认 / 失败确认 ← Broker

失败或超时 → 有限次数重试 → 告警/补偿
```

不同 MQ 的典型能力：

| MQ | 常见发送确认机制 |
|---|---|
| RabbitMQ | Publisher Confirm；无法路由时 Return Callback |
| Kafka | `acks`、`retries`、幂等生产者 |
| RocketMQ | 同步发送结果、失败重试、事务消息 |

发送超时不一定代表 Broker 未收到消息：可能消息已到达但确认在网络中丢失。因此重试仍可能造成重复消息。

【面试考点】

- 发送端必须有确认、超时、有限重试、失败告警。
- “超时重试”可能产生重复，消费者必须幂等。

【高频追问】

- RabbitMQ 的 Confirm 与 Return 有何区别？
  - Confirm 确认消息是否已被 Broker 接收并处理；Return 用于消息到达 Exchange 但无法按路由规则投递到任何 Queue 的场景。

【容易答错的坑】

- 错误：收到发送成功回调，代表消费者已经处理成功。
- 正确：它通常仅代表消息已被 Broker 接收/持久化，和消费结果无关。

### 2.2 本地消息表（Transactional Outbox）

最难的问题是：数据库事务提交与发送 MQ 消息是两个独立动作。

失败窗口：

```text
开启本地事务 → 写订单成功 → 提交订单事务 → 发送 MQ 前宕机
```

结果：订单已存在，但“订单已创建”事件没有发出，数据不一致。

本地消息表方案：在**同一个数据库事务**中，同时写业务数据与待发送消息记录。

```text
本地事务：
  1. 写入 orders
  2. 写入 outbox_message（status = NEW）
  3. 提交事务

独立投递任务：
  4. 扫描 NEW 消息
  5. 发送至 MQ
  6. 收到 Broker 确认后更新 status = SENT
  7. 失败则重试，超限则告警/人工处理
```

这样，订单与待发送事件要么一起提交，要么一起回滚；后续投递即使失败也能持续补发。

示例表字段：

| 字段 | 说明 |
|---|---|
| `id` | 消息唯一 ID |
| `biz_key` | 业务唯一键，如订单号 |
| `topic` / `event_type` | 事件路由信息 |
| `payload` | 消息体 |
| `status` | NEW、SENDING、SENT、FAILED |
| `retry_count` / `next_retry_at` | 重试控制 |
| `created_at` | 审计与超时扫描 |

【面试考点】

- 本地消息表解决的是“本地 DB 写入成功但 MQ 未发送”的双写不一致。
- 它保障的是**最终一致性**，不是同步强一致。
- 定时扫描是兜底，实时投递可降低延迟；二者可同时存在。

【高频追问】

- 若消息成功发到 MQ，但更新本地消息表为 `SENT` 失败呢？
  - 定时任务会再次投递，产生重复消息；依赖下游幂等保证业务结果正确。
- 消息表会不会成为性能瓶颈？
  - 高流量下可以分表、分库、按状态索引、批量扫描、CDC（如 Debezium）投递；但不应牺牲事务一致性。

【容易答错的坑】

- 错误：本地消息表配合定时任务可以做到消息绝不重复。
- 正确：它重点防丢失，重复由下游幂等消化。

## 3. Broker 可靠性：持久化与副本

Broker 接到消息后，若只存在内存中就返回成功，机器宕机时消息会丢失。因此关键消息要保证落盘，并在必要时复制到多副本。

```text
Producer → Leader Broker（内存） → 磁盘
                                 └→ Follower 副本
```

### 3.1 持久化：内存、异步刷盘、同步刷盘

| 模式 | 可靠性 | 性能 | 适用情况 |
|---|---:|---:|---|
| 仅内存 | 最低 | 最高 | 可丢失的临时数据 |
| 异步刷盘 | 较高 | 高 | 大多数吞吐优先业务 |
| 同步刷盘 | 高 | 较低 | 金融、订单等极关键消息 |

同步刷盘是指 Broker 在消息真正写入磁盘后才向生产者确认；异步刷盘则可能先确认、后批量落盘，宕机窗口内仍有丢失风险。

### 3.2 副本复制与确认

单机磁盘持久化仍无法抵抗机器损坏。通过多副本，把消息复制到其他节点。

Kafka 的关键参数示例：

```text
acks = all
min.insync.replicas >= 2
replication.factor >= 3
```

- `acks=all`：等待 ISR 中副本确认。
- `min.insync.replicas=2`：至少 2 个同步副本在线才允许成功写入。
- `replication.factor=3`：通常至少三副本，容忍一个副本故障。

**更强可靠性通常以更高延迟、更低可用写入能力为代价。**

【面试考点】

- 消息持久化与集群副本是两道不同防线。
- 同步刷盘、防宕机；副本复制、防节点或磁盘故障。
- 可靠性、吞吐、延迟、可用性之间需要权衡。

【高频追问】

- Kafka 设置 `acks=all` 是否绝对不会丢？
  - 不能绝对保证。还要正确设置 `min.insync.replicas`、副本数、禁止不安全 Leader 选举，并考虑生产端重试和消费端处理。

【容易答错的坑】

- 错误：副本数为 3，就意味着任何情况下都不会丢。
- 正确：若允许未同步副本成为 Leader，或 ISR 配置不合理，仍可能丢失已确认数据。

## 4. 消费端可靠消费

推荐的处理顺序：

```text
拉取消息
  ↓
参数校验、反序列化、幂等判断
  ↓
执行本地业务事务
  ↓
本地事务提交成功
  ↓
ACK / 提交 Offset
```

### 4.1 为什么要先执行业务，再确认消息

错误顺序：

```text
收到消息 → ACK / 提交 Offset → 执行业务 → 宕机
```

此时 Broker 认为消息已消费，不再重投；但业务实际没有完成，形成消息丢失。

正确顺序的代价：

```text
执行业务成功 → ACK 前宕机 → 消息重投 → 可能重复执行业务
```

因此需要消费幂等。

### 4.2 重试、退避与死信

短暂故障（数据库抖动、下游超时）可以重试；持续失败的“毒消息”不能无限重试。

```text
消费失败
  ↓
有限次数重试（指数退避）
  ↓ 超过阈值
死信队列（DLQ）
  ↓
告警 → 定位原因 → 修复 / 补偿 / 重新投递
```

【面试考点】

- 消费成功的边界是**本地业务事务提交成功**，不只是代码未抛异常。
- 消费端可靠性依赖手动确认、幂等、有限重试、死信和监控。

【高频追问】

- 是否应该捕获所有异常并 ACK？
  - 不应该。可恢复失败应触发重试；不可恢复的格式错误等应进入死信队列，并记录原因，不能悄悄吞掉。

【容易答错的坑】

- 错误：无限重试最可靠。
- 正确：无限重试会阻塞消费、压垮下游并引发重试风暴；必须限制次数并隔离死信。

## 5. 重复消费：原因与解决方案

### 常见原因

```text
1. 业务成功，ACK/提交 Offset 前宕机
2. ACK 或提交请求超时，实际是否成功未知
3. 生产端超时重试，Broker 已收到第一次消息
4. 消费者 Rebalance、故障转移导致进度回退
5. 人工回溯、重放消息
```

### 推荐的幂等实现

以“支付成功更新订单”为例，使用数据库条件更新：

```sql
UPDATE orders
SET status = 'PAID', paid_at = NOW()
WHERE order_no = :orderNo
  AND status = 'UNPAID';
```

- 更新行数为 1：首次成功处理。
- 更新行数为 0：已支付或状态不允许迁移，按已处理/异常业务规则处理。

若还要写消费记录，可在同一个本地事务中写入：

```text
事务：状态机条件更新 + 插入 message_consume_log（message_id 唯一）
```

| 方案 | 优点 | 注意点 |
|---|---|---|
| 唯一索引 | 强一致、简单可靠 | 需设计正确业务唯一键 |
| 条件更新/状态机 | 最贴合业务语义 | 要清楚合法状态迁移 |
| 消费日志表 | 通用、可审计 | 需要清理策略和索引 |
| Redis `SETNX` | 性能高 | 宕机窗口、过期时间、原子性问题 |

**优先让数据库业务状态机或唯一约束成为幂等的最终防线。**

【面试考点】

- 可靠消息系统一般不承诺绝不重复，消费者必须幂等。
- 去重键优先使用业务唯一键（订单号、支付流水号），而不只依赖消息 ID。

【高频追问】

- Redis 去重能单独保证幂等吗？
  - 不建议。先抢到 Redis 锁后进程宕机，可能造成消息被误跳过；关键业务需用数据库唯一约束或状态机兜底。

【容易答错的坑】

- 错误：`messageId` 唯一，所以可完全用它防重。
- 正确：生产者重发同一业务事件可能生成新 messageId；业务主键更能表达“同一业务动作”。

## 6. 最终一致性与事务消息

### 6.1 为什么需要事务消息

业务库更新与发送 MQ 是分布式双写：

```text
更新订单数据库 + 发送“订单已支付”消息
```

任何一个成功、另一个失败，都会造成不一致。传统 XA 两阶段提交能提供强一致，但性能和可用性成本高，互联网业务通常不作为首选。

常见方案对比：

| 方案 | 一致性 | 实现复杂度 | 适用场景 |
|---|---|---:|---|
| 本地消息表 | 最终一致 | 中 | 通用、跨 MQ 场景 |
| MQ 事务消息 | 最终一致 | 中 | RocketMQ 等原生支持场景 |
| XA / 2PC | 强一致 | 高 | 少量强一致、可接受阻塞场景 |
| Saga / 补偿 | 最终一致 | 高 | 长事务、多服务编排 |

### 6.2 RocketMQ 事务消息流程

```text
1. Producer → Broker：发送半消息（Half Message）
2. Broker：持久化半消息，但暂不投递给 Consumer
3. Producer：执行本地事务（例如更新订单状态）
4. Producer → Broker：提交 Commit 或回滚 Rollback
5. Commit：Broker 将半消息投递给 Consumer
6. Broker 未收到结果：主动回查 Producer 的本地事务状态
7. Producer 根据事务结果返回 Commit / Rollback
```

半消息的价值：消费者不会看到“本地事务尚未成功”的业务事件。

事务回查解决 Producer 在本地事务完成后宕机、未来得及通知 Broker 的问题。

【面试考点】

- RocketMQ 事务消息是“半消息 + 本地事务 + Commit/Rollback + 事务回查”。
- 它解决生产者本地事务与消息发送的原子性问题，属于最终一致性方案。
- Consumer 仍需幂等，因为提交结果和投递仍可能重试。

【高频追问】

- 事务回查时如何判断本地事务状态？
  - 依据业务事务记录、订单状态或本地事务日志查询；不能依赖内存状态。
- 事务消息能保证下游消费一定成功吗？
  - 不能。它保障本地事务与消息可见性的协调；下游仍需通过重试、死信、补偿保证最终处理完成。

【容易答错的坑】

- 错误：事务消息就是分布式强一致事务。
- 正确：它通常提供的是可靠事件发布和最终一致性，而非跨多个业务库的同步原子提交。

## 7. 一套可复用的面试回答：如何保证消息不丢失

> 我会从生产端、Broker、消费端三层保证。生产端开启发送确认，处理超时和失败重试；为解决数据库提交与发消息的双写不一致，关键业务使用本地消息表或 RocketMQ 事务消息。Broker 端开启持久化，并配置多副本和合适的同步确认策略。消费端关闭自动确认，先在本地事务内完成幂等业务处理，再 ACK 或提交 Offset；失败采用有限次数、带退避的重试，超限转入死信队列并告警补偿。这样一般实现至少一次投递，再依靠消费端幂等实现业务效果上的恰好一次。
