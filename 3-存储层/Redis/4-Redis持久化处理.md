
> redis提供持久化处理机制：RDB快照和AOF日志

## RDB快照

>RDB快照总结就是一句话，在某一瞬间，将缓存中的数据“照”下来，写入磁盘，

### 一，redis提供了两种命令：

 1，save：save命令是在当前程序执行，生成RDB快照文件，由于和操作命令的执行和生成RDB文件是在同一个线程，如果消耗的时间太长，**会阻塞主线程**。
 2，bgsave：执行这个命令，redis会启动一个子线程，子线程共享主线程的内存数据，完成fork后读取内存数据并生成RDB快照文件，所以不会阻塞主线程。
>需要注意的是，在linux系统当中，所有的进程都没有办法直接操作物理内存，而是由操作系统给主进程分配一个虚拟内存，主进程只能操作虚拟内存，此时操作系统会维护虚拟内存与物理内存的一个映射表，也就是页表对物理内存进行读写操作
>而我们上述所说的fork，就是拷贝页表给子进程




redis还可以通过配置文件的选项来实现隔一段时间就执行一次bgsave
```
save 800 1 //意思是800秒之内至少对数据库修改了1次，就会执行bgsave
```

这里需要提一点的是RDB快照是**全量快照**，每次执行RDB快照都是将内存中**所有数据**写入磁盘
如果操作太频繁会对Redis性能产生影响，但是如果频率太低，数据丢失的也会更多，丢失概率也就更大

### 二，copy-on-write 写时复制技术

当我们执行bgsave的过程中，主进程接收请求要执行的写操作，此时数据能被修改吗？

当然可以被修改，因为bgsave的fork采用的是copy-on-write技术：
1，当主进程执行度的读的操作，访问的是共享物理内存
2，当主进程执行写的操作，则会拷贝一份物理内存的副本，在副本中进行写操作

## AOP

AOP文件会记录每一个写命令，可以看作是命令日志文件

### 一，3种写回策略:
```
//表示每执行一次写命令，立刻记录到AOF文件
appendfsync always

//默认方案，表示写命令执行完先放入AOF缓冲区，然后每隔1s将缓冲区的数据写入AOF文件中
appendfsync everysec

//写命令执行完先放入缓冲区，由操作系统决定什么时候将数据写入磁盘
appendfsync no
```

### 二，AOF重写机制
因为AOF是追加日志的形式记录，所以AOF文件会因为记录的积累而变得“臃肿”，这其中AOF会记录对同一个key的多次写操作，但事实上只有最后一次写才有效，AOF提供了一种命令专门用来处理无意义的操作
bgrewriteaof，可以用最少的命令达到相同的效果，它的后台重写过程和RDB bgsave过程类似
```
//AOF文件比上次文件增长超过多少百分比则触发重写
auto-aof-rewrite-percentage 100
//AOF文件体积最小多大以上才出发重写
auto-aof-rewrite-min-size 64mb
```
