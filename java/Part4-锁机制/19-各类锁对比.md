## 二、ReentrantLock vs synchronized 详细对比

| 对比维度 | synchronized | ReentrantLock |
|---------|-------------|---------------|
| **锁类型** | JVM 内置关键字 | JDK API（java.util.concurrent.locks） |
| **实现层面** | JVM 层（monitorenter/monitorexit） | Java 层（AQS） |
| **可重入性** | 可重入（Monitor._count） | 可重入（AQS state） |
| **公平性** | 非公平锁 | 可选公平/非公平（构造参数） |
| **响应中断** | 不可中断 | lockInterruptibly() 可响应中断 |
| **超时获取** | 不支持 | tryLock(timeout) 支持 |
| **条件变量** | 只有一个 wait/notify | 多个 Condition（await/signal） |
| **锁绑定多个条件** | 不支持 | 支持（newCondition） |
| **释放方式** | 自动释放（退出同步块） | 必须手动 unlock（finally 块中） |
| **JVM 锁优化** | 支持锁升级（偏向/轻量/重量） | 无 JVM 级别优化 |
| **使用复杂度** | 简单 | 需要 try-finally 保证释放 |
| **适用场景** | 简单同步、锁竞争不激烈 | 复杂同步、需要高级功能 |

## 三、公平锁 vs 非公平锁

### 3.1 核心差异（源码级）

**非公平锁（NonfairSync）：**

```java
// 非公平锁获取锁时，先直接 CAS 抢一次
final void lock() {
    if (compareAndSetState(0, 1))  // 先尝试插队！
        setExclusiveOwnerThread(Thread.currentThread());
    else
        acquire(1);
}
```

**公平锁（FairSync）：**

```java
// 公平锁获取锁时，不会先 CAS，而是直接进入 acquire
final void lock() {
    acquire(1);  // 没有先抢的逻辑！
}

// acquire 内部调用 tryAcquire
protected final boolean tryAcquire(int acquires) {
    // 关键：hasQueuedPredecessors() 检查队列中是否有等待的线程
    if (c == 0) {
        if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) {
            // 队列为空才能 CAS
            setExclusiveOwnerThread(Thread.currentThread());
            return true;
        }
    }
    // ...
}
```

**区别总结：**
- 非公平锁：新线程先 CAS 抢一次，抢不到再排队（效率高，但可能饿死）
- 公平锁：严格按 FIFO 队列顺序获取锁（公平，但吞吐量低约 10%-20%）

### 3.2 为什么默认非公平？

因为非公平锁吞吐量更高。实际场景中，线程释放锁后，队列中的线程被唤醒需要时间，这个间隙新来的线程可以直接获取锁，减少了 CPU 空闲时间。

## 四、可重入锁的实现原理

**synchronized 可重入：** Monitor._count 计数，每次进入 +1，退出 -1，减到 0 释放。

**ReentrantLock 可重入：** AQS state 变量记录重入次数（state=0 无锁，state=N 重入 N 次）。同一线程再获取时 owner 匹配则 state 递增；释放时 state 递减，减到 0 才真正释放。

## 五、读写锁 ReentrantReadWriteLock

### 5.1 核心规则

| 场景 | 读锁 | 写锁 |
|-----|------|------|
| 读锁被持有时 | 可再获取读锁（共享） | 阻塞 |
| 写锁被持有时 | 阻塞 | 阻塞 |

**口诀：读读不互斥，读写互斥，写写互斥。**

### 5.2 状态存储（AQS state 高 16 位读 / 低 16 位写）

```java
// 用一个 int 同时表示读锁和写锁的数量
static final int SHARED_SHIFT   = 16;
static final int SHARED_UNIT    = (1 << SHARED_SHIFT);
static final int MAX_COUNT      = (1 << SHARED_SHIFT) - 1;
static final int EXCLUSIVE_MASK = (1 << SHARED_SHIFT) - 1;

// 读锁数量 = state >>> 16
static int sharedCount(int c) { return c >>> SHARED_SHIFT; }
// 写锁数量 = state & 0xFFFF
static int exclusiveCount(int c) { return c & EXCLUSIVE_MASK; }
```

### 5.3 写锁降级为读锁

```java
// 写锁降级：持有写锁 → 获取读锁 → 释放写锁
writeLock.lock();
try {
    // 修改数据
    updateData();
    // 降级：先获取读锁
    readLock.lock();
} finally {
    // 再释放写锁
    writeLock.unlock();
}
// 此时持有读锁，其他线程可以读但不能写
try {
    // 使用数据
    useData();
} finally {
    readLock.unlock();
}
```

**注意：** 读锁不能升级为写锁（会死锁），但写锁可以降级为读锁。

## 六、StampedLock（JDK8 乐观读锁）

```java
StampedLock stampedLock = new StampedLock();

// 乐观读（不加锁，性能最高）
long stamp = stampedLock.tryOptimisticRead();
double value = sharedData;  // 读取数据
if (!stampedLock.validate(stamp)) {
    // 乐观读失败，升级为悲观读锁
    stamp = stampedLock.readLock();
    try {
        value = sharedData;
    } finally {
        stampedLock.unlockRead(stamp);
    }
}

// 写锁
long writeStamp = stampedLock.writeLock();
try {
    sharedData = newValue;
} finally {
    stampedLock.unlockWrite(writeStamp);
}
```

**StampedLock 三种模式：**
1. **写锁**：独占，与悲观读互斥
2. **悲观读锁**：共享，与写锁互斥
3. **乐观读**：无锁，通过 validate 检查期间是否有写操作

**注意：** StampedLock 不可重入，不适合包装为 synchronized 方法。

## 七、自旋锁 vs 阻塞锁

| 对比 | 自旋锁 | 阻塞锁 |
|-----|-------|-------|
| **原理** | CAS 忙等循环 | 操作系统 Mutex 挂起线程 |
| **CPU 占用** | 持续占用 CPU | 释放 CPU |
| **上下文切换** | 无 | 有（用户态→内核态） |
| **适用场景** | 锁持有时间极短 | 锁持有时间长/竞争激烈 |
| **风险** | 自旋过久浪费 CPU | 频繁切换开销大 |

## 八、死锁

### 8.1 死锁的 4 个必要条件

1. **互斥条件**：资源只能被一个线程持有
2. **请求与保持**：持有资源的同时请求其他资源
3. **不可剥夺**：已获得的资源不能被强行夺走
4. **循环等待**：线程间形成环形等待链

### 8.2 预防死锁

| 策略 | 方法 |
|-----|------|
| 破坏互斥 | 无法破坏（锁的本质就是互斥） |
| 破坏请求与保持 | 一次性获取所有资源 |
| 破坏不可剥夺 | 设置超时 tryLock(timeout) |
| 破坏循环等待 | **按固定顺序加锁**（最实用） |

### 8.3 按固定顺序加锁（最实用）

```java
// 正确：按 hashCode 顺序加锁，破坏循环等待
public void transfer(Account from, Account to, int amount) {
    Account first = from.hashCode() < to.hashCode() ? from : to;
    Account second = first == from ? to : from;
    synchronized (first) { synchronized (second) { /* ... */ } }
}
```

### 8.4 死锁排查：`jps -l` 找 PID → `jstack <pid>` 检测死锁，或用 JConsole/VisualVM。

## 九、常见误区

| 误区 | 正解 |
|-----|------|
| ReentrantLock 一定比 synchronized 好 | 简单场景 synchronized 更简洁，且有 JVM 锁优化 |
| 公平锁一定比非公平锁好 | 公平锁吞吐量低 10%-20%，大部分场景用非公平即可 |
| 读写锁的读锁可以升级为写锁 | 不可以，会导致死锁 |
| StampedLock 是 ReentrantReadWriteLock 的替代品 | 不完全替代，StampedLock 不可重入 |
| 死锁只在加锁时发生 | 多个线程以不同顺序获取多把锁就会死锁 |

## 十、面试题

### Q1：ReentrantLock 和 synchronized 有什么区别？
**答：** synchronized 是 JVM 内置关键字，自动释放，支持锁升级优化；ReentrantLock 是 JDK API，需要手动释放，支持公平锁、响应中断、超时获取、多条件变量。ReentrantLock 功能更丰富，synchronized 使用更简单。

### Q2：公平锁和非公平锁的源码差异是什么？
**答：** 非公平锁的 lock() 方法先 CAS 抢一次（compareAndSetState(0,1)），抢不到才进入 acquire 排队；公平锁直接进入 acquire，tryAcquire 中会先检查 hasQueuedPredecessors() 确保队列中没有更早的等待者才允许 CAS。

### Q3：读写锁的读锁为什么不能升级为写锁？
**答：** 如果允许读锁升级为写锁，两个线程同时持有读锁并同时尝试升级为写锁，会互相等待对方释放读锁，形成死锁。

### Q4：StampedLock 的乐观读是怎么实现的？
**答：** 调用 tryOptimisticRead() 获取一个 stamp（版本号），然后读取数据，最后调用 validate(stamp) 检查期间是否有写操作（通过检查 stamp 是否过期）。如果过期则升级为悲观读锁重新读取。

### Q5：如何预防死锁？实际项目中怎么做的？
**答：** 最实用的方法是**按固定顺序加锁**。此外可以使用 tryLock(timeout) 设置超时来破坏不可剥夺条件，或者一次性获取所有资源来破坏请求与保持条件。排查死锁用 jstack 或 JConsole。

### Q6：ReentrantLock 的可重入是怎么实现的？
**答：** 基于 AQS 的 state 变量。首次获取锁时 state 从 0 CAS 到 1；同一线程再次获取时判断 owner 是否是自己，是则 state 递增；释放时 state 递减，减到 0 才真正释放锁。

### Q7：什么场景下用 ReentrantLock 而不是 synchronized？
**答：** 需要响应中断（lockInterruptibly）、超时获取（tryLock）、公平排队、多个等待队列（Condition）、需要尝试获取锁（tryLock 非阻塞）时使用 ReentrantLock。

### Q8：写锁降级是什么？为什么要降级？
**答：** 写锁降级是持有写锁时获取读锁，再释放写锁的过程。这样可以保证在释放写锁后，其他线程不能写但自己还能继续读（持有读锁），保证数据可见性同时提高读并发。
