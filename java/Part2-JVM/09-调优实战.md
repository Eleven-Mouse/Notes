
> **一句话总结**: 调优不是玄学，是"监控 → 发现问题 → 定位原因 → 调整参数 → 验证效果"的闭环，面试常考"OOM/CPU 100% 怎么排查 + 常用工具 + GC 日志分析"。

## 二、核心知识点

### 1. 常用 JVM 参数

#### 1.1 堆大小设置

| 参数 | 说明 | 推荐值 |
|------|------|--------|
| `-Xms` | 初始堆大小 | 与 Xmx 相同，避免动态扩容 |
| `-Xmx` | 最大堆大小 | 物理内存的 50%-80%，不超过 32G（指针压缩） |
| `-Xmn` | 新生代大小 | 堆大小的 1/3 到 1/2 |
| `-Xss` | 每个线程栈大小 | 默认 1MB，线程多时可调小到 256k |

> **面试经验**: Xms 和 Xmx 设为一样，避免堆大小动态调整的开销。

#### 1.2 新生代比例控制

| 参数 | 说明 |
|------|------|
| `-XX:NewRatio=2` | 老年代:新生代 = 2:1 |
| `-XX:SurvivorRatio=8` | Eden:S0:S1 = 8:1:1 |
| `-XX:MaxTenuringThreshold=15` | 对象晋升老年代的年龄阈值 |

#### 1.3 Metaspace

| 参数 | 说明 |
|------|------|
| `-XX:MetaspaceSize=256m` | 初始元空间大小 |
| `-XX:MaxMetaspaceSize=512m` | 最大元空间大小 |

> MetaspaceSize 是初始大小也是扩容触发阈值，设太小会频繁 Full GC。

#### 1.4 收集器选择

| 参数 | 说明 |
|------|------|
| `-XX:+UseSerialGC` | Serial + Serial Old |
| `-XX:+UseParNewGC` | ParNew + Serial Old |
| `-XX:+UseParallelGC` | Parallel Scavenge + Parallel Old（JDK 8 默认） |
| `-XX:+UseConcMarkSweepGC` | ParNew + CMS + Serial Old（备用） |
| `-XX:+UseG1GC` | G1（JDK 9+ 默认） |
| `-XX:+UseZGC` | ZGC（JDK 11+） |

#### 1.5 GC 日志参数（JDK 8）

```bash
-XX:+PrintGCDetails          # 打印 GC 详细信息
-XX:+PrintGCDateStamps       # 打印时间戳
-XX:+PrintGCTimeStamps       # 打印 JVM 启动后的相对时间
-Xloggc:/path/to/gc.log      # GC 日志输出路径
-XX:+HeapDumpOnOutOfMemoryError   # OOM 时自动 dump
-XX:HeapDumpPath=/path/to/dump    # dump 文件路径
```

#### 1.6 GC 日志参数（JDK 9+ 统一用 Xlog）

```bash
-Xlog:gc*:file=/path/to/gc.log:time,uptime:filecount=5,filesize=10m
```

### 2. JDK 自带监控工具

| 工具 | 用途 | 常用命令 |
|------|------|----------|
| **jps** | 查看 Java 进程 | `jps -l` 显示全限定类名 |
| **jstat** | 查看 GC 统计信息 | `jstat -gcutil <pid> 1000` 每秒输出一次 |
| **jmap** | 查看堆内存、导出 dump | `jmap -heap <pid>` / `jmap -dump:format=b,file=heap.hprof <pid>` |
| **jstack** | 查看线程堆栈 | `jstack <pid>` / `jstack -l <pid>`（含锁信息） |
| **jinfo** | 查看/修改 JVM 参数 | `jinfo -flags <pid>` / `jinfo -flag +PrintGCDetails <pid>` |

#### jstat 关键指标解读

```
jstat -gcutil <pid> 1000
  S0     S1     E      O      M      YGC   YGCT    FGC    FGCT   GCT
  0.00  45.23  67.89  32.45  95.12   234   1.234    5    2.345  3.579
```

| 指标 | 含义 |
|------|------|
| S0/S1 | Survivor 0/1 使用率 |
| E | Eden 使用率 |
| O | 老年代使用率 |
| M | Metaspace 使用率 |
| YGC/YGCT | Young GC 次数/总耗时 |
| FGC/FGCT | Full GC 次数/总耗时 |

> **关注点**: FGC 次数是否持续增长、FGCT 是否过长、O 是否接近 100%

### 4. GC 日志分析方法

#### Young GC 日志示例（JDK 8 G1）:

```
2026-04-26T10:30:15.123+0800: 12.345: [GC pause (G1 Evacuation Pause) (young)
  [Eden: 256.0M(256.0M)->0.0B(230.0M)
   Survivors: 0.0B->26.0M
   Heap: 256.0M(512.0M)->24.5M(512.0M)]
  [Times: user=0.08 sys=0.01, real=0.02 secs]
```

**解读要点**:
- GC 类型: G1 Young GC
- Eden 从 256M 降到 0（被清空）
- Survivors 从 0 增长到 26M
- 堆总使用从 256M 降到 24.5M
- 耗时: real=0.02s（实际停顿 20ms）

#### Full GC 日志示例:

```
2026-04-26T10:31:20.456+0800: 75.678: [Full GC (Allocation Failure)
  [Eden: 0.0B(230.0M)->0.0B(230.0M)
   Survivors: 0.0B->0.0B
   Heap: 450.0M(512.0M)->448.5M(512.0M)]
  [Times: user=1.20 sys=0.05, real=1.25 secs]
```

> Full GC 后堆几乎没减少（450M → 448.5M），说明内存快满了，需要扩堆或排查泄漏。

### 5. 常见问题排查流程

#### 5.1 OOM 排查

```
发现 OOM
  ↓
确认 OOM 类型（heap / metaspace / direct buffer / unable to create thread）
  ↓
heap: -XX:+HeapDumpOnOutOfMemoryError 导出 dump
  ↓
用 MAT（Memory Analyzer Tool）打开 dump 文件
  ↓
查看 Dominator Tree / Leak Suspects 报告
  ↓
找到占用内存最大的对象 → 分析引用链 → 定位泄漏代码
```

**MAT 关键功能**:
- **Leak Suspects**: 自动分析可能的内存泄漏
- **Dominator Tree**: 查看占用内存最大的对象
- **GC Roots**: 查看对象为什么无法被回收（引用链）
- **Histogram**: 按类统计对象数量和大小

#### 5.2 CPU 100% 排查

```
top 命令找到 CPU 占用最高的 Java 进程 PID
  ↓
top -Hp <pid> 找到 CPU 占用最高的线程 TID
  ↓
printf "%x\n" <tid> 将线程 ID 转为十六进制
  ↓
jstack <pid> | grep <hex_tid> -A 30 查看线程堆栈
  ↓
分析堆栈: 死循环? 频繁 GC? 正则回溯? 加密运算?
  ↓
如果堆栈显示 GC 线程: jstat -gcutil 查看 GC 频率 → 内存问题
如果堆栈显示业务线程: 定位具体代码行 → 优化算法/修复 bug
```

#### 5.3 内存泄漏排查

```
jmap -dump:format=b,file=heap.hprof <pid>  导出堆转储
  ↓
MAT 打开 heap.hprof
  ↓
Leak Suspects 报告 → 查看可疑对象
  ↓
Dominator Tree → 找到 Retained Size 最大的对象
  ↓
查看 GC Roots 引用链 → 确认谁持有引用不释放
  ↓
常见原因: static 集合未清理 / ThreadLocal 未 remove / 监听器未注销 / 缓存无限增长
```

> **Shallow Size vs Retained Size**: Shallow 是对象自身大小，Retained 是对象被回收后能释放的总大小（包括其引用的所有对象）。排查泄漏看 Retained Size。

#### 5.4 Full GC 频繁排查

```
jstat -gcutil <pid> 1000 持续观察 GC 频率和老年代使用率
  ↓
确认 Full GC 触发原因:
  ├── 老年代空间不足 → 堆太小 or 内存泄漏 or 大对象过多
  ├── Metaspace 不足 → 动态生成类太多
  ├── System.gc() 被调用 → 代码或框架主动触发
  └── CMS Concurrent Mode Failure → 预留空间不够
  ↓
对症下药:
  ├── 增大堆/老年代
  ├── 增大 MetaspaceSize
  ├── 加 -XX:+DisableExplicitGC 禁止 System.gc()
  └── 换收集器（如 CMS → G1）
```

### 6. G1 调优建议

| 参数 | 建议值 | 说明 |
|------|--------|------|
| `-XX:MaxGCPauseMillis=200` | 200ms（默认） | 目标停顿时间，G1 会尽量满足 |
| `-XX:InitiatingHeapOccupancyPercent=45` | 45%（默认） | 堆使用率达到多少开始并发标记 |
| `-XX:G1HeapRegionSize` | 根据堆大小自动计算 | 1-32MB，大堆建议设大一些 |
| `-XX:G1MixedGCLiveThresholdPercent=85` | 85%（默认） | Region 存活对象比例低于此值才纳入 Mixed GC |

**G1 调优核心原则**:
1. **不要设年轻代大小**（`-Xmn`），让 G1 自行调整 Region 分配
2. **MaxGCPauseMillis 是目标不是保证**，设太小会牺牲吞吐量
3. **IHOP 适当调低**，让并发标记更早开始，避免 Full GC
4. **关注 Mixed GC 频率**，如果 Mixed GC 后老年代仍然很高，可能需要增大堆

## 三、面试题

### Q1: 线上服务 OOM 了怎么排查？

**答**: 第一步确认 OOM 类型（heap/metaspace/direct buffer）。堆 OOM 的话，如果提前配了 `-XX:+HeapDumpOnOutOfMemoryError`，拿到 dump 文件用 MAT 分析 Leak Suspects 和 Dominator Tree，找到占用内存最大的对象和引用链，定位泄漏代码。如果没有 dump，用 `jmap -dump` 在线导出（注意会 STW）。

### Q2: 线上 CPU 100% 怎么排查？

**答**: `top` 找到 Java 进程 PID，`top -Hp <pid>` 找到最忙线程的 TID，转十六进制后用 `jstack <pid> | grep <hex_tid>` 查看线程堆栈。如果堆栈显示 GC 线程，用 `jstat` 看 GC 频率，可能是内存不足导致频繁 GC。如果堆栈显示业务线程，直接定位到代码行排查（死循环、正则回溯、加密运算等）。

### Q3: 常用的 JVM 参数有哪些？

**答**: 堆设置：`-Xms` `-Xmx`（建议相同）`-Xmn` `-Xss`；方法区：`-XX:MetaspaceSize` `-XX:MaxMetaspaceSize`；收集器：`-XX:+UseG1GC`；GC 日志：`-Xlog:gc*`（JDK 9+）；OOM 时 dump：`-XX:+HeapDumpOnOutOfMemoryError`。

### Q4: jstat、jmap、jstack 分别什么场景使用？

**答**: jstat 用于实时查看 GC 统计（频率、各区域使用率）；jmap 用于查看堆内存概况和导出 heap dump（OOM 排查）；jstack 用于查看线程堆栈（CPU 高、死锁、线程挂起等问题排查）。

### Q5: Arthas 和 JDK 自带工具有什么区别？

**答**: Arthas 最大优势是不需要重启应用就能在线诊断。JDK 工具功能基础但安全可靠，Arthas 提供了 watch（方法观测）、trace（调用链耗时分析）、jad（在线反编译）等高级功能，更适合线上问题排查。但 Arthas 需要额外安装，使用时要注意对性能的影响。

### Q6: 如何分析 GC 日志判断是否需要调优？

**答**: 关注三个指标：(1) Full GC 频率——正常应该很少（几小时一次甚至更少），频繁 Full GC 需要调优；(2) GC 停顿时间——关注 real 时间，是否影响用户体验；(3) 各区域使用率——老年代是否持续增长不下降（可能泄漏）。如果 GC 后堆内存回收效果差（回收前后变化小），需要排查大对象或内存泄漏。

### Q7: G1 调优有哪些注意事项？

**答**: (1) Xms 和 Xmx 设一样，避免动态扩容；(2) 不要手动设年轻代大小，让 G1 自动管理 Region；(3) MaxGCPauseMillis 设合理值（200ms），太小会牺牲吞吐量；(4) 关注 Mixed GC 是否正常触发，避免退化成 Full GC；(5) 堆大时适当增大 RegionSize。

### Q8: 如何排查内存泄漏？

**答**: (1) `jmap -dump` 导出堆转储；(2) 用 MAT 打开，查看 Leak Suspects 报告；(3) 关注 Retained Size 最大的对象（不是 Shallow Size）；(4) 通过 GC Roots 引用链找到谁持有引用不释放；(5) 常见原因：static 集合只增不减、ThreadLocal 未 remove、监听器未注销、缓存无淘汰策略。

## 四、常见误区

| 误区 | 正确理解 |
|------|----------|
| 调优就是调大堆 | 堆越大 GC 停顿越长，需要平衡 |
| Xms 和 Xmx 不同可以省内存 | 动态扩容会触发 Full GC，建议相同 |
| System.gc() 会立即 GC | 只是建议，JVM 可能忽略；可加 `-XX:+DisableExplicitGC` 禁用 |
| jmap dump 不影响服务 | dump 会触发 STW，线上低峰期操作 |
| GC 调优能解决所有性能问题 | 先优化代码，调优是最后手段 |
| Arthas 完全没有性能影响 | watch/trace 对性能有影响，线上慎用 |

## 五、实战场景

1. **上线前标配参数**: `-Xms2g -Xmx2g -XX:+UseG1GC -XX:+HeapDumpOnOutOfMemoryError -Xlog:gc*:file=gc.log`

3. **紧急排查 CPU 高**: Arthas `thread -n 5` 一键定位最忙线程
4. **内存泄漏**: MAT 分析 dump，重点关注 Retained Size 和引用链
