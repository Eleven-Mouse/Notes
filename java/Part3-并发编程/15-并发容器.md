## 二、核心知识点

### 2.1 ConcurrentHashMap JDK7 vs JDK8

| 维度    | JDK7                      | JDK8                 |
| ----- | ------------------------- | -------------------- |
| 数据结构  | Segment[] + HashEntry[]   | Node[] + 链表/红黑树      |
| 锁粒度   | Segment 级别（默认 16 段）       | Node 头节点级别（更细）       |
| 锁机制   | ReentrantLock（Segment 继承） | CAS + synchronized   |
| 查询复杂度 | O(n) 遍历链表                 | 链表 O(n)，红黑树 O(log n) |
| 并发度   | Segment 数量（默认 16）         | Node 数组长度            |

```
JDK7 结构：
  Segment[0]      Segment[1]  ...  Segment[15]     ← 16个Segment，各持一把锁
  ┌──────────┐    ┌─────────┐      ┌──────────┐
  │HashEntry │    │HashEntry│      │HashEntry │    ← 每个Segment下是链表数组
  │链表数组   │    │链表数组  │      │链表数组   │
  └──────────┘    └─────────┘      └──────────┘

JDK8 结构：
  Node[0]  Node[1]  Node[2]  ...  Node[n]      ← 一个大数组
  │        │        │              │
  null     Node→Node→Node         null          ← 链表（长度>8转红黑树）
           (链表)    (红黑树)
```

### 2.2 ConcurrentHashMap JDK8 put 流程

```
put(key, value)
    │
    ▼
  计算 key 的 hash值
    │
    ▼
  判断 Node[] 是否为空 → 初始化数组（CAS + 自旋）
    │
    ▼
  定位到桶位置 (n-1) & hash
    │
    ├── 桶为空 → CAS 写入新 Node（无锁）
    │
    ├── 桶不为空且 hash == MOVED(-1) → 正在扩容，帮助扩容
    │
    └── 桶不为空 → synchronized(头节点) 上锁
            │
            ├── 遍历链表，key 相同则覆盖 value
            ├── 没有相同 key → 尾插新节点
            └── 链表长度 >= 8 → 转红黑树（treeifyBin）
```

---

### 2.3 ConcurrentHashMap JDK8 get 流程

```
get(key)
    │
    ▼
  计算 hash，定位桶位置
    │
    ├── 桶为空 → 返回 null
    │
    ├── 桶的头节点匹配 → 直接返回 value
    │
    └── 头节点不匹配 →
            │
            ├── hash < 0（正在扩容/红黑树）→ 调用 find() 查找
            │
            └── 否则遍历链表查找

  注意：get 不加锁！
  Node 的 val 和 next 都用 volatile 修饰，保证可见性
```

---

### 2.4 ConcurrentHashMap resize（扩容）

```
扩容触发条件：元素总数 > 装载因子 * 数组长度（默认 0.75 * n）

多线程并发扩容（JDK8 亮点）：
  1. 新数组容量 = 旧数组 * 2
  2. 旧数组分成若干段，每个线程负责一段的迁移
  3. 迁移完成的桶放置 ForwardingNode（hash=MOVED=-1）
  4. 其他线程 put 时遇到 ForwardingNode，知道在扩容，帮助扩容
  5. 所有段迁移完成，切换到新数组
```

### 2.5 ConcurrentHashMap 的 size() 怎么算

```
JDK7：遍历所有 Segment，累加 count（先乐观读，不一致再加锁）

JDK8：
  baseCount（基础计数） + CounterCell[]（分散计数，类似 LongAdder）
  │
  ├── 无竞争时：CAS 更新 baseCount
  ├── 有竞争时：不同线程更新不同的 CounterCell（分散热点）
  └── size() = baseCount + 所有 CounterCell 的值

  注意：size() 返回的是一个近似值（并发下可能不准确）
  如果需要精确值：用 mappingCount()
```

### 2.6 CopyOnWriteArrayList

```java
// 写时复制原理
public boolean add(E e) {
    synchronized (lock) {            // 加锁
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1); // 复制新数组
        newElements[len] = e;
        setArray(newElements);       // 指向新数组
        return true;
    }
}

// 读不加锁
public E get(int index) {
    return elementAt(getArray(), index); // 直接读数组引用（volatile）
}
```

| 特点 | 说明 |
|------|------|
| 读操作 | 不加锁，直接读 volatile 数组引用 |
| 写操作 | 加锁 + 复制整个数组 → 代价大 |
| 迭代器 | 弱一致性，遍历的是创建时的快照 |
| 适用场景 | 读多写少（如配置列表、监听器列表） |
| 不适用 | 写多场景（频繁复制数组，内存压力大） |

### 2.7 BlockingQueue 阻塞队列

| 队列 | 特点 | 有界 | 适用场景 |
|------|------|------|---------|
| ArrayBlockingQueue | 数组实现，公平/非公平可选（ReentrantLock） | 有界 | 线程池任务队列 |
| LinkedBlockingQueue | 链表实现，默认无界（Integer.MAX_VALUE） | 可有界 | 生产者-消费者 |
| PriorityBlockingQueue | 支持优先级排序（自然顺序或 Comparator） | 无界 | 任务按优先级处理 |
| SynchronousQueue | 不存储元素，每个 put 必须等 take | — | CachedThreadPool |
| DelayQueue | 元素到期才能取出 | 无界 | 延时任务（订单超时） |
| LinkedTransferQueue | transfer 直接传给消费者 | 无界 | 消息传递 |

**核心方法**：

| 方法 | 抛异常 | 返回值 | 阻塞 | 超时 |
|------|--------|--------|------|------|
| 插入 | add(e) | offer(e) | put(e) | offer(e, time, unit) |
| 移除 | remove() | poll() | take() | poll(time, unit) |
| 检查 | element() | peek() | — | — |

### 2.8 ConcurrentSkipListMap（跳表）

```
跳表结构（多层索引，空间换时间）：

Level 3:  Head ──────────────────────────────────── 50
Level 2:  Head ────────── 20 ───────────────────── 50
Level 1:  Head ── 10 ──── 20 ──── 30 ──────────── 50
Level 0:  Head → 5 → 10 → 15 → 20 → 25 → 30 → 40 → 50 → 60

查找过程：从最高层开始，逐层向下缩小范围
  查找 25：Head(L3) → Head(L2) → 20(L2) → 20(L1) → 25(L0)
  时间复杂度：O(log n)，与平衡树相当
```

| 特点 | 说明 |
|------|------|
| 有序 | 按 key 自然排序或指定 Comparator |
| 线程安全 | CAS 实现，无锁 |
| 对比 TreeMap | TreeMap 非线程安全，ConcurrentSkipListMap 线程安全 |
| 时间复杂度 | 查找/插入/删除均为 O(log n) |

### 2.9 为什么 Collections.synchronizedXXX 不推荐

```java
// synchronizedXXX 实现（以 HashMap 为例）
public V get(Object key) {
    synchronized (mutex) { return m.get(key); } // 每个操作都加全局锁
}
public V put(K key, V value) {
    synchronized (mutex) { return m.put(key, value); } // 全局锁
}
```

| 对比 | Collections.synchronizedMap | ConcurrentHashMap |
|------|---------------------------|-------------------|
| 锁粒度 | 全局锁（一个 mutex） | 桶级别锁（Node 头） |
| 读操作 | 加锁 | 不加锁（volatile 读） |
| 迭代 | 必须手动加锁 | 弱一致性，不需要加锁 |
| 性能 | 低 | 高 |

## 三、面试题

### Q1：ConcurrentHashMap JDK7 和 JDK8 的区别？（超高频）
**答**：JDK7 用 Segment 分段锁（默认 16 段），每段一个 ReentrantLock。JDK8 改为 CAS + synchronized，锁粒度从 Segment 细化到 Node 头节点；数据结构增加红黑树（链表长度 > 8 转红黑树）；并发度不再受 Segment 数量限制。

### Q2：ConcurrentHashMap 的 put 流程？
**答**：(1) 计算 hash 定位桶；(2) 桶为空则 CAS 写入；(3) 桶正在扩容（hash=-1）则帮助扩容；(4) 否则 synchronized 头节点，遍历链表/红黑树插入或覆盖；(5) 链表长度 >= 8 转红黑树。

### Q3：ConcurrentHashMap 的 get 需要加锁吗？
**答**：不需要。Node 的 val 和 next 都用 volatile 修饰，保证了可见性。读操作直接通过 volatile 语义获取最新值。

### Q4：ConcurrentHashMap 的 size() 怎么实现的？
**答**：JDK8 采用 baseCount + CounterCell[] 类似 LongAdder 的分散计数方案。无竞争时 CAS 更新 baseCount，有竞争时各线程更新不同 CounterCell。size() 累加所有值，返回近似值。

### Q5：CopyOnWriteArrayList 的原理？适用场景？
**答**：写时复制——写操作加锁后复制整个数组，修改新数组，然后将引用指向新数组。读操作不加锁。适合读多写少场景（如监听器列表），不适合频繁写的场景。

### Q6：BlockingQueue 有哪些实现？分别什么场景？
**答**：ArrayBlockingQueue 有界队列适合线程池；LinkedBlockingQueue 可无界适合生产者-消费者；SynchronousQueue 不存储元素适合直接传递；PriorityBlockingQueue 适合按优先级处理；DelayQueue 适合延时任务。

### Q7：ConcurrentHashMap 能完全替代 Hashtable 吗？
**答**：功能上可以，性能上远优于 Hashtable。Hashtable 用 synchronized 修饰每个方法（全局锁），ConcurrentHashMap 锁粒度细得多。但注意 ConcurrentHashMap 不允许 key/value 为 null，Hashtable 也不允许。

### Q8：什么是弱一致性迭代器？
**答**：ConcurrentHashMap 的迭代器在遍历时不会抛 ConcurrentModificationException，但可能不会反映遍历过程中的修改（能看到迭代器创建时的状态和之后部分修改）。这是性能和一致性之间的权衡。

## 四、常见误区

| 误区 | 正确理解 |
|------|---------|
| "ConcurrentHashMap 允许 null key" | 不允许，put null 会 NPE |
| "ConcurrentHashMap 的 size() 精确" | 并发下是近似值 |
| "synchronizedMap 可以替代 ConcurrentHashMap" | 全局锁性能远差 |
| "CopyOnWriteArrayList 适合写多场景" | 写时复制整个数组，写多性能差 |
| "ConcurrentHashMap put 一定会加锁" | 桶为空时用 CAS 不加锁 |
| "BlockingQueue 的 add 和 put 一样" | add 满了抛异常，put 满了阻塞等待 |

## 五、实战场景

1. **全局缓存**：ConcurrentHashMap 存储配置/元数据，高并发读写
2. **任务队列**：线程池用 ArrayBlockingQueue 存储待执行任务
3. **监听器管理**：CopyOnWriteArrayList 管理事件监听器（遍历多，增删少）
4. **延时任务**：DelayQueue 实现订单超时自动取消
5. **排行榜**：ConcurrentSkipListMap 维护有序排名数据
