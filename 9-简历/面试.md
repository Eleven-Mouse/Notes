## 项目：古树名木普查（GSDC）  

- 防止并发修改导致的数据覆盖，在调查记录的更新操作中引入乐观锁机制；  
  >答：乐观锁的底层实现就是cas（比较并交换），靠cpu原语保证原子性
  >我们先解决了并发更新时谁覆盖谁的问题，做法是给记录加版本字段（version），每次更新都自动加1，更新sql 里统一做版本递进（patch/状态更新/删除）这样至少能保证“每次写操作都有版本演进”，确保每次修改都有版本轨迹，便于并发问题的定位和后续冲突控制，
  >例如： UPDATE t_order
		  SET status = ?, version = version + 1
		  WHERE id = ? AND version = ?
  
- 基于 PostGIS 实现空间数据存储和行政区坐标反查，完成 WGS84/CGCS2000 坐标系变换和空间索引配置；  
>行政区反查的核心是：输入点先统一到业务坐标系，再做空间包含判断
>1，首先  我们就会判断你传来的坐标是什么类型
>	如果是像(116.3, 39.9)这种经纬度，就当它是WGS84，就不符合我们系统的要求，如果不是经纬度范围，就当它已经是投影坐标了，就是符合我们系统要求的4549
>2，统一坐标
>	经纬度先 ST_Transform 转成 4549，保证“点”和”行政区面“在同一坐标系下比较
>	如果不统一坐标系，判断会偏，甚至完全错误
>3，先粗筛再精判
>	&&： xzq.geom && p.geom  这个点的包围框有没有落进这个行政区面的包围框范围
>	ST_Covers：再做精确包含判断，ST_Covers(xzq.geom, p.geom) 才是精确空间关系判断，意思是“这个行政区面是否真正覆盖这个点”。
>4，多个行政区覆盖时怎么选
>	ORDER BY ST_Area 选面积最小的那个面。
	这样通常会选到更细一级的区划，减少边界附近“到底算哪个区”的歧义。


- 参与实现 AI 植物识别服务，采用多账号轮询 + CAS 限流 + ArrayBlockingQueue 异步处理应对第三方 API 调用频率限制；  
>因为第三方api调用时有使用频率限制的，为了解决这个问题我做了三层缓冲：
>1，入口排队，用ArrayBlockingQueue 做有界排队，队列满了就快速失败，防止服务被拖死
>worker 异步消费，主线程只等 future 结果
- 针对多巡检员并发提交时的编号冲突问题，基于 PostgreSQL Advisory Lock 实现按县区串行化的业务 ID 生成，在保证 tree_id 唯一性和连续性的同时避免了分布式锁引入的额外依赖；  

- 针对外业弱网场景下数据提交丢失的用户反馈，设计草稿/提交分层校验策略：草稿仅校验必填项支持中途保存，提交时执行完整业务规则校验，减少因网络中断导致的数据丢失；  

- 采用 DDD 分层架构组织业务模块，划分 adapter/application/domain/infrastructure 四层职责，在项目中实践了领域模型与基础设施的解耦；
