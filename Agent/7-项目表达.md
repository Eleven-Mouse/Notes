## 1. 项目概述

### 1.1 项目名称

**智能客服 Agent 系统（Smart Customer Service Agent）**

### 1.2 业务背景

> 某电商平台，日均客服咨询量 5 万+，涉及订单查询、物流追踪、退换货处理、商品咨询等场景。
>
> 原有方案：传统规则引擎 + 关键词匹配 + 人工兜底，准确率 60%，人工转接率 40%。
>
> 目标：用 Agent 构建智能客服，提升自动解决率，降低人工成本。

### 1.3 项目指标（面试可量化）

| 指标 | 优化前 | 优化后 | 提升幅度 |
|------|-------|-------|---------|
| 自动解决率 | 60% | 85% | +25% |
| 人工转接率 | 40% | 15% | -25% |
| 平均响应时间 | 30 秒 | 5 秒 | -83% |
| 用户满意度 | 72% | 91% | +19% |
| 月度 Token 成本 | - | 3 万/月 | 可控 |
| P99 延迟 | - | < 5s | 达标 |

### 1.4 技术栈

| 层级 | 技术选型 | 理由 |
|------|---------|------|
| Agent 编排 | LangChain + LangGraph | 成熟生态 + 灵活编排 |
| LLM | 通义千问（主）+ GPT-4o（复杂场景） | 国内部署合规 + 效果兜底 |
| 向量数据库 | Milvus | 千万级文档高性能 |
| 短期记忆 | Redis | 会话级别存储 |
| 长期记忆 | Milvus + MySQL | 向量检索 + 结构化查询 |
| 工具层 | MCP Server | 标准化工具调用 |
| 后端框架 | Spring Boot 3.x | Java 主流 |
| 可观测性 | LangSmith + Prometheus | 全链路追踪 + 指标监控 |

## 3. 核心模块详解

### 3.1 意图识别 + 路由分发（Workflow 层）

```
用户消息进入
    │
    ▼
意图分类器（通义-turbo / Haiku，延迟 < 200ms）
    │
    ├── 订单查询 → 路由到「订单 Agent」
    ├── 物流咨询 → 路由到「物流 Agent」
    ├── 退换货   → 路由到「售后 Agent」
    ├── 商品咨询 → 直接走 RAG（不经过 Agent，节省成本）
    ├── 投诉     → 直接转人工（高风险场景）
    └── 其他     → 走通用 Agent 兜底
```

**为什么这里用 Workflow：** 意图识别是确定性的分类任务，用小模型做分类就够了，不需要 Agent 的动态决策。成本低、延迟低、结果稳定。

### 3.2 Agent 执行引擎（核心）

以"订单 Agent"为例，ReAct 执行流程：

```
用户："我的订单123456到哪了，怎么还没到？"
    │
    ▼
Thought: 用户想查订单123456的物流状态
Action: query_order({orderId: "123456"})
Observation: 订单已发货，顺丰SF1234，预计4月27日送达
    │
    ▼
Thought: 订单在途，用户可能着急，查一下物流详情
Action: query_logistics({orderId: "123456"})
Observation: 4月25日到达北京分拣中心，预计明天送达
    │
    ▼
Thought: 信息完整，可以回答了。预计明天到，给用户安抚
Final Answer: "您的订单123456已到达北京分拣中心，预计明天（4月27日）送达。
              由于快递中转需要时间，还请耐心等待。如有问题可以随时联系我。"
```

### 3.3 MCP 工具层

```java
// 订单 MCP Server
@Component
public class OrderMcpServer {

    @Autowired private OrderService orderService;

    @McpTool(name = "query_order", description = "根据订单号查询订单详情，包含状态、金额、商品信息")
    public OrderDetail queryOrder(
        @McpParam(name = "orderId", description = "订单号") String orderId
    ) {
        return orderService.queryDetail(orderId);
    }

    @McpTool(name = "cancel_order", description = "取消未发货的订单")
    public Result cancelOrder(
        @McpParam(name = "orderId", description = "订单号") String orderId,
        @McpParam(name = "reason", description = "取消原因") String reason
    ) {
        // 高风险操作 → Human-in-the-loop
        return orderService.cancel(orderId, reason);
    }
}
```

### 3.4 RAG 知识库

```
离线索引：
  商品文档（10000+）→ PDF解析 → 500字递归分片 → BGE-large-zh 向量化 → Milvus
  售后政策（50+）   → Markdown解析 → 300字分片 → 向量化 → Milvus
  FAQ 问答对（5000+）→ 直接向量化 → Milvus

在线检索：
  问题 → BGE 向量化 → Milvus 向量检索(Top-10) + ES BM25(Top-10)
       → RRF 融合排序 → BGE-Reranker 精排 → Top-3 → 注入 Prompt
```

### 3.5 Memory 系统

```
用户进入对话：
  ├── L1 工作记忆：最近 5 轮对话拼接到 Prompt（~2K Token）
  ├── L2 短期记忆：Redis 存完整会话历史，24h 过期
  └── L3 长期记忆：
       ├── 用户历史偏好（Milvus 向量检索）
       └── 历史订单摘要（MySQL 结构化查询）
```

## 4. 技术亮点（面试展开讲，每个亮点 30 秒）

### 亮点 1：Workflow + Agent 混合架构

> 不是所有场景都用 Agent。意图识别用 Workflow（小模型分类），简单查询走 RAG（不经过 Agent），只有需要多步推理和工具调用的场景才启动 Agent。
>
> 这样整体成本降低 60%，平均响应时间从 15 秒降到 5 秒。

### 亮点 2：分级模型策略

> 不是所有 LLM 调用都用大模型。意图识别用通义-turbo（$0.01），Agent 推理用通义-plus（$0.05），复杂投诉用 GPT-4o（$0.30）。
>
> 月度 Token 成本从预估的 8 万降到实际 3 万。

### 亮点 3：MCP 标准化工具调用

> 现有 Spring Boot 微服务通过 MCP 适配层暴露给 Agent，新增客服场景只需启动新 MCP Server。
>
> 工具调用标准化后，从通义切换到 GPT-4o，工具层代码零修改。

### 亮点 4：RAG 混合检索 + Reranker

> 同时用向量检索（语义匹配）和 BM25（关键词匹配），RRF 融合排序 + BGE-Reranker 精排。
>
> 检索准确率从 75%（纯向量）提升到 92%（混合+Reranker）。

### 亮点 5：全链路可观测性

> LangSmith 做全链路 Tracing（每一步 Thought/Action/Observation 都有记录），Prometheus 监控 Token 消耗、工具调用成功率、P99 延迟。
>
> 出问题分钟级定位——是 LLM 决策错误还是工具调用失败。

### 亮点 6：稳定性保障

> 最大迭代次数 8 次、死循环检测、参数 Schema 校验、输出质量评估。
>
> 高风险操作（取消订单、退款）Human-in-the-loop 人工确认。
>
> Agent 失败自动走 Fallback 预设流程。

## 5. 面试讲法（完整模拟）

### 【开场 30 秒】

> 我负责了一个智能客服 Agent 系统的架构设计和核心开发。
>
> 业务背景是电商平台，日均客服咨询 5 万条。原规则引擎准确率 60%。我们用 LangChain + LangGraph 搭建了 Workflow + Agent 混合架构——意图识别走 Workflow，多步推理走 Agent。
>
> 最终自动解决率提升到 85%，人工转接降到 15%，平均响应 5 秒。

### 【深入讲解 2 分钟——"详细讲讲架构"】

> 系统分四层：
>
> **第一层 Spring Boot 网关**，负责会话管理、鉴权、限流和审计。
>
> **第二层 LangGraph 编排层**。用户消息进来后，先用通义-turbo 做意图分类——订单/物流/售后/商品/投诉。分类后路由到不同专职 Agent。商品咨询这种简单场景直接走 RAG 不经过 Agent。
>
> **第三层 MCP 工具层**。每个 Agent 通过 MCP 调用内部微服务。MCP 的好处是工具标准化，换模型不需要改工具代码，多个 Agent 共享同一套 MCP Server。
>
> **第四层数据层**：RAG 用 Milvus 做向量存储，混合检索加 Reranker 精排。Memory 分三层——Prompt 中传最近 5 轮、Redis 存完整会话、Milvus+MySQL 做长期记忆。
>
> 可观测性用 LangSmith + Prometheus。

### 【被追问"技术挑战"——1 分钟】

> 最大挑战是稳定性和成本。
>
> 稳定性：加了最大 8 次迭代限制、死循环检测、参数校验、输出质量评分。高风险操作加人工确认。Agent 失败走 Fallback。
>
> 成本：分级模型策略，意图识别用通义-turbo，Agent 用通义-plus，复杂场景用 GPT-4o。月度 Token 从 8 万降到 3 万。
>
> 检索效果：初期纯向量检索准确率只有 75%，加了 BM25 混合检索和 Reranker 后提升到 92%。
