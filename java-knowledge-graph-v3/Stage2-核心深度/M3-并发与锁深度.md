## 知识点 1：synchronized 与 CAS ⭐🔥

### 【是什么】
synchronized 是 JVM 内置的互斥锁机制，CAS 是无锁并发的底层原语（Compare-And-Swap）。

### 【原理】

#### synchronized 锁升级过程

```
一个对象从无锁 → 偏向锁 → 轻量级锁 → 重量级锁 的升级过程：

┌──────────────────────────────────────────────────┐
│ Mark Word (64 bit) 锁状态变化                      │
├──────────────────────────────────────────────────┤
│                                                  │
│ 无锁：    [unused:25][identity_hashcode:31][0][01]│
│           ↑ hashCode第一次计算后写入               │
│                                                  │
│ 偏向锁：  [thread:54][epoch:2][0][01]             │
│           ↑ 记录获取锁的线程ID                     │
│           同一线程再次进入：检查threadID，无需CAS   │
│                                                  │
│ 轻量级锁：[ptr_to_lock_record:62][00]             │
│           ↑ 指向栈中Lock Record的指针              │
│           多线程轻度竞争：自旋CAS                   │
│                                                  │
│ 重量级锁：[ptr_to_heavyweight_monitor:62][10]      │
│           ↑ 指向ObjectMonitor的指针                │
│           严重竞争：线程阻塞（OS互斥量）            │
│                                                  │
│ GC标记：  [空][11]                                │
└──────────────────────────────────────────────────┘

升级是单向的（不可降级，G1下有例外）
```

#### CAS 原理

```java
// CAS = Compare And Swap（比较并交换）
// CPU指令级别的原子操作：cmpxchg

// 伪代码：
do {
    oldValue = memory.read(addr);      // 读当前值
    newValue = f(oldValue);            // 计算新值
} while (!compareAndSwap(addr, oldValue, newValue));
// 如果内存值==oldValue，就设为newValue，否则重试

// Java中的CAS → Unsafe类
// unsafe.compareAndSwapInt(obj, offset, expect, update)

// CAS三大问题：
// 1. ABA问题 → 解决：AtomicStampedReference（加版本号）
// 2. 自旋开销 → 解决：LongAdder分散热点 / 限制自旋次数
// 3. 只能单变量 → 解决：AtomicReference包装对象
```

### 【怎么用 — 项目落地】

**场景：博客系统的并发控制**

```java
// 场景1：文章点赞 — 用CAS实现原子操作
public class ArticleLikeService {
    private AtomicInteger likeCount = new AtomicInteger(0);

    public boolean like() {
        // CAS自增
        likeCount.incrementAndGet();  // 底层CAS
        return true;
    }
}

// 场景2：库存扣减（AI接口调用次数限制）
public class QuotaService {
    private AtomicLong remainQuota;

    public boolean deduct(String userId) {
        long current;
        do {
            current = remainQuota.get();
            if (current <= 0) return false;
        } while (!remainQuota.compareAndSet(current, current - 1));
        return true;
    }
}

// 场景3：用synchronized保护共享资源
public class CommentService {
    // 对同一篇文章的评论写入需要同步
    public synchronized void addComment(Long articleId, Comment comment) {
        // 同步块保护
        List<Comment> comments = getComments(articleId);
        comments.add(comment);
        saveComments(articleId, comments);
    }
}
```

### 【问题场景】

| 问题 | 场景 | 方案 |
|------|------|------|
| ABA | 账户余额从100→200→100 | AtomicStampedReference |
| 自旋耗CPU | 高并发下CAS持续失败 | 用synchronized或LongAdder |
| 锁膨胀 | 大量线程竞争同一把锁 | 分段锁/减小锁粒度 |
| 伪共享 | 多线程写相邻volatile变量 | @Contended注解填充缓存行 |

### 【面试怎么问】

**Q：synchronized的锁升级过程？**

> "JDK6引入锁升级优化。对象头的Mark Word记录锁状态。无锁→偏向锁：第一个线程获取锁时CAS写入线程ID，之后同线程重入只判断线程ID无需CAS。偏向锁→轻量级锁：第二个线程竞争时，撤销偏向，两个线程CAS竞争Lock Record。轻量级锁→重量级锁：自旋超过阈值（自适应自旋），升级为ObjectMonitor，线程阻塞。升级是单向的，一般不可降级。"

**追问：synchronized和ReentrantLock区别？**

> "synchronized是JVM层面（monitorenter/monitorexit），ReentrantLock是API层面（AQS）。synchronized自动释放，Lock必须手动unlock（finally中）。ReentrantLock支持公平锁、可中断、多条件变量（Condition）、超时获取。synchronized有锁升级优化。一般简单场景用synchronized，需要高级特性用ReentrantLock。"

## 知识点 2：AQS 与 Lock ⭐🔥

### 【是什么】
AQS（AbstractQueuedSynchronizer）是 Java 并发包的基石框架，提供了一套基于 FIFO 等待队列的锁机制模板。

### 【原理】

#### AQS 核心三要素（源码级）

```
┌──────────────────────────────────────────────────┐
│               AQS 核心结构                        │
│                                                  │
│  volatile int state                              │
│  ├── 独占模式：0=未锁，1=已锁，>1=重入               │
│  └── 共享模式：表示可用资源数（如Semaphore的许可数）   │
│                                                  │
│  CLH 双向队列（FIFO）                              │
│                                                  │
│        ┌──────┐    ┌──────┐    ┌──────┐          │
│  head →│Node A│ ←→ │Node B│ ←→ │Node C│ ← tail   │
│        └──────┘    └──────┘    └──────┘          │
│   SIGNAL   ←prev    next→                        │
│                                                  │
│  每个Node:                                        │
│  ├── Thread thread    → 等待的线程                 │
│  ├── int waitStatus   → CANCELLED(1)/SIGNAL(-1)   │
│  │                       /CONDITION(-2)/PROPAGATE │
│  ├── Node prev/next   → 双向链表指针                │
│  └── Node nextWaiter  → Condition队列用            │
│                                                   │
│  模板方法模式：                                     │
│  AQS定义: acquire/release/acquireShared/...       │
│  子类实现: tryAcquire/tryRelease/tryAcquireShared │
└──────────────────────────────────────────────────┘
```

#### ReentrantLock.lock() 源码流程（非公平锁）

```
lock()
  ├── compareAndSetState(0, 1)     ← CAS抢锁，不管队列
  │   ├── 成功 → setExclusiveOwnerThread(current) → 获取锁
  │   └── 失败 → acquire(1)
  │              ├── tryAcquire(1)  ← 再次尝试获取
  │              │   ├── state==0 → CAS抢锁（非公平：可插队）
  │              │   └── state>0 && owner==current → state++（重入）
  │              ├── addWaiter(EXCLUSIVE) ← 入队（CAS设置tail）
  │              └── acquireQueued(node, 1) ← 自旋获取/阻塞
  │                  ├── 前驱是head → tryAcquire
  │                  │   ├── 成功 → setHead(node) → 出队
  │                  │   └── 失败 → shouldParkAfterFailedAcquire
  │                  └── 前驱不是head → LockSupport.park(this)
  │
  unlock()
  ├── tryRelease(1)  ← state--
  │   └── state==0 → unparkSuccessor(head.next)
  └── LockSupport.unpark(succeedor.thread) ← 唤醒下一个节点
```

#### 公平锁 vs 非公平锁（源码差异）

```java
// 非公平锁：直接CAS抢锁
final void lock() {
    if (compareAndSetState(0, 1))  // 直接抢，不管队列
        setExclusiveOwnerThread(Thread.currentThread());
    else
        acquire(1);
}

// 公平锁：先检查队列
final void lock() {
    acquire(1);  // 不直接抢，走AQS流程
}

protected final boolean tryAcquire(int acquires) {
    if (c == 0) {
        if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) {
            // hasQueuedPredecessors() → 检查队列中是否有等更久的线程
            // 公平锁多了这个检查！
        }
    }
}
```

### 【怎么用 — 项目落地】

**场景：基于AQS实现自定义同步器**

```java
// 项目场景：AI接口限流器 — 同时只允许N个请求调用AI
public class AIRateLimiter extends AbstractQueuedSynchronizer {
    private final int maxConcurrent;

    public AIRateLimiter(int maxConcurrent) {
        this.maxConcurrent = maxConcurrent;
        setState(maxConcurrent); // 初始许可数
    }

    @Override
    protected int tryAcquireShared(int arg) {
        for (;;) {
            int current = getState();
            int remain = current - arg;
            if (remain < 0 || compareAndSetState(current, remain)) {
                return remain;  // <0 表示获取失败（需排队）
            }
        }
    }

    @Override
    protected boolean tryReleaseShared(int arg) {
        for (;;) {
            int current = getState();
            int next = current + arg;
            if (compareAndSetState(current, next)) {
                return true;
            }
        }
    }

    // 使用：
    // limiter.acquireShared(1);  // 获取许可
    // callAI();                   // 调用AI
    // limiter.releaseShared(1);  // 释放许可
}
```

### 【问题场景】

| 问题 | 场景 | 分析 |
|------|------|------|
| 公平锁吞吐低 | 高并发场景 | 每次都要检查队列，线程切换多 |
| 非公平锁饥饿 | 低优先级线程长期获取不到 | 适当改用公平锁 |
| 伪唤醒 | park后不该醒却醒了 | AQS自旋检查，不是只park一次 |
| 队列中CANCELLED节点 | 线程被中断/超时 | acquireQueued中会跳过cancelled节点 |

### 【面试怎么问】

**Q：AQS的原理？如何实现锁的？**

> "AQS核心是volatile int state + CLH双向队列。state表示同步状态，子类通过CAS修改state来获取锁。获取失败的线程封装成Node加入CLH队列尾，然后park阻塞。当锁释放时，unpark队列头节点的后继节点，唤醒它去竞争。模板方法模式：AQS定义acquire/release骨架，子类实现tryAcquire/tryRelease。ReentrantLock用state=0/1表示未锁/已锁，重入就state++。CountDownLatch用state表示倒计数。Semaphore用state表示许可数。"

**追问1：公平锁和非公平锁的区别？为什么默认非公平？**

> "公平锁在tryAcquire前先调用hasQueuedPredecessors检查队列中是否有等待线程。非公平锁直接CAS抢锁，允许插队。默认非公平是因为吞吐量更高：线程释放锁后，新来的线程直接CAS获取（不需要park/unpark的上下文切换），实测吞吐量高很多。代价是可能导致队列中的线程'饥饿'。"

**追问2：为什么用CLH队列而不是普通队列？**

> "CLH队列的优势：1.前驱节点的状态决定后继是否需要阻塞（look at predecessor策略）2.入队只需CAS设置tail，O(1)复杂度 3.节点状态维护简单（只需看前驱的waitStatus是否SIGNAL）4.适合自旋锁场景，CLH本身就是为自旋锁设计的队列。"

## 知识点 3：线程池 ⭐🔥

### 【是什么】
线程池是预先创建一组线程复用的机制，避免频繁创建销毁线程的开销，并控制并发度。

### 【原理】

#### 7大参数

```
ThreadPoolExecutor(
    int corePoolSize,        // 核心线程数（即使空闲也不回收，除非allowCoreThreadTimeOut）
    int maximumPoolSize,     // 最大线程数
    long keepAliveTime,      // 非核心线程空闲存活时间
    TimeUnit unit,           // 时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,        // 线程工厂（自定义线程名，便于排查）
    RejectedExecutionHandler handler    // 拒绝策略
)
```

#### 执行流程（面试必画）

```
                         提交任务 execute(task)
                                │
                    ┌───────────▼───────────┐
                    │ 当前线程数 < corePoolSize? │
                    └─────┬──────────┬──────┘
                         Yes         No
                          │           │
                   创建核心线程     ┌──▼────────────┐
                   直接执行任务     │ workQueue未满？ │
                                   └──┬─────────┬──┘
                                     Yes        No
                                      │          │
                               任务放入队列   ┌────▼──────────────┐
                               等待执行       │ 当前线程数 < max?  │
                                             └──┬───────────┬───┘
                                               Yes          No
                                                │             │
                                        创建非核心线程     ┌──▼──────┐
                                        立即执行任务       │ 拒绝策略  │
                                                          └─────────┘
```

#### 4种拒绝策略

```
AbortPolicy（默认）→ 抛RejectedExecutionException
CallerRunsPolicy   → 提交任务的线程自己执行（降速保护）
DiscardPolicy      → 静默丢弃（不抛异常）
DiscardOldestPolicy → 丢弃队列中最老的任务，重新提交
```

### 【怎么用 — 项目落地】

**场景：博客+AI系统的线程池设计**

```java
@Configuration
public class ThreadPoolConfig {

    // 1. 文章操作线程池（IO密集型）
    @Bean("articleExecutor")
    public ThreadPoolExecutor articleExecutor() {
        return new ThreadPoolExecutor(
            8,                              // 核心：8（IO密集，CPU核数*2）
            16,                             // 最大：16
            60, TimeUnit.SECONDS,           // 非核心60s回收
            new LinkedBlockingQueue<>(1000), // 有界队列，防OOM
            new ThreadFactory() {
                private final AtomicInteger i = new AtomicInteger(1);
                public Thread newThread(Runnable r) {
                    return new Thread(r, "article-pool-" + i.getAndIncrement());
                }
            },
            new ThreadPoolExecutor.CallerRunsPolicy() // 降速保护
        );
    }

    // 2. AI调用线程池（长耗时，需要隔离）
    @Bean("aiExecutor")
    public ThreadPoolExecutor aiExecutor() {
        return new ThreadPoolExecutor(
            4,                              // 核心少，AI调用慢
            8,
            120, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(500),
            r -> new Thread(r, "ai-pool-" + System.currentTimeMillis()),
            new ThreadPoolExecutor.AbortPolicy() // AI队列满了直接拒绝
        );
    }
}
```

### 【问题场景】

| 问题 | 原因 | 方案 |
|------|------|------|
| OOM | 队列用无界队列 | 必须用有界队列 |
| 任务丢失 | shutdown后队列中任务 | shutdownNow获取未执行列表 |
| 线程泄漏 | 未关闭线程池 | @PreDestroy关闭 |
| 死锁 | 任务间互相依赖 | 不同任务用不同线程池隔离 |

### 【面试怎么问】

**Q：线程池的参数怎么设置？**

> "分CPU密集型和IO密集型。CPU密集型：核心线程数=CPU核数+1，充分利用CPU。IO密集型：核心线程数=CPU核数*2或CPU核数/(1-阻塞系数)。队列长度根据业务容忍的延迟来设，一般500~2000。拒绝策略优先CallerRunsPolicy（让调用者线程执行，起到降速保护）。生产中必须给线程自定义名字，便于日志排查。"

**追问：为什么不推荐用Executors创建线程池？**

> "阿里巴巴规约禁止的原因：newFixedThreadPool和newSingleThreadPool用LinkedBlockingQueue（无界队列），任务堆积会OOM。newCachedThreadPool的maximumPoolSize=Integer.MAX_VALUE，可能创建海量线程导致OOM。手动创建ThreadPoolExecutor可以明确控制边界。"

## 知识点 4：volatile + JMM ⭐🔥

### 【是什么】
volatile 是 Java 的轻量级同步机制，保证可见性和有序性（不保证原子性）。JMM（Java Memory Model）定义了线程与内存的交互规范。

### 【原理】

#### JMM 三大特性

```
┌──────────────────────────────────────────────────┐
│               JMM 内存模型                        │
│                                                  │
│   线程A                  线程B                    │
│  ┌─────────┐            ┌─────────┐              │
│  │工作内存  │            │工作内存  │              │
│  │(副本)   │            │(副本)   │              │
│  └────┬────┘            └────┬────┘              │
│       │  read/load       write/store │            │
│       │  use             assign      │            │
│  ┌────▼──────────────────────────▼────┐          │
│  │          主内存（Main Memory）      │          │
│  │         共享变量的真实副本          │          │
│  └───────────────────────────────────┘          │
│                                                  │
│  JMM三大特性：                                    │
│  可见性：volatile写后立即刷回主存，其他线程立即可见  │
│  有序性：volatile读写前后插入内存屏障，禁止重排序    │
│  原子性：volatile不保证（i++不是原子操作）          │
└──────────────────────────────────────────────────┘
```

#### happens-before 8条规则

```
1. 程序顺序规则：同一线程中，前面的操作happens-before后面的
2. volatile变量规则：volatile写 happens-before 后续的volatile读
3. 锁规则：unlock happens-before 后续的lock
4. 传递性：A→B, B→C 则 A→C
5. 线程启动：start() happens-before 线程内的所有操作
6. 线程终止：线程内操作 happens-before join()返回
7. 线程中断：interrupt() happens-before 被中断线程检测到中断
8. 对象构造：构造方法 happens-before finalize()
```

#### volatile 底层实现

```
volatile写：
  StoreStore屏障  → 保证前面所有普通写已刷新
  volatile写操作
  StoreLoad屏障   → 保证volatile写对后续读可见

volatile读：
  volatile读操作
  LoadLoad屏障    → 保证后面的读不会被重排到前面
  LoadStore屏障   → 保证后面的写不会被重排到前面
```

### 【怎么用 — 项目落地】

**场景：DCL单例模式（双重检查锁）**

```java
public class AIClient {
    private static volatile AIClient instance; // 必须volatile

    public static AIClient getInstance() {
        if (instance == null) {                    // 第一次检查（无锁）
            synchronized (AIClient.class) {
                if (instance == null) {            // 第二次检查（加锁）
                    instance = new AIClient();     // volatile防止指令重排
                }
            }
        }
        return instance;
    }
}

// 为什么需要volatile？
// new AIClient() 不是原子操作，分三步：
// 1. 分配内存空间
// 2. 初始化对象
// 3. 将引用指向内存地址
// 不加volatile，2和3可能重排序：
// 线程A执行了1→3（还没初始化），线程B第一次检查instance!=null，返回未初始化的对象 → NPE
```

### 【面试怎么问】

**Q：volatile的作用？原理？**

> "volatile保证可见性和有序性，不保证原子性。可见性：volatile写操作会强制刷回主存，并让其他线程的工作内存副本失效。有序性：通过内存屏障禁止指令重排序。底层通过Lock前缀指令实现：1.锁定缓存行，写回主存 2.使其他CPU缓存行失效（MESI协议）。经典应用是DCL单例模式。"

**追问：volatile和synchronized区别？**

> "volatile是轻量级同步，只保证可见性+有序性，不保证原子性。synchronized是重量级，保证三大特性。volatile不会阻塞线程，synchronized会。volatile修饰变量，synchronized修饰方法/代码块。volatile适用于一个线程写、多个线程读的场景（如状态标志位），涉及复合操作（i++）必须用synchronized或Atomic类。"

## 知识点 5：ThreadLocal ⭐🔥

### 【是什么】
ThreadLocal 提供线程本地变量，每个线程独立拥有一份副本，线程间互不干扰。

### 【原理】

#### 底层结构
```
Thread
  └── ThreadLocal.ThreadLocalMap
        └── Entry[] table
              └── Entry extends WeakReference<ThreadLocal>
                    ├── key = ThreadLocal（弱引用）
                    └── value = 线程本地值（强引用）

每个Thread对象持有一个ThreadLocalMap
ThreadLocalMap是ThreadLocal的静态内部类
Entry的key是ThreadLocal本身（弱引用），value是实际存储的值
```

#### 内存泄漏原理（面试必问）
```
┌─────────────────────────────────────────────┐
│  内存泄漏链路：                                │
│                                             │
│  Thread（强引用）                             │
│    └── ThreadLocalMap（强引用）                │
│          └── Entry[]                         │
│                └── Entry                     │
│                      ├── key → ThreadLocal   │
│                      │   （WeakReference）    │
│                      │   GC后key=null        │
│                      └── value → 实际对象    │
│                          （强引用，GC回收不了） │
│                                             │
│  当ThreadLocal被GC回收后：                    │
│  key=null, value还在 → 内存泄漏              │
│                                             │
│  为什么key用弱引用？                          │
│  → 如果key是强引用，ThreadLocal对象本身都无法回收│
│  → 用弱引用至少保证ThreadLocal对象可以被回收    │
│                                             │
│  解决：用完必须remove()！                     │
└─────────────────────────────────────────────┘
```

### 【怎么用 — 项目落地】

**场景：博客系统中ThreadLocal存储用户上下文**

```java
// 用户上下文工具类
public class UserContext {
    private static final ThreadLocal<User> currentUser = new ThreadLocal<>();

    public static void set(User user) {
        currentUser.set(user);
    }

    public static User get() {
        return currentUser.get();
    }

    public static void remove() {
        currentUser.remove();  // 必须调用！
    }
}

// 拦截器中设置
@Component
public class AuthInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, ...) {

        return true;
    }

    @Override
    public void afterCompletion(...) {
        UserContext.remove();  // 请求结束必须清理！防止线程池复用导致泄漏
    }
}

// Service中直接使用
@Service

    public Article createArticle(ArticleDTO dto) {
        User user = UserContext.get(); // 无需传参
        // ...
    }
}
```

### 【面试怎么问】

**Q：ThreadLocal原理？为什么会内存泄漏？**

> "ThreadLocal通过在每个Thread对象中维护一个ThreadLocalMap来存储线程本地变量。ThreadLocalMap的Entry的key是ThreadLocal的弱引用，value是强引用。当ThreadLocal被GC回收后，key变为null但value仍然存在，形成内存泄漏。线程池场景下更严重，因为线程不会销毁。解决方法是使用完毕后在finally中调用remove()清理。"

**追问：ThreadLocal和InheritableThreadLocal区别？在线程池中怎么传递？**

> "InheritableThreadLocal可以在子线程创建时继承父线程的值。但在线程池中，线程是复用的，不会重新创建，所以无法继承。解决方案是阿里开源的TransmittableThreadLocal（TTL），通过装饰Runnable/Callable，在任务执行前capture父线程值，执行时replay，执行后restore。"

## 知识点 6：分布式锁 ⭐🔥

### 【是什么】
在分布式系统中，多个节点需要对共享资源互斥访问时使用的跨进程锁机制。

### 【原理】

#### 三种实现对比
```
┌──────────┬──────────────────┬──────────────────┬──────────────────┐
│ 维度      │ Redis            │ ZooKeeper        │ MySQL            │
├──────────┼──────────────────┼──────────────────┼──────────────────┤
│ 实现方式  │ SETNX + 过期时间  │ 临时顺序节点      │ 行锁/唯一索引     │
│ 性能     │ 最高（内存）       │ 中（网络开销）     │ 最低（磁盘）      │
│ 可靠性   │ 中（宕机可能丢锁）  │ 高（Session机制）  │ 高（事务保证）    │
│ 过期续约  │ Redisson看门狗    │ 临时节点自动删除   │ 事务超时自动释放  │
│ 公平性   │ 非公平            │ 公平（顺序节点）   │ 非公平           │
│ 适用场景  │ 高并发短任务       │ 强一致性要求       │ 低并发简单场景    │
└──────────┴──────────────────┴──────────────────┴──────────────────┘
```

#### Redisson 看门狗原理
```
加锁成功后，启动后台线程（Watchdog）
每10秒（leaseTime/3）检查锁是否还被持有
如果持有 → 自动续约30秒（默认leaseTime）
如果持锁线程宕机 → 看门狗停止续约 → 锁30秒后自动过期

代码：
RLock lock = redisson.getLock("article:lock:" + articleId);
lock.lock();  // 默认30秒过期，看门狗自动续约
// 或指定leaseTime但不用看门狗：
lock.lock(10, TimeUnit.SECONDS);
```

### 【怎么用 — 项目落地】

**场景：博客系统文章编辑锁**

```java
@Service
public class ArticleService {
    @Autowired
    private RedissonClient redisson;

    public void editArticle(Long articleId, ArticleDTO dto) {
        RLock lock = redisson.getLock("article:edit:" + articleId);
        try {
            // 尝试加锁：最多等待5秒，锁自动过期30秒
            if (lock.tryLock(5, 30, TimeUnit.SECONDS)) {
                try {
                    // 1. 查询文章
                    Article article = articleMapper.selectById(articleId);
                    // 2. 更新
                    article.setTitle(dto.getTitle());
                    article.setContent(dto.getContent());
                    // 3. 保存
                    articleMapper.updateById(article);
                    // 4. 清除缓存
                    redis.del("article:detail:" + articleId);
                } finally {
                    lock.unlock();
                }
            } else {
                throw new BusinessException("文章正在编辑中，请稍后再试");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

### 【面试怎么问】

**Q：分布式锁怎么实现？Redis和ZK的区别？**

> "Redis用SETNX+过期时间实现，高并发性能好，但宕机可能丢锁（RedLock方案解决但争议大）。ZK用临时顺序节点，天然支持公平锁和锁重入，Session断开自动释放，可靠性高但性能不如Redis。MySQL用行锁或唯一索引，最简单但性能差。生产中推荐Redisson，内置看门狗自动续约，支持可重入、公平锁、读写锁。"

**追问：Redisson看门狗机制？如果业务执行时间超过锁过期时间？**

> "Redisson加锁时如果不指定leaseTime，默认30秒过期，同时启动看门狗线程。看门狗每10秒（leaseTime/3）检查：如果锁还被当前线程持有，自动续约到30秒。业务执行完unlock后看门狗停止。如果持锁节点宕机，看门狗线程也死了，锁30秒后自动过期，其他节点可以获取。关键：不能指定leaseTime，否则看门狗不生效。"
