## Module 1: Java 基础

### Q1：HashMap 底层原理？为什么用红黑树？

**追问1：** HashMap 的扩容机制？JDK7 和 JDK8 扩容有什么区别？
**追问2：** HashMap 线程不安全体现在哪里？多线程下用什么？

> **标准回答：**
> "HashMap 底层数组+链表+红黑树（JDK8）。put先hash扰动定位桶，空桶直接插入，冲突时链表尾插。链表>=8且数组>=64转红黑树（查找O(logN)），<6退回链表。扩容2倍，JDK8用hash&oldCap判断新位置不用重新hash。线程不安全：JDK7头插法并发扩容死循环，JDK8尾插不死循环但会数据丢失。多线程用ConcurrentHashMap。初始化建议指定容量避免频繁扩容：容量=（预期元素数/0.75）+1。"

### Q2：ConcurrentHashMap 怎么保证线程安全？

**追问1：** JDK7 和 JDK8 实现有什么不同？
**追问2：** ConcurrentHashMap 的 get 需要加锁吗？为什么？

> **标准回答：**
> "JDK7用Segment分段锁，16个Segment每个是一把ReentrantLock。JDK8用CAS+synchronized，空桶CAS插入，冲突时synchronized锁头节点，锁粒度从Segment级别细化到桶级别。get全程无锁，因为Node的val和next是volatile修饰，保证可见性。扩容时多线程协作，通过transferIndex分片，每个线程负责一段桶的迁移。size()方法用baseCount+CounterCell数组实现无锁计数（类似LongAdder思路）。"

## Module 2: JVM

### Q1：说一下 JVM 内存模型？堆怎么分代？

**追问1：** 对象什么时候进入老年代？
**追问2：** 如何判断对象可以被回收？GC Roots有哪些？

> **标准回答：**
> "JVM内存分线程私有（PC、栈、本地方法栈）和共享（堆、方法区/元空间）。堆分新生代（Eden+S0+S1，8:1:1）和老年代。对象进入老年代：年龄达阈值/大对象直接进入/动态年龄判断/Survivor放不下。GC判断用可达性分析，从GC Roots出发不可达的可回收。GC Roots包括栈帧引用、静态变量、常量、JNI引用、锁持有对象。程序计数器是唯一不会OOM的区域。"

### Q2：G1 收集器的原理？和 CMS 比有什么优势？

**追问1：** G1 什么时候会 Full GC？怎么避免？
**追问2：** ZGC 了解吗？和 G1 的区别？

> **标准回答：**
> "G1将堆划分为等大Region（1~32MB），优先回收垃圾最多的Region（Garbage First）。三种回收：Young GC回收所有Young Region，Mixed GC回收Young+部分Old Region，Full GC是退化场景。相比CMS：1.G1可控制停顿时间（MaxGCPauseMillis）2.基于Region整理避免碎片 3.没有浮动垃圾问题。ZGC是JDK15+的收集器，通过染色指针和读屏障实现亚毫秒停顿，支持TB级堆，停顿时间不随堆增大而增加。G1的停顿和Region数相关，ZGC始终亚毫秒。"

### Q3：线上 OOM 怎么排查？

**追问1：** CPU 100% 怎么排查？
**追问2：** 频繁 Full GC 怎么处理？

> **标准回答：**
> "OOM排查：1.配置HeapDumpOnOutOfMemoryError自动dump 2.MAT分析支配树找最大对象 3.沿GC Roots引用链定位泄漏源。CPU 100%：1.top找PID 2.top -Hp找最高线程 3.printf转十六进制 4.jstack定位代码行。频繁Full GC：jstat确认频率和趋势，Full GC后老年代不下降说明内存泄漏，下降后快速填满说明空间不足，调大堆或降低晋升阈值。生产中用G1 + -XX:MaxGCPauseMillis控制停顿，配合Arthas实时诊断。"

## Module 3: 并发编程

### Q1：synchronized 和 ReentrantLock 的区别？

**追问1：** synchronized 的锁升级过程？
**追问2：** volatile 和 synchronized 的区别？

> **标准回答：**
> "synchronized是JVM内置锁，monitorenter/monitorexit字节码实现，自动释放。ReentrantLock是AQS实现的API锁，需手动unlock。ReentrantLock支持公平锁、可中断、超时、多Condition。synchronized有锁升级优化（偏向→轻量→重量），JDK6后性能接近。volatile只保证可见性+有序性不保证原子性，synchronized三大特性都保证。简单场景用synchronized，需要公平/可中断/多条件用ReentrantLock。"

### Q2：AQS 的原理？CountDownLatch 和 Semaphore 的实现？

**追问1：** 公平锁和非公平锁的区别？
**追问2：** AQS 的独占模式和共享模式区别？

> **标准回答：**
> "AQS核心是volatile int state + CLH双向队列。独占模式（ReentrantLock）：state=0/1表示锁状态，获取失败的线程入队park，释放时unpark后继。共享模式（Semaphore/CountDownLatch）：state表示资源数/计数，多个线程可同时获取。CountDownLatch初始化state=N，countDown()使state-1，await()检查state==0才放行。Semaphore的tryAcquireShared返回值>=0表示获取成功。公平锁在tryAcquire前检查hasQueuedPredecessors，非公平直接CAS。"

### Q3：线程池的参数怎么设置？

**追问1：** 为什么不推荐用 Executors？
**追问2：** 线程池的拒绝策略有哪些？生产中用哪个？

> **标准回答：**
> "CPU密集型核心线程=CPU核数+1，IO密集型=CPU核数*2。队列用有界队列（LinkedBlockingQueue(500)），防OOM。拒绝策略推荐CallerRunsPolicy让调用者线程执行，起到降速保护。不推荐Executors：newFixedThreadPool用无界队列会OOM，newCachedThreadPool最大线程Integer.MAX_VALUE会创建海量线程。生产中手动创建ThreadPoolExecutor，指定自定义ThreadFactory命名线程，finally中unlock/shutdown。"

## Module 4: MySQL

### Q1：MySQL 为什么用 B+ 树做索引？

**追问1：** 什么是回表？覆盖索引？
**追问2：** 联合索引 (a,b,c)，where a=1 and c=3 走索引吗？

> **标准回答：**
> "B+树相比B树：1.非叶子不存数据，一页放更多key，树更矮IO少 2.叶子链表支持范围查询 3.查询性能稳定。3层B+树存2000万条只需3次IO。回表是二级索引查到主键后再查聚簇索引，覆盖索引是查询字段都在索引中不需要回表（explain显示Using index）。联合索引(a,b,c)中where a=1 and c=3，a走索引c不走（中间b断了，不满足最左前缀）。但如果开启了索引下推（ICP），存储引擎会在索引中先过滤c，减少回表次数。"

### Q2：MVCC 的原理？RC 和 RR 有什么区别？

**追问1：** MySQL 怎么防止幻读？
**追问2：** RR 级别下一定不会出现幻读吗？

> **标准回答：**
> "MVCC通过隐藏字段（事务ID+回滚指针）+ Undo版本链 + ReadView实现。ReadView记录当前活跃事务，通过可见性规则判断版本链中哪个版本对当前事务可见。RC每次SELECT创建新ReadView，RR只在第一次SELECT创建。防幻读：RR级别下Next-Key Lock（Record+Gap）锁住间隙防止新插入。但RR级别下仍可能出现幻读的特殊情况：事务中先普通读（快照读），再当前读（SELECT FOR UPDATE），后者会读到新插入的行。"

### Q3：慢查询怎么优化？

**追问1：** EXPLAIN 的 type 字段有哪些？什么算好？
**追问2：** 深分页怎么优化？

> **标准回答：**
> "慢查询优化步骤：1.EXPLAIN看执行计划 2.type字段从好到差：system>const>eq_ref>ref>range>index>ALL 3.确保type至少是range。常见优化：加索引/覆盖索引/联合索引/索引下推。深分页优化：延迟关联，先用子查询通过覆盖索引拿到id，再回表取完整数据。其他方案：游标分页（WHERE id > last_id LIMIT 20）。线上通过slow_query_log + pt-query-digest分析慢SQL。"

## Module 5: Redis

### Q1：Redis 为什么快？

**追问1：** Redis 和 Memcached 的区别？
**追问2：** Redis 的线程模型？

> **标准回答：**
> "Redis快的原因：1.纯内存操作 2.单线程避免上下文切换和锁竞争 3.IO多路复用（epoll） 4.高效的数据结构（SDS/ziplist/skiplist）。Redis6.0引入多线程处理网络IO读写，但命令执行仍是单线程。和Memcached区别：Redis支持更多数据类型、支持持久化、支持集群、单线程（MC多线程）。Redis线程模型：主线程+后台线程（bgsave/bgrewriteaof/close fd），6.0+增加IO线程处理读写。"

### Q2：缓存穿透、击穿、雪崩怎么解决？

**追问1：** 缓存和数据库一致性怎么保证？
**追问2：** 热点 Key 怎么处理？

> **标准回答：**
> "穿透（查不存在的数据）：布隆过滤器+缓存空值。击穿（热点key过期）：互斥锁（Redisson）+逻辑过期。雪崩（大量key同时过期）：TTL加随机值+多级缓存+限流。一致性：Cache Aside模式（先DB后删缓存），延迟双删（删→更新DB→延迟再删），终极方案Canal监听Binlog异步删缓存。热点Key：1.本地缓存（Caffeine）作为L1 2.拆分成多个key分散到不同节点 3.Redis集群分片。"

## Module 6: Spring

### Q1：Spring IOC 的原理？Bean 的生命周期？

**追问1：** BeanFactory 和 ApplicationContext 区别？
**追问2：** Spring 怎么解决循环依赖？

> **标准回答：**
> "IOC通过BeanDefinition扫描和注册（@Component/@Service/@Configuration），在refresh()中实例化所有非懒加载单例Bean。Bean生命周期：实例化→属性注入→Aware回调→BeanPostProcessor前置→@PostConstruct→afterPropertiesSet→init-method→BeanPostProcessor后置（AOP代理在此生成）→销毁。循环依赖通过三级缓存解决：一级完整Bean、二级早期引用、三级ObjectFactory。构造器注入的循环依赖无法自动解决，需@Lazy。"

### Q2：Spring 事务什么时候会失效？

**追问1：** @Transactional(readOnly=true) 有什么用？
**追问2：** 事务传播行为 REQUIRED 和 NESTED 区别？

> **标准回答：**
> "事务失效六种：1.非public方法 2.同类调用（this不经过代理）3.异常被内部catch 4.rollbackFor没配 5.MyISAM引擎 6.未被Spring管理。最容易被忽略的是rollbackFor=Exception.class。readOnly=true提示驱动优化（MySQL的InnoDB不支持真正只读事务，但会做一些优化）。REQUIRED共用事务一起回滚，NESTED通过Savepoint实现嵌套，内层回滚不影响外层，但外层回滚内层也回滚。"

### Q3：Spring Boot 自动装配原理？

**追问1：** @Conditional 注解有什么用？
**追问2：** 如何自定义 Starter？

> **标准回答：**
> "@SpringBootApplication包含@EnableAutoConfiguration，通过SpringFactoriesLoader加载META-INF/spring.factories中的配置类。@Conditional系列注解（@ConditionalOnClass/@ConditionalOnMissingBean等）按条件决定是否装配。自定义Starter：1.创建xxx-spring-boot-starter模块 2.编写自动配置类@Configuration+@ConditionalOnClass 3.在spring.factories中注册 4.创建spring-configuration-metadata.json提供提示。Spring Boot 3.x改用META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports。"

## Module 7: 消息队列

### Q1：如何保证消息不丢失？

**追问1：** 如何保证消息顺序？
**追问2：** 消息积压怎么处理？

> **标准回答：**
> "三端保证：生产者（acks=all+重试+回调确认）、Broker（min.insync.replicas>=2）、消费者（手动提交offset）。消息顺序：同一业务key发同一partition，单线程消费或内存队列保证顺序。积压处理：1.紧急扩容消费者 2.增加partition 3.如果超过 retention 先转储再消费 4.排查消费端是否有阻塞。重复消费：消费者端实现幂等（唯一键去重/数据库唯一约束/Redis setnx）。"

## Module 8: 分布式系统

### Q1：CAP 理论？你的项目怎么取舍的？

**追问1：** 一致性哈希的原理？虚拟节点有什么用？
**追问2：** 分布式事务有哪些方案？

> **标准回答：**
> "CAP：一致性/可用性/分区容错性三者只能满足两个。因为网络分区（P）必然存在，所以实际是CP或AP的取舍。注册中心：Nacos支持AP/CP切换，Eureka是AP，ZK是CP。一致性哈希：将hash值空间组织成环，节点和key都映射到环上，顺时针找最近的节点。虚拟节点解决数据倾斜问题，每个物理节点对应多个虚拟节点，使分布更均匀。分布式事务：强一致用2PC（Seata AT），最终一致用TCC/消息事务/Saga。大多数场景用消息最终一致性，性能和可靠性折中。"
