## 二、系统设计面试答题框架

### 四步法

```
Step 1：需求确认（5 分钟）
  - 明确功能范围（核心功能 vs 边缘功能）
  - 明确非功能性需求（QPS / 延迟 / 数据量 / 可用性）
  - 确定约束条件

Step 2：高层设计（5-10 分钟）
  - 画出整体架构图
  - 列出核心组件
  - 说明数据流向

Step 3：详细设计（15-20 分钟）
  - 深入核心组件的实现
  - 讨论技术选型和 trade-off
  - 解决技术难点（并发/一致性/性能）

Step 4：扩展讨论（5 分钟）
  - 瓶颈分析
  - 扩展方案（水平扩展/缓存/异步）
  - 容灾和监控
```

## 三、秒杀系统设计

### 整体架构

```
用户 → CDN（静态资源）
     → Nginx（负载均衡 + 限流）
     → Gateway（鉴权 + 限流）
     → 秒杀服务
        ├── Redis（预扣库存 + 分布式锁）
        ├── MQ（异步下单）
        └── DB（最终落单）
```

### 核心方案

```
1. 活动前：
   - 商品库存预热到 Redis
   - 秒杀链接动态生成（防提前刷接口）

2. 秒杀中：
   - 网关层限流（令牌桶，QPS 控制）
   - Redis 原子预扣库存（Lua 脚本保证原子性）
   - 异步下单（发送 MQ，立即返回"排队中"）
   - 用户端轮询/ WebSocket 获取结果

3. 秒杀后：
   - MQ 消费者创建订单
   - 超时未支付则回补库存
   - 订单入库
```

### 库存扣减 Lua 脚本

```lua
-- Redis + Lua 原子扣减库存
local stock_key = KEYS[1]           -- "seckill:stock:goods_001"
local user_key = KEYS[2]            -- "seckill:users:goods_001"
local user_id = ARGV[1]
local deduct_num = tonumber(ARGV[2])

-- 1. 检查是否已经购买过（防重复）
if redis.call('sismember', user_key, user_id) == 1 then
    return -1  -- 已购买
end

-- 2. 检查库存
local stock = tonumber(redis.call('get', stock_key) or '0')
if stock < deduct_num then
    return 0  -- 库存不足
end

-- 3. 扣减库存 + 记录用户（原子操作）
redis.call('decrby', stock_key, deduct_num)
redis.call('sadd', user_key, user_id)

return 1  -- 扣减成功
```

### 防超卖方案

| 方案 | 实现 | 优缺点 |
|------|------|--------|
| **Redis Lua 原子扣减** | 预扣库存到 Redis，Lua 保证原子性 | 推荐，性能高 |
| **DB 乐观锁** | `UPDATE stock SET count=count-1 WHERE goods_id=? AND count>0` | 简单但 DB 压力大 |
| **DB 悲观锁** | `SELECT ... FOR UPDATE` | 强一致但性能差 |

### 防刷方案

```
1. 验证码：秒杀前输入验证码（防机器人 + 削峰）
2. 接口限流：令牌桶控制 QPS
3. 用户频率控制：Redis 记录用户请求次数（如 1 分钟内最多 5 次）
4. IP 限流：防止同一 IP 高频请求
5. 黑名单机制：异常用户加入黑名单
6. 隐藏秒杀地址：动态 URL，活动开始时才暴露
```

## 四、短链系统设计

### 核心流程

```
生成长链：
  用户提交长 URL → 生成短码 → 存储 映射关系 → 返回短链

访问短链：
  用户点击短链 → 查询短码对应的长链 → 302 重定向到长链

完整流程：
  https://short.cn/abc123 → 查询 → https://www.example.com/very/long/url/...
                          → 302 Redirect
```

### 短码生成算法

#### 方案一：自增 ID + Base62

```
1. 数据库自增 ID：1, 2, 3, ...
2. 转为 Base62 编码：1→1, 10→a, 62→10, ...

Base62 字符集：0-9 a-z A-Z（62 个字符）
6 位短码可表示 62^6 = 568 亿个 URL

问题：短码可预测，可能被遍历
解决：ID 加盐/混淆（如加一个随机前缀或位运算打乱）
```

#### 方案二：MurmurHash

```
对长 URL 做 MurmurHash → 取前 6 位作为短码

问题：哈希冲突
解决：如果冲突，追加随机盐重新 Hash，或使用数据库唯一约束检测

Base62 编码示例：
  ID = 123456789
  123456789 转为 62 进制 → "8M0kx"
  不足 6 位前面补 0 → "08M0kx"（实际实现可能不需要补位）
```

### 存储方案

```
写入：
  短码 + 长URL + 创建时间 + 过期时间 → MySQL（持久化）
                                  → Redis（缓存，加速查询）

读取（高频操作）：
  1. 先查 Redis（短码 → 长URL）
  2. Redis 未命中 → 查 MySQL → 写入 Redis
  3. 302 重定向

高可用：
  MySQL 主从复制 + 分库分表（按短码 Hash 分片）
  Redis 集群（主从 + 哨兵 / Cluster）
```

### 302 vs 301

```
301（永久重定向）：
  浏览器缓存，后续直接跳转，不经过短链服务
  优点：快    缺点：无法统计点击量

302（临时重定向）：
  每次都经过短链服务
  优点：可统计点击量/来源    缺点：多一次服务端跳转

推荐：302（短链服务通常需要统计分析功能）
```

## 五、其他常见系统设计题概览

### 新闻 Feed 流

```
推模式（写扩散）：发文时写入所有粉丝的收件箱
  适用：粉丝少的大多数用户

拉模式（读扩散）：读 Feed 时从关注列表聚合
  适用：粉丝多的超级大 V

推拉结合：
  普通用户用推模式
  大 V 用拉模式
```

### IM 即时通讯系统

```
核心问题：消息的实时推送

方案：
  - WebSocket 长连接
  - 消息存储（发件箱 + 收件箱模型）
  - 消息已读/未读（计数器）
  - 离线消息（拉取）
  - 群聊（写扩散优化）
```

### 搜索建议（自动补全）

```
方案：
  - 前缀树（Trie）：适合小数据量
  - Elasticsearch（completion suggester）：适合大数据量
  - Redis 有序集合：按搜索热度排序

实时性：
  记录用户搜索词 → 聚合统计热度 → 更新建议词库
```

## 六、面试题

### Q1：设计一个秒杀系统？🔥🔥🔥🔥🔥

架构：CDN → Nginx 限流 → Gateway 鉴权限流 → 秒杀服务 → Redis 预扣库存 → MQ 异步下单 → DB。核心：Redis Lua 原子扣减防超卖、MQ 异步削峰、验证码防机器人、动态 URL 防提前刷。

### Q2：如何防止超卖？🔥🔥🔥🔥

Redis Lua 脚本原子操作：检查库存 → 扣减 → 记录用户（一个 Lua 脚本内完成，Redis 单线程保证原子性）。DB 层面用乐观锁兜底：`UPDATE stock SET count=count-1 WHERE id=? AND count>0`。

### Q3：设计一个短链系统？🔥🔥🔥

短码生成（自增 ID + Base62 或 MurmurHash），存储（MySQL + Redis 缓存），302 重定向（可统计点击），高可用（MySQL 分片 + Redis 集群）。

### Q4：秒杀系统如何扛住高并发？🔥🔥🔥

分层防护：CDN 挡静态资源、Nginx 限流、Gateway 限流鉴权、Redis 预扣库存（不走 DB）、MQ 异步削峰。核心思想：层层过滤，最终到 DB 的请求极少。

### Q5：短链系统的短码如何生成？有什么问题？🔥🔥

自增 ID + Base62（可预测需加盐混淆）或 MurmurHash（有冲突需检测）。6 位 Base62 可表示 568 亿 URL，通常够用。

### Q6：系统设计面试应该怎么回答？🔥🔥

四步法：需求确认（明确范围和约束）→ 高层设计（架构图 + 数据流）→ 详细设计（核心组件 + 技术选型 + trade-off）→ 扩展讨论（瓶颈 + 扩展 + 容灾）。边说边画图，主动讨论 trade-off。

## 七、常见误区

| 误区 | 正确理解 |
|------|----------|
| 秒杀直接操作数据库 | 应该用 Redis 预扣库存，MQ 异步下单，保护 DB |
| 短码必须全局唯一 | 需要唯一性保证（数据库唯一约束） |
| 系统设计要面面俱到 | 抓核心矛盾，重点解决最大瓶颈，体现 trade-off 思维 |
| 高并发 = 加机器 | 先优化单机性能，再考虑水平扩展 |
| 一上来就讲详细实现 | 先确认需求、画高层架构，再深入细节 |

## 八、实战场景

### 秒杀系统完整链路

```
时间线：
  T-7d：商品信息预热到 Redis + CDN
  T-1h：秒杀链接生成（动态加密 URL）
  T-5min：前端倒计时，加载验证码
  T-0s：用户点击 → 验证码校验 → Redis Lua 预扣库存 → 发 MQ
  T+0.5s：返回"排队中"
  T+2s：MQ 消费者创建订单 → DB
  T+5s：用户轮询/WebSocket 收到结果
  T+15min：超时未支付 → 回补库存
```
