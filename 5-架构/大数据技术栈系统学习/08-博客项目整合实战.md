# 博客项目主线实战：串起 Jenkins、K8s、Doris、Scala、Spark、HDFS 和分布式

## 结论

博客项目可以利用，而且很适合作为学习这些技术的实战载体。

这篇文档是整个专题的主线。其它每篇技术文档都应该回到这个项目里验证，而不是只停留在概念学习。

正确方式不是把所有技术硬塞进博客核心业务，而是把博客拆成三层：

```text
博客业务层
  -> 工程化部署层
  -> 数据分析层
```

这样既能保留博客项目本身的业务完整性，又能自然引入 Jenkins、K8s、HDFS、Spark、Doris 等技术。

主线原则：

```text
博客业务保持干净，工程化和数据分析作为能力扩展。
```

## 总体架构

推荐目标：

```text
博客系统 + DevOps 自动化 + 访问日志分析平台
```

整体链路：

```text
用户访问博客
  |
  v
博客服务记录访问日志
  |
  v
日志落盘或进入采集组件
  |
  v
HDFS 保存原始日志
  |
  v
Spark + Scala 清洗和统计
  |
  v
Doris 保存统计结果
  |
  v
后台报表 / SQL / BI 查询
```

部署链路：

```text
提交博客代码
  |
  v
Jenkins 拉代码
  |
  v
编译、测试、打包
  |
  v
构建 Docker 镜像
  |
  v
推送镜像仓库
  |
  v
K8s 滚动部署博客服务
```

## 每个技术在博客项目里怎么用

| 技术 | 在博客项目里的角色 | 什么时候用 | 能做什么 |
| --- | --- | --- | --- |
| 分布式 | 架构思想 | 博客访问量上来、服务要多实例、高可用时 | 负载均衡、多实例部署、故障恢复、缓存拆分 |
| Jenkins | 自动化流水线 | 需要稳定构建、测试、部署时 | 自动拉代码、跑测试、打包、构建镜像、部署 |
| K8s | 运行平台 | 服务需要容器化部署、滚动更新、扩缩容时 | 管理 Pod、Service、配置、健康检查、滚动发布 |
| HDFS | 原始日志存储 | 访问日志量变大，需要长期保存和离线分析时 | 存储海量日志、作为 Spark 输入 |
| Spark | 日志计算引擎 | 需要统计 PV、UV、热门文章、用户行为时 | 清洗日志、聚合指标、生成日报 |
| Scala | Spark 任务语言 | 使用 Scala 写 Spark 作业或读 Spark 源码时 | 编写 ETL、解析日志、聚合统计 |
| Doris | 分析查询库 | 指标结果需要快速查询、做后台报表时 | 查询 PV/UV、热门文章、趋势图数据 |

## 不要怎么用

这些做法不推荐：

- 不要为了用 HDFS，把博客文章正文存进 HDFS。
- 不要为了用 Spark，让每次用户访问都触发 Spark 任务。
- 不要为了用 Doris，替代博客核心业务库。
- 不要为了用 K8s，一开始就把所有组件都部署进去。
- 不要为了用 Jenkins，写一堆没有测试和回滚价值的复杂流水线。

更合理的边界：

```text
MySQL：存博客业务数据
Redis：做缓存、计数、限流
HDFS：存访问日志和离线数据
Spark：做离线统计
Doris：存统计结果并支撑查询
Jenkins：自动化构建部署
K8s：运行博客服务和相关任务
```

## 第一阶段：把博客业务做扎实

目标：先有一个完整博客系统。

建议功能：

- 文章发布
- 文章列表
- 文章详情
- 分类
- 标签
- 评论
- 浏览量
- 用户登录
- 后台管理

架构重点：

- Controller 不写复杂业务。
- Service 承载业务逻辑。
- Repository / Mapper 负责数据访问。
- DTO / VO 和数据库实体分清楚。
- 文章、评论、用户、标签边界清楚。

验收标准：

- 博客主流程能跑通。
- 数据库表结构清晰。
- 接口有基本参数校验。
- 关键业务有日志。
- 项目能一键启动。

## 第二阶段：接入 Jenkins

目标：把手工构建变成自动化。

流水线：

```text
Git 提交
  |
  v
Jenkins 拉代码
  |
  v
运行测试
  |
  v
打包 Jar
  |
  v
归档构建产物
```

重点：

- Jenkinsfile
- Maven / Gradle 构建
- 单元测试
- 构建日志
- 构建产物
- 凭据管理

验收标准：

- 推送代码后能触发构建。
- 测试失败时流水线失败。
- 能下载打包产物。
- 密码、Token 不写死在代码里。

## 第三阶段：Docker + K8s 部署博客

目标：让博客服务具备现代部署能力。

部署链路：

```text
博客 Jar
  |
  v
Docker 镜像
  |
  v
K8s Deployment
  |
  v
K8s Service
  |
  v
Ingress 或网关访问
```

K8s 重点：

- Deployment：部署无状态博客服务。
- Service：给博客服务提供稳定访问入口。
- ConfigMap：管理普通配置。
- Secret：管理敏感配置。
- Readiness Probe：确认服务能不能接流量。
- Liveness Probe：确认服务是否需要重启。
- Resource Request / Limit：限制资源使用。

验收标准：

- 能把博客打成 Docker 镜像。
- 能部署到 K8s。
- 能通过 Service 或 Ingress 访问。
- 能滚动更新版本。
- Pod 异常时能查看日志和事件。

## 第四阶段：记录访问日志

目标：为数据分析准备原始数据。

日志内容建议：

```text
request_id,user_id,article_id,path,ip,user_agent,referer,event_time,status,cost_ms
```

重点：

- 每次访问文章详情时记录日志。
- 日志格式稳定。
- 时间字段统一。
- request_id 方便排查链路。
- 不要在日志里记录明文密码、Token 等敏感信息。

验收标准：

- 访问文章会产生结构化日志。
- 日志能按天切分。
- 日志字段能支撑 PV、UV、热门文章分析。

## 第五阶段：日志进入 HDFS

目标：把原始访问日志保存到大数据存储层。

推荐目录：

```text
/data/blog/access_log/dt=2026-07-23/access.log
/data/blog/access_log/dt=2026-07-24/access.log
```

重点：

- 按日期分区。
- 控制小文件数量。
- 原始日志尽量不要随意覆盖。
- 脏数据交给后续 Spark 清洗。

验收标准：

- 能把日志上传到 HDFS。
- 能按日期查看日志。
- Spark 能读取对应目录。
- 能说明小文件问题怎么处理。

## 第六阶段：Spark + Scala 做日志分析

目标：从访问日志中生成分析指标。

建议指标：

- 每日 PV
- 每日 UV
- 每篇文章 PV
- 热门文章 Top 10
- 平均响应耗时
- 状态码分布
- 访问来源分布

处理链路：

```text
读取 HDFS 日志
  |
  v
解析字段
  |
  v
过滤脏数据
  |
  v
按日期、文章、来源聚合
  |
  v
输出指标结果
```

重点：

- 使用 case class 表示日志。
- 使用 Option 处理脏数据。
- 使用 DataFrame / Spark SQL 做聚合。
- 注意 Shuffle 和数据倾斜。
- 输出结果要有清晰 Schema。

验收标准：

- 脏日志不会导致任务失败。
- PV、UV 结果正确。
- 任务能重复执行。
- 同一天重复跑不会产生重复结果。

## 第七阶段：Doris 做分析查询

目标：让统计结果能被快速查询。

建议表：

```text
blog_article_daily_stat
blog_site_daily_stat
blog_referer_daily_stat
blog_status_daily_stat
```

典型字段：

```text
dt, article_id, pv, uv, avg_cost_ms
```

重点：

- 按 dt 分区。
- 按 article_id 或 event_type 分桶。
- 明细表和聚合表分开。
- 报表查询优先查聚合表。

验收标准：

- Spark 结果能写入 Doris。
- Doris SQL 能查每日 PV、UV。
- 能查热门文章 Top 10。
- 能解释为什么这样分区和分桶。

## 第八阶段：后台报表

目标：把数据分析结果展示到博客后台。

页面建议：

- 站点总览
- 每日趋势
- 热门文章
- 访问来源
- 状态码分布
- 慢请求排行

接口链路：

```text
博客后台接口
  |
  v
查询 Doris
  |
  v
返回报表数据
```

重点：

- 报表接口只查聚合结果。
- 不要每次页面访问都触发 Spark。
- 查询条件要限制时间范围。
- 慢查询需要加索引、分区或预聚合。

验收标准：

- 后台能看到 PV、UV。
- 能看到热门文章。
- 能按日期筛选。
- 页面查询不会拖垮主业务库。

## 分阶段落地顺序

推荐顺序：

```text
博客主功能
  -> Jenkins 自动构建
  -> Docker 镜像化
  -> K8s 部署
  -> 访问日志
  -> HDFS 存日志
  -> Spark + Scala 分析
  -> Doris 查询
  -> 后台报表
```

为什么先 Jenkins、Docker、K8s：

- 博客项目天然适合练部署。
- 工程化收益马上可见。
- 后续大数据任务也能复用流水线。

为什么后做 HDFS、Spark、Doris：

- 这些技术需要数据量和分析场景。
- 访问日志分析是最自然的入口。
- 不会污染博客核心业务。

## 面试表达

可以这样讲：

```text
我不是只做了一个普通博客，而是在博客基础上扩展了工程化部署和数据分析能力。

工程化方面，我用 Jenkins 做 CI/CD，用 Docker 镜像化服务，并通过 K8s 实现滚动部署、健康检查和配置管理。

数据分析方面，我把博客访问日志按日期落到 HDFS，用 Spark + Scala 做离线清洗和指标统计，最后把 PV、UV、热门文章等结果写入 Doris，供后台报表快速查询。
```

这个表达的重点是：

- 博客是业务载体。
- Jenkins 和 K8s 体现工程化能力。
- HDFS、Spark、Doris 体现数据平台能力。
- 分布式思维贯穿多实例、高可用、存储和计算。

## 最终验收标准

- 博客功能完整可用。
- Jenkins 能自动构建和部署。
- 博客服务能运行在 K8s。
- 访问日志结构化输出。
- 日志能进入 HDFS。
- Spark 能统计访问指标。
- Doris 能查询分析结果。
- 后台能展示核心报表。
- 能清楚解释每个技术为什么用、什么时候用、能做什么。

## 一句话总结

博客项目最适合当“技术承载体”：**业务主线保持简单，工程化用 Jenkins + K8s，数据分析用 HDFS + Spark + Doris，分布式思想贯穿整体架构。**
