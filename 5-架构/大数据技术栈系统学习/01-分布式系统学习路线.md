# 分布式系统学习路线：从小白到架构思维

## 结论

分布式不是某个框架，而是一种系统设计思想：**当一台机器存不下、算不动、扛不住、不能容忍单点故障时，把系统拆到多台机器上协同工作。**

但分布式不是银弹。它解决了规模问题，也带来了网络、数据一致性、故障恢复、排查复杂度等新问题。

## 它是什么

单机系统里，代码、数据、计算、请求都主要发生在一台机器上。

分布式系统里，一个完整能力由多台机器共同完成：

```text
用户请求
  |
  v
负载均衡
  |
  v
多个服务实例
  |
  v
缓存 / 消息队列 / 数据库 / 文件系统 / 计算引擎
```

核心变化是：

- 机器会宕机。
- 网络会延迟。
- 消息可能重复。
- 数据可能短时间不一致。
- 一次请求可能跨多个服务。

## 什么时候用

适合使用分布式的场景：

- 单机 CPU、内存、磁盘不够。
- 数据量很大，需要分片存储。
- 请求量很高，需要多实例抗流量。
- 任务很重，需要多机器并行计算。
- 系统不能因为一台机器宕机就整体不可用。
- 团队和业务复杂，需要服务拆分。

不适合一开始就分布式的场景：

- 业务还很小。
- 单机数据库足够。
- 团队没有运维和排障能力。
- 问题主要是代码混乱，而不是容量不够。

一句话：

```text
能用单机稳稳解决时，不要急着上分布式。
单机已经成为瓶颈时，分布式才是工程解法。
```

## 能做什么

分布式系统主要能解决：

- **扩展性**：通过加机器提升处理能力。
- **高可用**：部分机器故障时，系统仍可继续服务。
- **大数据存储**：例如 HDFS 把大文件分块存到多台机器。
- **大数据计算**：例如 Spark 把任务拆成多个分区并行执行。
- **服务治理**：例如微服务、注册中心、网关、限流、熔断。
- **弹性调度**：例如 K8s 根据资源把容器调度到不同节点。

## 架构位置

分布式是底层思维，贯穿很多技术：

```text
分布式思想
  |
  |-- HDFS：分布式存储
  |-- Spark：分布式计算
  |-- Doris：分布式 OLAP 查询
  |-- Kafka：分布式消息队列
  |-- Redis Cluster：分布式缓存
  |-- K8s：分布式资源调度
  |-- 微服务：分布式业务系统
```

学分布式的关键，不是背 CAP，而是理解：

> 系统拆到多台机器后，原来简单的问题为什么变复杂了？

## 入门阶段

目标：能解释分布式为什么存在。

重点：

- 单机系统的瓶颈
- 横向扩展和纵向扩展
- 主从架构
- 分片
- 副本
- 负载均衡
- 故障转移

必须理解的例子：

```text
一份数据存 3 个副本
```

好处：

- 一台机器坏了，数据还在。
- 读请求可以分摊到多个节点。

代价：

- 写入要考虑多个副本同步。
- 副本之间可能短时间不一致。
- 修复故障需要复制数据。

## 进阶阶段

目标：能看懂常见分布式系统的设计取舍。

重点：

- CAP
- BASE
- 一致性
- 可用性
- 分区容错
- 强一致
- 最终一致
- 幂等
- 重试
- 超时
- 限流
- 熔断
- 降级

重点理解：

```text
网络不可靠，所以远程调用不能当成本地函数调用。
```

常见问题：

- 请求成功了，但响应超时了怎么办？
- 消息被消费两次怎么办？
- 服务 A 成功了，服务 B 失败了怎么办？
- 节点挂了，谁来接管？
- 数据副本不一致，读哪个？

- 能解释可用性和一致性的取舍。

## 重点难点

### 一致性

一致性不是一句“数据一致”这么简单。

常见层次：

- 强一致：写完后所有读都能看到最新值。
- 最终一致：短时间可能不一致，最终会同步一致。
- 读己之写：用户自己写完后，自己能读到。

架构判断：

- 钱、库存、订单状态更偏强一致。
- 日志、推荐、统计报表通常可以最终一致。

### 幂等

幂等指同一个操作执行多次，结果和执行一次一样。

例如：

```text
扣款请求重复执行两次
```

如果没有幂等，就可能扣两次钱。

分布式里因为超时、重试、消息重复，幂等非常重要。

### 数据倾斜

数据倾斜指一部分节点任务特别重，其他节点很闲。

在 Spark、数据库分片、消息队列分区里都常见。

架构判断：

```text
不是机器越多越快，数据分布不均时，加机器也可能没用。
```

## 实战项目

做一个简化版分布式任务处理系统：

```text
任务提交服务 -> 消息队列 -> 多个 Worker -> 结果存储 -> 查询接口
```

要实现：

- 任务 ID 去重
- Worker 可水平扩展
- 失败任务重试
- 任务状态查询
- 日志记录

验收标准：

- 启动多个 Worker 后，任务可以被分摊处理。
- 某个 Worker 停掉后，其他 Worker 还能继续工作。
- 同一个任务重复提交不会重复处理。
- 能查询任务成功、失败、执行中状态。

## 学习路线

```text
单机系统瓶颈
  -> 横向扩展
  -> 分片和副本
  -> CAP 和一致性
  -> 幂等、重试、超时
  -> 分布式事务
  -> 可观测性
  -> 容量规划和架构取舍
```

## 面试和工作重点

必须能讲清楚：

- 为什么需要分布式。
- 分布式带来了哪些复杂度。
- 什么是 CAP。
- 为什么重试必须配合幂等。
- 为什么服务拆分后排查更难。
- 分片和副本分别解决什么问题。
- 强一致和最终一致分别适合什么场景。

## 一句话总结

分布式的核心不是“多台机器”，而是：**在机器会坏、网络会抖、数据会延迟的前提下，仍然让系统稳定完成业务目标。**
