# 以博客项目为主的大数据与平台技术栈学习总览

## 结论

这套技术不要按“名词列表”学，也不要脱离项目空学。最合适的主线是：**把你的博客项目升级成一个带自动化部署、容器化运行、访问日志分析能力的综合项目。**

学习链路：

```text
博客业务
  -> Jenkins 做自动化
  -> Docker + K8s 管部署运行
  -> 博客访问日志进入 HDFS
  -> Scala + Spark 做日志分析
  -> Doris 做报表查询
  -> 分布式思想贯穿高可用和扩展
```

对应到系统分层：

| 层次 | 技术 | 核心作用 |
| --- | --- | --- |
| 底层思想 | 分布式 | 解释为什么多机器系统会复杂 |
| 存储层 | HDFS | 存海量大文件 |
| 开发语言 | Scala | 编写 Spark 数据处理逻辑 |
| 计算层 | Spark | 清洗、转换、聚合、Join |
| 分析层 | Doris | 快速 SQL 查询、报表和 BI |
| 自动化层 | Jenkins | 构建、测试、打包、部署 |
| 运行平台层 | K8s | 容器编排、资源调度、服务治理 |
| 综合实战 | 博客项目 | 串起业务、工程化部署和数据分析 |

主项目定位：

```text
博客项目不是练手边角料，而是所有技术的落地点。
```

## 如何利用你的博客项目

博客项目非常适合用来承载这套技术，但不要把所有组件都塞进博客核心业务。

推荐把它拆成三层：

```text
博客业务层
  -> 工程化部署层
  -> 数据分析层
```

对应关系：

| 层次 | 可以练什么 |
| --- | --- |
| 博客业务层 | 文章、分类、标签、评论、浏览量、后台管理 |
| 工程化部署层 | Jenkins、Docker、K8s、滚动发布、健康检查 |
| 数据分析层 | 访问日志、HDFS、Spark + Scala、Doris 报表查询 |

最推荐的落地项目是：

```text
博客系统 + DevOps 自动化 + 访问日志分析平台
```

## 一条完整链路

```text
业务系统产生日志
  |
  v
日志上传到 HDFS
  |
  v
Spark 读取 HDFS 数据
  |
  v
Scala 编写清洗和聚合逻辑
  |
  v
结果写入 Doris
  |
  v
BI 或报表查询 Doris
  |
  v
Jenkins 自动构建和触发任务
  |
  v
K8s 运行服务、任务或相关组件
```

放到博客项目里就是：

```text
用户访问博客
  |
  v
博客产生日志
  |
  v
HDFS 保存原始日志
  |
  v
Spark + Scala 统计 PV / UV / 热门文章
  |
  v
Doris 保存统计结果
  |
  v
博客后台展示报表
```

## 学习重点

新手最容易犯的错误是每个组件都学一点，但不知道它们为什么出现、分别站在哪一层。

你应该优先抓住这些问题：

- 什么时候单机不够，必须分布式？
- 数据为什么要放 HDFS，而不是直接放 MySQL？
- Spark 为什么适合做 ETL，而不适合做在线接口？
- Scala 在 Spark 里扮演什么角色？
- Doris 为什么适合报表查询，而不是替代 Spark？
- Jenkins 解决的是自动化问题，不是运行平台问题。
- K8s 解决的是容器编排问题，不是数据计算问题。

## 最小实战目标

做一个用户访问日志分析项目：

```text
access.log
  -> HDFS
  -> Spark + Scala
  -> Doris
  -> Jenkins 自动触发
  -> 可选：K8s 运行服务或任务
```

验收标准：

- 能解释每个组件为什么出现。
- 能把数据从 HDFS 读出来。
- 能用 Spark 处理数据。
- 能把结果写入 Doris。
- 能用 SQL 查出报表结果。
- 能用 Jenkins 自动构建或触发。
- 能理解 K8s 在部署和运行层的作用。
- 能把博客项目改造成工程化部署和访问日志分析实战项目。

## 推荐落地顺序

```text
博客主功能
  -> Jenkins 自动构建
  -> Docker 镜像化
  -> K8s 部署
  -> 访问日志
  -> HDFS 存日志
  -> Spark + Scala 分析
  -> Doris 查询
  -> 后台报表
```
