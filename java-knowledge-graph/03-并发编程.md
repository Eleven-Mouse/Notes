### 2.2 JMM — Java 内存模型

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   线程 A     │     │   线程 B     │     │   线程 C     │
│ ┌──────────┐ │     │ ┌──────────┐ │     │ ┌──────────┐ │
│ │ 工作内存  │ │     │ │ 工作内存  │ │     │ │ 工作内存  │ │
│ │(CPU缓存) │ │     │ │(CPU缓存) │ │     │ │(CPU缓存) │ │
│ └────┬─────┘ │     │ └────┬─────┘ │     │ └────┬─────┘ │
└──────┼───────┘     └──────┼───────┘     └──────┼───────┘
       │ read/write         │ read/write         │ read/write
       ▼                    ▼                    ▼
┌─────────────────────────────────────────────────────────┐
│                      主内存（Main Memory）                │
│              共享变量（堆中的实例字段 / 静态字段）           │
└─────────────────────────────────────────────────────────┘
```

**三大特性与保证手段：**

| 特性 | 含义 | 保证手段 |
|------|------|---------|
| 原子性 | 操作不可分割 | synchronized / Lock / AtomicInteger |
| 可见性 | 修改对其他线程立即可见 | volatile / synchronized / Lock |
| 有序性 | 避免指令重排序 | volatile / happens-before |

### 2.3 volatile 原理

```
写操作：
  1. 将当前缓存行数据写回主内存
  2. 使其他 CPU 缓存中该变量失效（MESI 协议）

读操作：
  1. 从主内存读取最新值

内存屏障：
  StoreStore → volatile 写 → StoreLoad
  LoadLoad → volatile 读 → LoadStore
```

**为什么 volatile 不能保证 i++ 原子性？**

```java
// i++ 实际是三步操作
volatile int i = 0;

// 线程 A 和线程 B 同时执行 i++
// 1. 读 i 的值（都是 0）        ← volatile 保证读到最新值
// 2. 计算 i+1（都是 1）         ← 但两个线程都算出 1
// 3. 写回 i（都是 1）           ← 最终 i=1，而不是 2

// 解决：用 AtomicInteger（CAS 保证原子性）
AtomicInteger i = new AtomicInteger(0);
i.incrementAndGet();  // CAS 保证原子性
```

### 2.4 AQS 核心原理

```
                    ┌──────────────────────────┐
                    │    AQS 核心数据结构        │
                    ├──────────────────────────┤
                    │  volatile int state       │ ← 同步状态
                    │  CLH 双向队列（FIFO）      │ ← 等待线程队列
                    └──────────────────────────┘

以 ReentrantLock 为例：

lock() 流程：
1. CAS 尝试将 state 从 0 改为 1
2. 成功 → 获取锁（记录当前线程为独占线程）
3. 失败 → 将当前线程包装为 Node 加入 CLH 队列尾部
4. 前驱节点释放锁时唤醒后继节点

unlock() 流程：
1. 将 state 减 1（可重入，state 可能 > 1）
2. state == 0 时释放锁
3. 唤醒 CLH 队列中下一个节点

公平锁：入队前先检查队列中是否有等待线程，有则排队
非公平锁：入队前先 CAS 抢一次，抢不到再排队（ReentrantLock 默认）
```

### 2.5 线程池 — 核心参数与执行流程

**ThreadPoolExecutor 7 大参数：**

```java
public ThreadPoolExecutor(
    int corePoolSize,        // 核心线程数（即使空闲也存活）
    int maximumPoolSize,     // 最大线程数
    long keepAliveTime,      // 非核心线程空闲存活时间
    TimeUnit unit,           // 存活时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,        // 线程工厂（自定义线程名）
    RejectedExecutionHandler handler    // 拒绝策略
)
```

**执行流程（必背）：**

```
提交任务
  │
  ▼
当前线程数 < corePoolSize？
  ├── 是 → 创建核心线程执行任务
  └── 否 → 核心线程数已满
            │
            ▼
      任务队列未满？
        ├── 是 → 任务放入队列等待
        └── 否 → 队列已满
                  │
                  ▼
            当前线程数 < maximumPoolSize？
              ├── 是 → 创建非核心线程执行任务
              └── 否 → 线程数已满
                        │
                        ▼
                  执行拒绝策略
```

**4 种拒绝策略：**

| 策略 | 行为 |
|------|------|
| AbortPolicy（默认） | 抛出 RejectedExecutionException |
| CallerRunsPolicy | 由提交任务的线程自己执行 |
| DiscardPolicy | 直接丢弃，不抛异常 |
| DiscardOldestPolicy | 丢弃队列中最老的任务，重新提交 |

**为什么不推荐 Executors？**

```
newFixedThreadPool / newSingleThreadExecutor：
  → 队列是 LinkedBlockingQueue（无界队列）
  → 任务堆积 → OOM

newCachedThreadPool：
  → 最大线程数 = Integer.MAX_VALUE
  → 大量创建线程 → OOM

正确做法：手动创建 ThreadPoolExecutor，明确指定参数
```

**线程池参数如何设定？**

```
CPU 密集型（计算为主）：corePoolSize = CPU 核心数 + 1
IO 密集型（网络/磁盘等待多）：corePoolSize = CPU 核心数 * 2（或根据 IO 等待时间计算）

公式：线程数 = CPU 核心数 * (1 + IO 等待时间 / CPU 计算时间)
```

### 2.6 ConcurrentHashMap 原理

```
JDK7：分段锁（Segment）
  ┌─────────┬─────────┬─────────┬─────────┐
  │Segment 0│Segment 1│Segment 2│  ...    │  每个 Segment 是一把锁
  │┌───┬───┐│┌───┬───┐│┌───┬───┐│         │  默认 16 个 Segment
  ││ H │   │││ H │   │││ H │   ││         │  最大并发度 = 16
  │└───┴───┘│└───┴───┘│└───┴───┘│         │
  └─────────┴─────────┴─────────┴─────────┘

JDK8：CAS + synchronized（锁粒度更细）
  数组 + 链表 / 红黑树
  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │...│   │  每个桶一把锁（锁桶的头节点）
  │   │ ↓ │   │ ↓ │   │   │   │   │
  │   │链表│   │树 │   │   │   │   │
  └───┴───┴───┴───┴───┴───┴───┴───┘

  put 流程：
  1. 计算 hash，定位桶
  2. 桶为空 → CAS 写入
  3. 桶非空 → synchronized 锁住头节点 → 遍历链表/树插入
  4. 链表长度 ≥ 8 且数组长度 ≥ 64 → 转红黑树
```

### 2.7 ThreadLocal 原理与内存泄漏

```
每个 Thread 对象内部有一个 ThreadLocalMap
ThreadLocalMap 的 key 是 ThreadLocal 的弱引用，value 是强引用

Thread → ThreadLocalMap → Entry[]
                          ┌──────────────────────────────┐
                          │ Entry(key=弱引用, value=强引用) │
                          └──────────────────────────────┘

内存泄漏原因：
1. ThreadLocal 对象被回收（key 变 null）
2. 但 value 仍然被 Entry 强引用
3. Entry 被 ThreadLocalMap 引用
4. ThreadLocalMap 被 Thread 引用
5. 如果线程不销毁（线程池）→ value 永远不回收

解决：用完必须调用 threadLocal.remove()
```

## 三、高频面试题（10 题）

### Q1：线程和进程的区别？
```
进程：操作系统资源分配的基本单位（独立内存空间）
线程：CPU 调度的基本单位（共享进程的内存）

一个进程可以有多个线程
线程切换开销远小于进程切换
线程间通信更简单（共享内存）
```

### Q2：synchronized 和 volatile 的区别？
```
volatile：仅保证可见性 + 禁止重排序，不保证原子性，轻量级
synchronized：保证原子性 + 可见性 + 有序性，重量级

volatile 适用于：状态标志、DCL 单例
synchronized 适用于：复合操作（读-改-写）
```

### Q3：什么是 CAS？有什么问题？
```
Compare And Swap：比较当前值与期望值，相同则更新为新值

问题：
1. ABA 问题 → 用 AtomicStampedReference 加版本号
2. 自旋开销（长时间 CAS 不成功会占用 CPU）→ 限制自旋次数
3. 只能保证单个变量的原子性 → 用 AtomicReference 包装对象
```

### Q4：AQS 是什么？怎么工作的？
```
AbstractQueuedSynchronizer — 并发工具的基础框架

核心：
1. volatile int state — 同步状态（0=未锁 / >0=锁次数/信号量数）
2. CLH 双向队列 — 存放等待的线程

模板方法：子类实现 tryAcquire/tryRelease（独占）或 tryAcquireShared/tryReleaseShared（共享）

基于 AQS 的工具：ReentrantLock / Semaphore / CountDownLatch / ReentrantReadWriteLock
```

### Q5：线程池的核心参数？执行流程？
```
7 大参数：corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler

执行流程：
1. 线程数 < core → 创建核心线程
2. core 满了 → 入队列
3. 队列满了 → 创建非核心线程
4. maximum 也满了 → 拒绝策略
```

### Q6：ConcurrentHashMap JDK7 和 JDK8 的区别？
```
JDK7：Segment 分段锁，并发度固定为 16
JDK8：CAS + synchronized，锁粒度为单个桶，并发度 = 数组长度

JDK8 改进：
1. 锁粒度更细（并发度更高）
2. 链表 → 红黑树（查询 O(n) → O(log n)）
3. 去掉 Segment 层，简化实现
```

### Q7：CountDownLatch 和 CyclicBarrier 的区别？
```
CountDownLatch：一次性的，一个线程等待 N 个线程完成
CyclicBarrier：可复用的，N 个线程互相等待到齐后一起继续

类比：
CountDownLatch = 等所有人都上车的乘客
CyclicBarrier = 等所有人都到齐才开始吃饭的朋友
```

### Q8：ThreadLocal 为什么要用弱引用？还会内存泄漏吗？
```
key 用弱引用的原因：ThreadLocal 对象被回收后 key 自动变 null
但仍会泄漏：key=null 但 value 还有值，ThreadLocalMap 中出现 null key 的 Entry

根本原因：线程池中线程不销毁，ThreadLocalMap 一直存在

解决：用完必须 remove()
```

### Q9：sleep 和 wait 的区别？
```
sleep：Thread 类的方法，不释放锁，到时间自动唤醒
wait：Object 类的方法，释放锁，需要 notify/notifyAll 唤醒

共同点：都可以响应中断（InterruptedException）
```

### Q10：什么是 happens-before？
```
JMM 定义的规则，保证前一个操作的结果对后一个操作可见

核心规则：
1. 程序顺序规则：同一线程中，前面的操作 happens-before 后面的操作
2. volatile 规则：volatile 写 happens-before volatile 读
3. 锁规则：unlock happens-before 后续的 lock
4. 传递性：A → B, B → C 则 A → C
5. 线程启动：start() happens-before 线程内所有操作
6. 线程终止：线程内操作 happens-before join() 返回
```

## 四、常见误区

| 误区 | 正确理解 |
|------|---------|
| volatile 能保证线程安全 | 只保证可见性，不保证原子性 |
| 线程越多性能越好 | 线程过多导致上下文切换开销增大 |
| synchronized 已经过时 | JDK6+ 大量优化（锁升级），性能已接近 Lock |
| CAS 没有锁所以没开销 | 自旋会占用 CPU |
| 线程池的核心线程不会被回收 | setAllowCoreThreadTimeOut(true) 可以回收 |
| ThreadLocal 是线程安全的 | 只是线程隔离，不是线程安全 |
