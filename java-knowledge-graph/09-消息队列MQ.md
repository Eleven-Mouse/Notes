## 二、核心知识点精讲

### 2.1 为什么需要 MQ？

```
1. 解耦
  订单系统 → 直接调用 库存/物流/积分/短信 等系统
  → 其中一个系统挂了，下单失败
  → 用 MQ：订单系统只管发消息，各系统自己消费

2. 异步
  用户注册 → 发验证邮件 → 发短信 → 发优惠券
  → 串行执行 500ms
  → 用 MQ：发消息到 MQ 立即返回（50ms），消费者异步处理

3. 削峰
  秒杀活动 → 瞬间 10 万请求打到数据库 → 数据库崩溃
  → 用 MQ：请求先入队列，消费者按数据库能力匀速消费
```

### 2.2 Kafka 架构

```
┌──────────────────────────────────────────────────────────┐
│                    Kafka Cluster                          │
│                                                          │
│  Broker 1          Broker 2          Broker 3            │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐        │
│  │Topic A   │     │Topic A   │     │Topic A   │        │
│  │P0(Leader)│     │P1(Leader)│     │P2(Leader)│        │
│  │P1(Follow)│     │P2(Follow)│     │P0(Follow)│        │
│  └──────────┘     └──────────┘     └──────────┘        │
│                                                          │
│  Producer ──→ Topic A (3 Partitions) ──→ Consumer Group  │
│                                              ┌─────────┐ │
│                                              │C0: P0   │ │
│                                              │C1: P1   │ │
│                                              │C2: P2   │ │
│                                              └─────────┘ │
└──────────────────────────────────────────────────────────┘

关键规则：
- 一个 Partition 只能被 Consumer Group 中的一个 Consumer 消费
- 一个 Consumer 可以消费多个 Partition
- Consumer 数量 > Partition 数量时，多余的 Consumer 空闲
```

### 2.3 消息可靠性保证

```
三层保证：

1. 生产者 → Broker
   acks=0：发完不管（可能丢）
   acks=1：Leader 写入即确认（Leader 挂了可能丢）
   acks=all / -1：所有 ISR 写入才确认（最安全）
   + retries=N：失败重试
   + enable.idempotence=true：幂等生产（防止重试导致重复）

2. Broker 存储
   replication.factor >= 3：至少 3 个副本
   min.insync.replicas >= 2：至少 2 个 ISR 确认
   unclean.leader.election.enable=false：禁止非 ISR 的 Follower 成为 Leader

3. Consumer 消费
   enable.auto.commit=false：关闭自动提交
   → 业务处理完成后手动 commitSync / commitAsync
   → 消费失败不提交，下次重新消费
```

### 2.4 消息顺序保证

```
Kafka 保证：分区内消息严格有序（按 Offset）

如何保证同一业务的消息进入同一分区？
  → 指定 Partition Key（如 orderId）
  → hash(orderId) % partitionCount = 固定分区

全局有序：
  → 只能设 1 个 Partition（牺牲并行度）
  → 一般不需要，业务只需保证同一实体的消息有序
```

### 2.5 重复消费与幂等

```
消息队列的语义：
  At Most Once（最多一次）：可能丢消息
  At Least Once（至少一次）：可能重复（Kafka 默认）
  Exactly Once（恰好一次）：不丢不重（需要业务配合实现）

幂等性：同一操作执行多次，结果相同

实现幂等的方式：
1. 数据库唯一约束
   INSERT IGNORE / ON DUPLICATE KEY UPDATE

2. Redis SETNX
   SETNX order_id_processed 1 EX 86400
   消费前先判断是否已处理

3. 状态机
   订单状态：待支付 → 已支付 → 已发货
   只允许单向流转，重复消费不会改变状态

4. Kafka 幂等生产者
   enable.idempotence=true
   Producer 为每条消息分配 Sequence Number
   Broker 根据 <PID, Topic, Partition, SeqNum> 去重
```

### 2.6 消息积压处理

```
紧急处理：
1. 检查消费者是否异常（挂了 / 报错循环）
2. 临时增加消费者数量（同时增加 Partition）
3. 如果不能加 Partition：
   → 创建临时 Topic（更多 Partition）
   → 用程序将积压消息转发到临时 Topic
   → 更多消费者消费临时 Topic
4. 消费完积压后恢复原架构

长期预防：
1. 监控消费者 Lag（积压量）
2. 合理设置消费者数量 = Partition 数量
3. 优化消费逻辑（批量消费 / 异步处理）
4. 扩容 Partition
```

### 2.7 Kafka vs RabbitMQ

| 维度 | Kafka | RabbitMQ |
|------|-------|----------|
| 定位 | 分布式流处理平台 | 消息代理 |
| 吞吐量 | 百万级/秒 | 万级/秒 |
| 延迟 | 毫秒级 | 微秒级 |
| 消息模型 | 发布订阅（Topic + Partition） | 路由/发布订阅/点对点 |
| 持久化 | 顺序写磁盘（高效） | 内存为主，可选持久化 |
| 消息回溯 | 支持（通过 Offset） | 不支持（消费后删除） |
| 适用场景 | 日志/大数据/流处理/高吞吐 | 业务消息/路由灵活/低延迟 |
| 社区生态 | 大数据生态（Flink/Spark） | 企业应用 |

**选型建议：**
- 日志收集 / 大数据处理 / 高吞吐 → Kafka
- 业务消息 / 路由复杂 / 延迟敏感 → RabbitMQ
- 国内大厂 Java 后端 → Kafka 居多

## 三、高频面试题（8 题）

### Q1：为什么要用 MQ？有什么缺点？
```
优点：解耦 / 异步 / 削峰
缺点：
1. 系统复杂度增加（多了一个组件要维护）
2. 消息一致性问题（消息丢失 / 重复消费）
3. 系统可用性降低（MQ 挂了整个链路受影响）
4. 消息顺序问题
5. 调试和排查问题更困难
```

### Q2：如何保证消息不丢失？
```
三个环节都要保证：

1. 生产者：acks=all + retries + 幂等
2. Broker：副本 >= 3 + min.insync.replicas >= 2
3. 消费者：手动提交 Offset，业务处理完再确认
```

### Q3：如何保证消息的顺序性？
```
Kafka 保证分区内有序

方案：将需要有序的消息发到同一分区
  → 指定 key（如 orderId）→ hash 路由到固定分区

注意：Consumer 数量不能超过 Partition 数量
```

### Q4：如何处理重复消费？
```
核心思路：幂等性

1. 数据库唯一约束
2. Redis SETNX 去重
3. 状态机（订单状态只能单向流转）
4. 全局唯一 ID + 去重表
```

### Q5：Kafka 的高可用怎么保证？
```
1. 多 Broker 集群
2. 每个 Partition 有多个副本（Leader + Follower）
3. Leader 挂了 → 从 ISR 中选举新 Leader
4. Controller 节点管理分区状态
5. unclean.leader.election.enable=false 防止数据丢失
```

### Q6：Consumer Group 是什么？
```
定义：一组消费者共同消费一个 Topic 的所有 Partition
规则：一个 Partition 只能被组内一个 Consumer 消费
Rebalance：组内消费者变化时重新分配 Partition

注意：
- Consumer 数量 = Partition 数量 → 最优
- Consumer > Partition → 多余的 Consumer 空闲
- Consumer < Partition → 部分 Consumer 消费多个 Partition
```

### Q7：消息积压了怎么办？
```
紧急：
1. 检查消费者是否正常
2. 临时增加消费者 + Partition
3. 转发到更多 Partition 的临时 Topic

预防：
1. 监控 Lag 指标
2. 合理设置消费者数量
3. 优化消费逻辑
```

### Q8：Kafka 为什么这么快？
```
1. 顺序写磁盘（比随机写内存还快）
2. 零拷贝（sendfile 系统调用，避免用户态和内核态数据拷贝）
3. PageCache（利用操作系统页缓存）
4. 分区并行（多个 Partition 并行读写）
5. 批量处理（Producer 批量发送 / Consumer 批量拉取）
6. 数据压缩（减少网络传输和磁盘占用）
```

## 四、常见误区

| 误区 | 正确理解 |
|------|---------|
| MQ 能保证消息不丢 | 需要正确配置（acks=all + 手动提交等） |
| Kafka 保证全局有序 | 只保证分区内有序 |
| 消费者越多越好 | 超过 Partition 数量会浪费 |
| MQ 解决了一切问题 | 引入了新的复杂度（一致性问题） |
| RabbitMQ 性能比 Kafka 差 | 在低延迟场景 RabbitMQ 更优 |

## 五、实战应用场景

| 场景 | MQ 方案 |
|------|--------|
| 异步发送通知 | 下单后发 MQ → 短信/邮件服务消费 |

| 秒杀削峰 | 请求先入队列，按处理能力消费 |
| 日志收集 | 应用日志 → Kafka → ELK |
