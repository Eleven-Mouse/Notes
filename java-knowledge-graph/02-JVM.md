## 二、核心知识点精讲

### 2.1 JVM 内存结构全景图

```
┌─────────────────────────────────────────────────────────┐
│                    JVM 内存结构                           │
├─────────────┬─────────────┬─────────────────────────────┤
│  线程私有    │  线程私有    │       线程共享               │
│             │             │                             │
│  程序计数器  │  VM 栈      │  ┌───────────────────────┐  │
│  (PC)       │  ┌────────┐ │  │       堆（Heap）       │  │
│             │  │ 栈帧1  │ │  │  ┌──────┬───────────┐  │  │
│  记录当前   │  │ 栈帧2  │ │  │  │新生代 │ 老年代    │  │  │
│  执行的字节 │  │ 栈帧3  │ │  │  │Eden  │           │  │  │
│  码行号     │  │  ...   │ │  │  │S0|S1 │           │  │  │
│             │  └────────┘ │  │  └──────┴───────────┘  │  │
│             │             │  └───────────────────────┘  │
│             │  本地方法栈  │  ┌───────────────────────┐  │
│             │  (Native)   │  │  方法区 / 元空间        │  │
│             │             │  │  (类信息/常量/静态变量)  │  │
│             │             │  └───────────────────────┘  │
└─────────────┴─────────────┴─────────────────────────────┘
```

**各区域常见异常：**

| 区域 | 异常类型 | 典型原因 |
|------|---------|---------|
| 堆 | OutOfMemoryError: Java heap space | 创建过多对象 / 内存泄漏 |
| 栈 | StackOverflowError | 递归调用太深 / 循环依赖 |
| 元空间 | OutOfMemoryError: Metaspace | 动态生成太多类（CGLIB） |
| 直接内存 | OutOfMemoryError: Direct buffer memory | NIO 使用不当 |

### 2.2 类加载机制 — 双亲委派

```
加载请求自底向上委派，加载结果自顶向下返回：

        Bootstrap ClassLoader（rt.jar, 核心类库）
                ↑ 委派
        Extension ClassLoader（ext 目录）
                ↑ 委派
        Application ClassLoader（classpath）
                ↑ 委派
        自定义 ClassLoader
```

**为什么要双亲委派？**

```
1. 安全性：防止用户自定义 java.lang.String 替换核心类
2. 避免重复加载：父加载器已加载的类，子加载器不需要再加载
```

**打破双亲委派的经典场景：**

| 场景 | 原因 | 怎么打破的 |
|------|------|-----------|
| SPI（JDBC） | Bootstrap 加载接口，但实现类在 classpath | 线程上下文类加载器（Thread Context ClassLoader） |
| Tomcat | 不同 WebApp 可能依赖同一库的不同版本 | 每个 WebApp 有独立 WebAppClassLoader |
| 热部署 | 需要重新加载已修改的类 | 丢弃旧 ClassLoader，创建新的 |

### 2.3 垃圾回收 — 核心流程

**对象从出生到回收的完整生命周期：**

```
1. new 对象 → 优先分配到 Eden 区
2. Eden 满 → 触发 Minor GC
3. 存活对象 → 复制到 Survivor 区（年龄 +1）
4. 年龄达到阈值（默认 15）→ 晋升到老年代
5. 大对象（超过 -XX:PretenureSizeThreshold）→ 直接进入老年代
6. 老年代满 → 触发 Full GC（STW，最慢）
```

**GC 收集器对比（重点掌握 G1）：**

| 收集器 | 目标 | 算法 | STW | 适用场景 |
|--------|------|------|-----|---------|
| Serial | 单线程 | 复制 | 长 | Client 模式 |
| ParNew | 多线程 | 复制 | 中 | 配合 CMS |
| Parallel Scavenge | 吞吐量 | 复制 | 中 | 后台计算 |
| CMS | 低延迟 | 标记-清除 | 短（并发） | 已淘汰 |
| **G1** | **平衡** | **Region 化** | **可控** | **JDK9+ 默认** |
| ZGC | 超低延迟 | 着色指针 | <10ms | JDK15+ |

**G1 核心思想：**

```
1. 将堆划分为大小相等的 Region（1~32MB）
2. 每个 Region 可以是 Eden / Survivor / Old / Humongous
3. 优先回收收益最大的 Region（Garbage First 名称来源）
4. 可预测的停顿时间（-XX:MaxGCPauseMillis）
```

### 2.4 调优实战思路

**Full GC 频繁的排查流程：**

```
1. jstat -gcutil <pid> 1000 → 观察 GC 频率和各区域使用率
2. jmap -histo <pid> → 查看对象数量排行（哪个类最多？）
3. jmap -dump:format=b,file=heap.hprof <pid> → 导出堆转储
4. 用 MAT / VisualVM 分析 heap.hprof → 找到泄漏引用链
5. 定位代码中的泄漏点（常见：static 集合未清理 / ThreadLocal 未 remove）
```

**常见 JVM 参数配置（G1 为例）：**

```bash
# 堆大小（建议 Xms = Xmx，避免动态扩容开销）
-Xms2g -Xmx2g

# 新生代大小（G1 一般不设，自动调节）
# -Xmn512m（不建议 G1 手动设）

# 选择收集器
-XX:+UseG1GC

# 最大 GC 停顿目标
-XX:MaxGCPauseMillis=200

# GC 日志
-Xlog:gc*:file=gc.log

# 元空间大小
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=256m

# OOM 时自动 dump
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/heap.hprof
```

## 三、高频面试题（12 题）

### Q1：JVM 的内存结构是怎样的？
```
线程私有：程序计数器、虚拟机栈、本地方法栈
线程共享：堆、方法区（元空间）

堆：对象实例（GC 主要区域），分新生代和老年代
栈：方法调用的栈帧（局部变量表、操作数栈、动态链接）
方法区：类信息、常量、静态变量（JDK8 后为元空间，使用本地内存）
程序计数器：记录当前执行的字节码行号
```

### Q2：堆和栈的区别？
```
堆：线程共享，存对象实例，需要 GC 管理，空间大
栈：线程私有，存局部变量和方法调用信息，自动分配释放，空间小

栈溢出：StackOverflowError（递归太深）
堆溢出：OutOfMemoryError（对象太多 / 内存泄漏）
```

### Q3：什么是双亲委派模型？为什么要有？
```
定义：类加载请求先委派给父加载器，父加载器无法加载时才自己加载
目的：
1. 防止核心类被篡改（安全）
2. 避免重复加载（效率）

打破场景：SPI / Tomcat / 热部署
```

### Q4：JVM 有哪些垃圾收集器？G1 和 CMS 的区别？
```
CMS：标记-清除，并发收集，低延迟，但有碎片问题，JDK14 已移除
G1：Region 化，标记-整理为主，可预测停顿时间，JDK9 默认

G1 优势：
1. 没有 CMS 的碎片问题
2. 停顿时间可预测
3. 大堆表现更好（6GB+）
```

### Q5：什么情况下对象会进入老年代？
```
1. 年龄达到阈值（默认 15，-XX:MaxTenuringThreshold）
2. 大对象直接分配（-XX:PretenureSizeThreshold）
3. 动态年龄判断：Survivor 区中同龄对象总和超过空间一半
4. Survivor 空间不足时，担保机制直接进老年代
```

### Q6：什么是 GC Roots？哪些对象可以作为 GC Roots？
```
定义：可达性分析的起点对象
包括：
1. 虚拟机栈中的引用（正在执行的方法中的局部变量）
2. 方法区中静态属性引用
3. 方法区中常量引用
4. 本地方法栈中 JNI 引用
5. JVM 内部引用（基本类型对应的 Class 对象等）
```

### Q7：Java 中的四种引用类型？
```
强引用（Strong）：Object obj = new Object() — 永不回收
软引用（SoftReference）：内存不足时回收 — 适合缓存
弱引用（WeakReference）：下次 GC 一定回收 — 适合 ThreadLocal
虚引用（PhantomReference）：随时回收，仅用于跟踪 GC — 管理堆外内存
```

### Q8：什么是内存泄漏？如何排查？
```
定义：对象不再使用但仍被 GC Roots 引用，无法被回收

排查步骤：
1. jstat 观察 Old 区持续增长
2. jmap -histo 看对象排行
3. jmap -dump 导出堆转储
4. MAT 分析找到 GC Roots 到泄漏对象的最短路径
5. 定位代码中持有引用的位置

常见原因：
- static 集合不断 add 不 remove
- ThreadLocal 用完不 remove
- 未关闭的连接 / 流
- 监听器 / 回调未注销
```

### Q9：JDK8 的方法区为什么从永久代改为元空间？
```
永久代问题：
1. 大小固定（-XX:MaxPermSize），容易 OOM
2. 字符串常量池容易溢出
3. GC 和堆耦合，难以优化

元空间优势：
1. 使用本地内存，不受堆大小限制
2. 自动扩容（受限于物理内存）
3. 类元数据的管理更灵活
```

### Q10：什么是 STW（Stop-The-World）？为什么 CMS / G1 要减少 STW？
```
定义：GC 时暂停所有用户线程

影响：用户感知为服务卡顿、超时

CMS 的策略：大部分标记阶段并发执行，只有初始标记和重新标记 STW
G1 的策略：通过 Region 化，只回收部分 Region，控制 STW 时间
ZGC：通过着色指针和读屏障，实现几乎无 STW（<10ms）
```

### Q11：JVM 调优的常见目标是什么？
```
1. 降低 GC 停顿时间（减少 STW 对用户的影响）
2. 降低 Full GC 频率（避免长时间停顿）
3. 提高吞吐量（减少 GC 占用的 CPU 时间）
4. 解决内存泄漏 / OOM 问题

常见调优手段：
- 增大堆空间
- 选择合适的收集器
- 调整新生代/老年代比例
- 调整晋升阈值
```

### Q12：说一下对象创建的过程？
```
1. 类加载检查（是否已加载该类）
2. 分配内存（指针碰撞 or 空闲列表）
3. 内存初始化零值（不赋初始值）
4. 设置对象头（Mark Word + 类型指针）
5. 执行 <init> 方法（构造函数）

线程安全：CAS + 失败重试 保证分配内存的线程安全
```

## 四、常见误区

| 误区 | 正确理解 |
|------|---------|
| 方法区就是永久代 | JDK8 后没有永久代，改为元空间（本地内存） |
| GC 会回收所有垃圾 | 只有 GC Roots 不可达的对象才会被回收 |
| 强引用一定会内存泄漏 | 不再使用但被引用的才会泄漏 |
| G1 不会 Full GC | G1 在回收速度跟不上分配速度时仍会 Full GC（退化 Serial Old） |
| 栈溢出是因为内存不够 | 栈溢出是调用深度太深（递归），不是内存总量不够 |
| CMS 没有碎片问题 | CMS 用标记-清除，碎片是最大问题（G1 用标记-整理解决） |
