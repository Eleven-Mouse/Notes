## 二、核心知识点精讲

### 2.1 锁分类全景

| 分类维度 | 类型 A | 类型 B | 区别 |
|---------|--------|--------|------|
| 悲观/乐观 | 悲观锁（synchronized） | 乐观锁（CAS） | 假设冲突是否频繁 |
| 公平性 | 公平锁（排队） | 非公平锁（可插队） | 是否按请求顺序获取 |
| 重入性 | 可重入（ReentrantLock） | 不可重入 | 同一线程是否可重复获取 |
| 排他性 | 独占锁（写锁） | 共享锁（读锁） | 是否允许多线程同时持有 |
| 等待方式 | 自旋锁（CPU空转等待） | 阻塞锁（线程挂起） | 等待时不释放 CPU |

### 2.2 synchronized 锁升级（核心中的核心）

**对象头 Mark Word 结构：**

```
┌──────────────────────────────────────────────────────┐
│                  Mark Word（64 bit）                   │
├──────────┬──────────────────────┬─────────────────────┤
│   状态    │     存储内容         │    标志位            │
├──────────┼──────────────────────┼─────────────────────┤
│  无锁     │ hashCode + 分代年龄  │    001              │
│  偏向锁   │ 线程ID + 分代年龄    │    101              │
│  轻量级锁 │ 指向栈中锁记录的指针  │    00               │
│  重量级锁 │ 指向 Monitor 的指针   │    10               │
│  GC 标记  │ 空                   │    11               │
└──────────┴──────────────────────┴─────────────────────┘
```

**锁升级完整流程：**

```
阶段 1：无锁
  │  第一次有线程访问同步块
  ▼
阶段 2：偏向锁
  │  通过 CAS 将线程 ID 写入 Mark Word
  │  同一线程再次进入：只比较线程 ID，无需 CAS（极快）
  │  有第二个线程来竞争
  ▼
阶段 3：轻量级锁（Thin Lock）
  │  撤销偏向锁，在当前线程栈帧中创建 Lock Record
  │  CAS 将 Mark Word 替换为指向 Lock Record 的指针
  │  成功 → 获取锁 / 失败 → 自旋等待
  │  自旋超过阈值（自适应自旋）
  ▼
阶段 4：重量级锁（Heavyweight Lock）
  │  将线程封装为 ObjectWaiter 挂到 Monitor 的 EntryList
  │  线程阻塞（调用操作系统 futex）
  │  等待被唤醒
  ▼
  锁释放 → 唤醒等待线程

注意：锁升级是单向的（不会降级），但偏向锁可以被批量撤销
```

**各级锁的对比：**

| 锁类型 | 适用场景 | 获取锁方式 | 性能 |
|--------|---------|-----------|------|
| 偏向锁 | 只有一个线程访问 | CAS 写线程 ID | 最高 |
| 轻量级锁 | 交替执行/短时间竞争 | CAS + 自旋 | 高 |
| 重量级锁 | 长时间竞争 | 操作系统互斥 | 最低 |

### 2.3 乐观锁 vs 悲观锁

```
悲观锁（Pessimistic Lock）：
  思想：假设一定会冲突，先加锁再操作
  实现：synchronized / ReentrantLock / SELECT ... FOR UPDATE
  场景：写多读少 / 竞争激烈

乐观锁（Optimistic Lock）：
  思想：假设不会冲突，先操作再检查
  实现：CAS / 版本号
  场景：读多写少 / 竞争不激烈
```

**乐观锁实战 — 数据库版本号：**

```sql
-- 表中增加 version 字段
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;

-- 影响行数 = 0 → 说明被其他事务修改了，需要重试
```

### 2.4 ReentrantLock vs synchronized

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 实现 | JVM 层面（monitorenter） | API 层面（AQS） |
| 锁释放 | 自动（作用域结束） | 手动（finally 中 unlock） |
| 可中断 | 不可 | lockInterruptibly() |
| 超时获取 | 不支持 | tryLock(timeout) |
| 公平锁 | 只有非公平 | 可选公平/非公平 |
| 条件变量 | wait/notify（一个） | Condition（多个） |
| 性能 | JDK6+ 优化后差距不大 | 高竞争时略优 |

**ReentrantLock 使用模板：**

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // 业务逻辑
} finally {
    lock.unlock();  // 必须在 finally 中释放
}
```

### 2.5 分布式锁

**Redis 分布式锁（最常用）：**

```java
// 加锁（保证原子性）
String result = jedis.set("lock:order:123", "unique_id", "NX", "EX", 30);

// 解锁（Lua 脚本保证原子性）
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                "  return redis.call('del', KEYS[1]) " +
                "else return 0 end";
jedis.eval(script, Collections.singletonList("lock:order:123"),
           Collections.singletonList("unique_id"));
```

**Redisson 看门狗机制：**

```
1. 默认锁过期时间 30 秒
2. 每 10 秒（1/3 过期时间）检查锁是否还被持有
3. 如果持有 → 自动续期到 30 秒
4. 客户端宕机 → 不续期 → 30 秒后自动释放

好处：避免业务没执行完锁就过期的问题
```

**三种分布式锁对比：**

| 维度 | Redis | ZooKeeper | MySQL |
|------|-------|-----------|-------|
| 性能 | 最高（内存） | 中等 | 最低（磁盘） |
| 可靠性 | 中等（主从切换可能丢锁） | 最高（ZAB 一致性） | 高 |
| 实现 | SETNX + 过期 | 临时顺序节点 | FOR UPDATE / 唯一索引 |
| 自动续期 | Redisson 看门狗 | 临时节点 + Session | 无 |
| 适用场景 | 高性能场景 | 强一致性场景 | 简单场景 |

## 三、原理图（文字描述）

### synchronized 锁升级原理图

```
   Thread A 第一次进入同步块
         │
         ▼ CAS 成功
   ┌─────────────┐
   │   偏向锁     │ Mark Word 存 Thread A 的线程 ID
   │  (Thread A)  │ Thread A 再次进入：直接比较线程 ID，无需 CAS
   └──────┬──────┘
          │ Thread B 尝试获取
          ▼ CAS 竞争
   ┌─────────────┐
   │  轻量级锁    │ Mark Word 指向栈中 Lock Record
   │  (自旋)     │ Thread B 自旋等待（不阻塞，消耗 CPU）
   └──────┬──────┘
          │ 自旋超过阈值
          ▼
   ┌─────────────┐
   │  重量级锁    │ Mark Word 指向 Monitor 对象
   │  (阻塞)     │ Thread B 被挂起（OS 层面，线程上下文切换）
   └─────────────┘
```

## 四、高频面试题（10 题）

### Q1：synchronized 的锁升级过程？
```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁

偏向锁：只有一个线程访问，Mark Word 存线程 ID，比较即可
轻量级锁：两个线程交替访问，CAS + 自旋
重量级锁：竞争激烈，线程阻塞等待 Monitor

锁升级是单向的，不可降级（JVM 优化策略）
```

### Q2：偏向锁什么时候会撤销？
```
1. 第二个线程尝试获取偏向锁时（需要等到全局安全点 STW）
2. 调用对象的 hashCode()（偏向锁不能存 hashCode）
3. 批量重偏向 / 批量撤销（类的撤销计数达到阈值）
```

### Q3：乐观锁和悲观锁的区别？
```
悲观锁：先加锁再操作（synchronized / SELECT FOR UPDATE）
乐观锁：先操作再验证（CAS / 版本号）

选择依据：
竞争少 → 乐观锁（减少加锁开销）
竞争多 → 悲观锁（减少重试开销）
```

### Q4：什么是可重入锁？怎么实现的？
```
定义：同一线程可以重复获取同一把锁而不会死锁

synchronized 实现：Monitor 的 _count 计数器（每次 +1）
ReentrantLock 实现：AQS 的 state 字段（每次 +1）

释放条件：计数归零才真正释放锁
```

### Q5：公平锁和非公平锁的区别？
```
公平锁：线程按排队顺序获取锁（FIFO）
非公平锁：新线程可以插队（先 CAS 抢一次，抢不到再排队）

非公平锁性能更好：减少线程切换开销
非公平锁可能导致饥饿：某些线程长时间获取不到锁

ReentrantLock 默认非公平，构造参数传 true 变公平
synchronized 只有非公平
```

### Q6：什么是自旋锁？自适应自旋？
```
自旋锁：获取锁失败时不阻塞，而是循环重试（CPU 空转）
自适应自旋：JVM 根据上次自旋是否成功动态调整自旋次数

优点：避免线程阻塞/唤醒的上下文切换开销（短时间等待更高效）
缺点：长时间自旋浪费 CPU
```

### Q7：Redis 分布式锁怎么实现？有什么问题？
```
实现：SET key value NX EX 30（加锁+过期时间原子操作）

问题：
1. 锁过期但业务未完成 → Redisson 看门狗续期
2. 主从切换丢锁 → RedLock（多个独立 Redis 实例）
3. 不可重入 → Redisson 的 hash 结构支持重入

解锁必须用 Lua 脚本（保证判断+删除的原子性）
```

### Q8：读写锁的应用场景？
```
ReentrantReadWriteLock：读读不互斥，读写互斥

适用场景：读多写少（如缓存、配置数据）

写锁可降级为读锁（获取写锁 → 获取读锁 → 释放写锁）
读锁不可升级为写锁（会死锁）
```

### Q9：synchronized 和 ReentrantLock 怎么选？
```
默认用 synchronized：简单、自动释放、JVM 持续优化
需要以下特性时用 ReentrantLock：
1. 可中断获取锁
2. 超时获取锁
3. 公平锁
4. 多条件变量（Condition）
5. 尝试获取锁（tryLock）
```

### Q10：什么是死锁？怎么排查和预防？
```
死锁条件（四个同时满足）：
1. 互斥：资源只能被一个线程持有
2. 持有并等待：持有锁的同时等待其他锁
3. 不可抢占：锁不能被强制释放
4. 循环等待：A等B，B等A

排查：
jstack <pid> → 查看线程栈中的 "Found one Java-level deadlock"
或 Arthas 的 thread -b 命令

预防：
1. 固定加锁顺序（所有线程按相同顺序获取锁）
2. 使用 tryLock(timeout) 超时放弃
3. 减小锁粒度
```

## 五、常见误区

| 误区 | 正确理解 |
|------|---------|
| synchronized 很慢 | JDK6+ 锁升级后，无竞争时和 CAS 一样快 |
| 锁可以降级 | 锁升级单向不可逆（偏向锁被撤销不算降级） |
| 轻量级锁比重量级锁快 | 竞争激烈时自旋消耗 CPU 反而更慢 |
| 分布式锁一定要用 ZooKeeper | Redis 更常用，性能更好 |
| synchronized 不能被中断 | 底层确实不行，所以才需要 ReentrantLock |

## 六、实战应用场景

| 场景 | 锁方案 |
|------|--------|
| 单机高并发计数 | AtomicInteger（CAS 乐观锁） |
| 单机互斥访问 | synchronized / ReentrantLock |
| 防止重复下单 | Redis 分布式锁（Redisson） |
| 库存扣减 | 数据库乐观锁（版本号）或 Redis + Lua |
| 配置热更新读 | ReentrantReadWriteLock（读多写少） |
| 转账操作 | 数据库悲观锁（SELECT FOR UPDATE） |
