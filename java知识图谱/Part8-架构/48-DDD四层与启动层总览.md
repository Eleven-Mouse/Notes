> 面试定位：回答 DDD 不要只背“贫血/充血”，要能落到分层职责与工程目录。

---

## 一、你要先讲出的结论

1. DDD 重点是“业务复杂度治理”，不是为了追求层数而分层。
2. 常见落地为四层：`application`、`domain`、`adapter`、`infrastructure`，再加 `start` 启动层。
3. 分层目标是依赖方向稳定：外层依赖内层，内层不感知外层技术细节。

---

## 二、分层职责图

```text
start（启动装配）
  -> application（用例编排）
    -> domain（领域规则）
      <- adapter（入站/出站适配）
      <- infrastructure（技术实现）
```

---

## 三、各层一句话定位

1. `application`：讲“做什么流程”，不写核心业务规则。
2. `domain`：讲“业务为什么这么做”，沉淀实体、值对象、领域服务。
3. `adapter`：把外部协议转换成领域可理解的输入输出。
4. `infrastructure`：提供数据库、MQ、RPC、缓存等技术能力实现。
5. `start`：启动配置、依赖注入、模块装配、环境加载。

---

## 四、面试高频陷阱

1. 把 SQL 和远程调用写进 Domain，导致领域层被技术污染。
2. Application 层堆满 if-else 业务规则，退化为事务脚本。
3. Adapter 直接操作数据库，绕开领域模型。
4. Start 层掺杂业务逻辑，启动与运行职责混乱。

---

## 五、面试追问速答

### Q1：DDD 和三层架构冲突吗？

- 不冲突。DDD 是业务建模方法，三层是技术分层方式，可叠加使用。

### Q2：小项目需要 DDD 吗？

- 简单 CRUD 不建议重度 DDD；复杂业务演进快的系统值得投入。

### Q3：如何判断 DDD 是否落地成功？

- 新需求修改集中在 application/domain，技术替换不冲击核心业务规则。
