
> **一句话总结**: 类从 .class 文件到 JVM 中使用，经历加载→验证→准备→解析→初始化五个阶段，双亲委派模型保证安全但可被打破，面试必问"加载过程 + 为什么要双亲委派 + 如何打破"。

## 二、核心知识点

### 1. 类加载的 5 个阶段

#### 1.1 加载（Loading）

**做了什么**:
1. 通过类的全限定名获取二进制字节流（来源不限于 class 文件，可以是 jar/war/网络/动态代理生成）
2. 将字节流转化为方法区的运行时数据结构
3. 在堆中生成该类的 `java.lang.Class` 对象，作为方法区数据的访问入口

> **注意**: 加载阶段是开发者可控性最强的阶段，可以自定义类加载器。

#### 1.2 验证（Verification）

**目的**: 确保 Class 文件的字节流符合 JVM 规范，不会危害虚拟机安全。

**四个验证环节**:
| 环节 | 验证内容 |
|------|----------|
| 文件格式验证 | 魔数 0xCAFEBABE、版本号、常量池索引 |
| 元数据验证 | 语义分析：是否有父类、是否继承了 final 类、接口实现是否完整 |
| 字节码验证 | 数据流分析：保证跳转指令不会跳到方法体外 |
| 符号引用验证 | 引用的类/方法/字段是否存在、是否可访问 |

#### 1.3 准备（Preparation）

**做了什么**: 为类变量（static）分配内存并设置**零值初始值**。

**关键区分**:
```java
// 准备阶段：value = 0（零值）
// 初始化阶段：value = 123（实际值）
private static int value = 123;

// 准备阶段：CONSTANT = 123（编译期常量，准备阶段就赋值）
private static final int CONSTANT = 123;
```

> 面试陷阱: `static final` 修饰的编译期常量在准备阶段就赋值，普通 static 变量在初始化阶段赋值。

#### 1.4 解析（Resolution）

**做了什么**: 将常量池中的符号引用替换为直接引用（内存地址）。

| 符号引用 | 直接引用 |
|----------|----------|
| 字符串形式的类名/方法名/字段名 | 内存中的直接指针/句柄/偏移量 |

**解析时机**: 可在初始化前（饿汉式），也可在使用时（懒解析）。

#### 1.5 初始化（Initialization）

**做了什么**: 执行类的 `<clinit>()` 方法——即所有 static 变量赋值和 static 代码块的合并。

**关键点**:
- `<clinit>()` 由编译器自动收集类中所有 static 赋值和 static 块合并产生
- 执行顺序严格按照源码中出现的顺序
- JVM 保证 `<clinit>()` 在多线程环境下被正确地加锁和同步
- 如果类没有 static 赋值和 static 块，就不会生成 `<clinit>()`

### 2. 双亲委派模型

**三个类加载器层次**:

```
Bootstrap ClassLoader（启动类加载器）
    ↑ 委派
Extension ClassLoader（扩展类加载器，JDK 9+ 改名 PlatformClassLoader）
    ↑ 委派
Application ClassLoader（应用类加载器 / 系统类加载器）
    ↑ 委派
自定义 ClassLoader
```

| 加载器 | 加载路径 | 实现语言 |
|--------|----------|----------|
| Bootstrap | `JAVA_HOME/lib`（rt.jar 等） | C++ 实现，不是 Java 类 |
| Extension | `JAVA_HOME/lib/ext` | Java 实现（`sun.misc.Launcher$ExtClassLoader`） |
| Application | classpath（用户类路径） | Java 实现（`sun.misc.Launcher$AppClassLoader`） |

**双亲委派流程**:
1. 收到类加载请求，先委派给父加载器
2. 父加载器无法加载（在自己的范围内找不到），子加载器才自己加载

**为什么要双亲委派?**
1. **安全性**: 防止用户自定义的 `java.lang.Object` 替换核心类（父加载器先加载了真的 Object）
2. **避免重复加载**: 父加载器已加载的类，子加载器不需要再加载

---

### 3. 打破双亲委派的场景

#### 3.1 SPI 机制（线程上下文类加载器）

**问题**: `java.sql.Driver` 接口在 rt.jar 中（Bootstrap 加载），但具体实现在各厂商 jar 中（classpath 中，Bootstrap 无法加载）。

**解决方案**: 使用线程上下文类加载器（Thread Context ClassLoader），默认是 AppClassLoader。

```java
// ServiceLoader 使用 TCCL 加载实现类
ServiceLoader<Driver> drivers = ServiceLoader.load(Driver.class);
```

#### 3.2 Tomcat

**打破原因**: 一个 Tomcat 部署多个 Web 应用，每个应用依赖同一库的不同版本，需要隔离。

**Tomcat 类加载策略**:
- 每个 WebApp 有一个独立的 `WebAppClassLoader`
- WebApp 优先自己加载，委派给 Bootstrap 后如果找不到就不委派给 AppClassLoader
- 共享库通过 `SharedClassLoader` 加载

#### 3.3 OSGi

- 每个模块（Bundle）有自己的 ClassLoader
- 模块间可以声明依赖关系，形成网状加载结构而非树状

#### 3.4 热部署

- 修改类后创建新的 ClassLoader 重新加载，旧 ClassLoader 和旧类一起被 GC 回收
- 实现：自定义 ClassLoader，重写 `findClass` 而非 `loadClass`（如果重写 loadClass 则完全打破双亲委派）

---

### 4. 类加载时机

#### 4.1 主动引用（触发初始化的 6 种情况）

1. `new` / `getstatic` / `putstatic` / `invokestatic` — 实例化、读写静态字段、调用静态方法
2. `java.lang.reflect` 包的方法对类进行反射调用
3. 初始化一个类时，其父类还未初始化，先触发父类初始化
4. JVM 启动时，用户指定的主类（包含 main 方法的类）
5. `MethodHandle`/`VarHandle` 解析时对应的类
6. 接口中定义了 default 方法，实现类初始化时先触发接口初始化

#### 4.2 被动引用（不会触发初始化）

1. 通过子类引用父类的静态字段 → 只触发父类初始化
2. 通过数组定义引用类 `new A[10]` → 不会触发 A 的初始化
3. 常量（`static final` 编译期常量）在准备阶段已赋值 → 引用常量不会触发初始化

---

### 5. 类卸载条件（了解即可）

同时满足以下三个条件：
1. 该类所有实例都已被回收
2. 加载该类的 ClassLoader 已被回收
3. 该类对应的 `java.lang.Class` 对象没有在任何地方被引用

> Bootstrap ClassLoader 永远不会被回收，所以核心类（如 rt.jar 中的）永远不会被卸载。

## 三、面试题

### Q1: 描述一下类加载的过程？

**答**: 分为五个阶段——加载（读取 class 文件到方法区，生成 Class 对象）→ 验证（确保格式和安全）→ 准备（static 变量赋零值）→ 解析（符号引用变直接引用）→ 初始化（执行 `<clinit>`，执行 static 赋值和 static 块）。

### Q2: 什么是双亲委派模型？为什么要用？

**答**: 类加载器收到加载请求后先委派给父加载器处理，父加载器无法加载时子加载器才自己加载。好处是：(1) 安全性——防止用户伪造核心类（如自定义 java.lang.Object）；(2) 避免重复加载——同一个类只加载一次。

### Q3: 有哪些打破双亲委派的场景？

**答**: (1) SPI 机制——JDBC 接口在 Bootstrap 加载，实现在 classpath，用线程上下文类加载器解决；(2) Tomcat——每个 WebApp 独立 ClassLoader 实现类隔离；(3) OSGi——模块化网状加载结构；(4) 热部署——重新创建 ClassLoader 加载修改后的类。

### Q4: 准备阶段和初始化阶段对 static 变量的处理有什么区别？

**答**: 准备阶段为 static 变量分配内存并赋零值（如 int → 0）；初始化阶段才执行真正的赋值动作。例外是 `static final` 修饰的编译期常量，在准备阶段就直接赋最终值。

### Q5: 什么情况下类会被初始化？什么情况下不会？

**答**: 主动引用会触发初始化：new 对象、读写非编译期 static 字段、调用 static 方法、反射调用、初始化子类先初始化父类、main 方法所在类。被动引用不会触发：通过子类引用父类 static 字段（只初始化父类）、数组引用类、引用编译期常量。

### Q6: 如何自定义类加载器？需要注意什么？

**答**: 继承 `ClassLoader`，重写 `findClass` 方法（推荐），在里面读取 class 文件字节流，调用 `defineClass` 转为 Class 对象。推荐重写 `findClass` 而非 `loadClass`，这样不会破坏双亲委派。如果需要打破双亲委派，才重写 `loadClass`。

### Q7: Tomcat 是如何实现应用隔离的？

**答**: Tomcat 为每个 Web 应用创建独立的 `WebAppClassLoader`。加载类时，先委派给 Bootstrap 加载核心类，如果 Bootstrap 找不到，WebAppClassLoader 自己加载（跳过了 Extension 和 AppClassLoader），实现不同应用间的类隔离。公共库通过 `SharedClassLoader` 在应用间共享。

### Q8: JVM 如何保证 `<clinit>` 方法的线程安全？

**答**: JVM 规范要求 `<clinit>()` 方法在多线程环境下必须被正确加锁和同步。如果一个线程正在执行类的 `<clinit>()`，其他线程必须阻塞等待。利用这一点可以实现单例模式的线程安全初始化（静态内部类实现单例）。

## 四、常见误区

| 误区 | 正确理解 |
|------|----------|
| 类加载就是加载阶段 | 类加载包含全部五个阶段，加载只是第一步 |
| 准备阶段赋实际值 | 准备阶段赋零值，初始化阶段才赋实际值 |
| 双亲是"父类"关系 | 是"父加载器"的委派关系，不是类的继承关系 |
| 自定义 ClassLoader 一定打破双亲委派 | 重写 `findClass` 不打破，重写 `loadClass` 才打破 |
| 类用完就会被卸载 | 类卸载条件很苛刻，实际中很少发生 |

## 五、实战场景

1. **ClassNotFoundException**: 类路径不对，检查 classpath 配置
2. **NoClassDefFoundError**: 编译时有但运行时找不到（可能是依赖冲突）
3. **ClassCastException**: 不同 ClassLoader 加载的同一个类被视为不同类
4. **热部署**: 用自定义 ClassLoader + 新实例替换，旧实例等待 GC 回收
