## 二、核心知识点精讲

  

### 2.1 服务注册与发现

  

```

工作流程：

  

1. 服务启动 → 向注册中心注册自己的地址（IP:Port）

2. 注册中心 → 维护服务列表（心跳检测存活）

3. 消费者 → 从注册中心获取服务列表

4. 消费者 → 通过负载均衡选择一个实例调用

5. 服务下线 → 注册中心剔除 → 通知消费者更新列表

  

Nacos 核心概念：

  命名空间（Namespace）→ 环境隔离（dev/test/prod）

  分组（Group）→ 业务隔离

  服务（Service）→ 一个微服务

  实例（Instance）→ 服务的一个运行节点

  集群（Cluster）→ 同机房/同区域的实例

  

CP vs AP：

  CP（ZooKeeper）：保证一致性，Leader 选举期间不可用

  AP（Eureka）：保证可用性，各节点数据可能短暂不一致

  Nacos：临时实例用 AP，持久实例用 CP

```

  

### 2.2 网关

  

```

请求流程：

  

客户端 → Gateway → 路由匹配 → 过滤器链 → 目标服务

  

Gateway 核心功能：

1. 路由（Route）：定义请求转发规则（Path / Host / Method）

2. 过滤器（Filter）：

   - 前置：鉴权 / 限流 / 日志 / 请求头修改

   - 后置：响应头修改 / 日志 / 统计

3. 负载均衡：集成 LoadBalancer

4. 熔断：集成 Sentinel / Resilience4J

  

为什么需要网关？

1. 统一入口（客户端不需要知道每个服务的地址）

2. 统一鉴权（不用每个服务都做鉴权）

3. 统一限流

4. 协议转换（HTTP → RPC）

```

  

### 2.3 限流算法

  

```

1. 固定窗口计数器

   ────|────|────|────

   0    10   20   30（秒）

   每个窗口内限 100 次

   问题：窗口边界可能 2 倍流量（10~11 秒可能 200 次）

  

2. 滑动窗口计数器

   更细粒度的固定窗口，解决边界问题

   Sentinel 默认使用

  

3. 令牌桶（Token Bucket）

   以固定速率生成令牌放入桶中

   请求需获取令牌才能通过

   允许突发流量（桶中有积攒的令牌）

   Google Guava RateLimiter 使用

  

4. 漏桶（Leaky Bucket）

   请求进入桶中，以固定速率流出

   不管流量多大，处理速率恒定

   适合平滑流量

  

选择：

  允许突发 → 令牌桶

  严格匀速 → 漏桶

  简单场景 → 滑动窗口

```

  

### 2.4 CAP 与 BASE

  

```

CAP 定理：

  C（Consistency）一致性：所有节点读到相同数据

  A（Availability）可用性：每个请求都能得到响应

  P（Partition tolerance）分区容错：网络分区时系统仍能工作

  

结论：网络分区不可避免 → 只能在 C 和 A 中二选一

  CP：ZooKeeper / Etcd（保证一致性，牺牲可用性）

  AP：Eureka / Nacos（临时实例）（保证可用性，牺牲一致性）

  

BASE 理论（对 CAP 中 AP 的延伸）：

  BA（Basically Available）基本可用：允许响应时间增加或功能降级

  S（Soft State）软状态：允许中间状态

  E（Eventual Consistency）最终一致性：一段时间后达到一致

```

  

### 2.5 分布式 ID — 雪花算法

  

```

Snowflake（64 bit）：

  

  0 | 00000000 00000000 00000000 00000000 00000000 0 | 00000 | 00000 | 000000000000

  │  │                    41 bit 时间戳                │ 5位   │ 5位   │ 12位序列号

  │  │               （可用约 69 年）                   │数据中心│机器ID │（每毫秒4096个）

  符号位                                              │       │       │

                                                      └───────┴───────┘

                                                          10 bit 机器ID

                                                          （1024 台机器）

  

优点：有序 / 无依赖 / 高性能

缺点：依赖时钟（时钟回拨会出问题）

解决时钟回拨：使用历史最大时间戳判断 / 等待追上

```

  

### 2.6 分布式事务

  

```

场景：订单服务扣库存 + 扣余额 → 必须同时成功或同时失败

  

方案对比：

  

1. 2PC（两阶段提交）

   协调者 → 询问所有参与者 → 全部 Yes → 提交

   问题：同步阻塞 / 协调者单点 / 脑裂

  

2. TCC（Try-Confirm-Cancel）

   Try：预留资源（冻结库存）

   Confirm：确认操作（扣减冻结的库存）

   Cancel：取消操作（释放冻结的库存）

   适合：资金 / 库存等一致性要求高的场景

  

3. 消息最终一致性

   发送半消息 → 本地事务提交 → 提交消息 → 消费者消费

   适合：对实时性要求不高，允许延迟一致

  

4. Seata（阿里开源）

   AT 模式（默认）：自动补偿（只需要加 @GlobalTransactional）

   TCC 模式：手动写 Try/Confirm/Cancel

   Saga 模式：长事务编排

  

推荐：大部分场景用 AT 模式或消息最终一致性

```

## 三、高频面试题（8 题）

  

### Q1：单体和微服务的区别？什么时候拆？

```

单体：所有功能在一个项目中，部署简单，但随代码量增加维护困难

微服务：按业务拆分，独立部署/开发/扩展，但增加运维复杂度

  

拆分时机：

- 团队 > 10 人

- 代码量 > 10 万行

- 部署频率高，互相影响

- 部分模块需要独立扩容

  

不要过早拆分（YAGNI 原则）

```

  

### Q2：CAP 定理是什么？

```

一致性 / 可用性 / 分区容错 三者不可兼得

  

网络分区不可避免 → 在 C 和 A 中选：

  CP：ZooKeeper（强一致，选举期间不可用）

  AP：Eureka / Nacos（高可用，短暂不一致）

  

BASE 是 AP 的实践：基本可用 + 软状态 + 最终一致

```

  

### Q3：服务注册中心怎么选？

```

Nacos（推荐）：AP/CP 可切换，功能全（注册 + 配置），Spring Cloud Alibaba 组件

Eureka：AP，已停更，不推荐新项目

ZooKeeper：CP，偏重，适合强一致场景（如 Kafka / Dubbo）

Consul：CP，Go 写的，跨语言支持好

```

  

### Q4：分布式锁有哪些实现？

```

Redis：SETNX + 过期时间，性能高，但有主从切换丢锁风险

  → Redisson + 看门狗

ZooKeeper：临时顺序节点，可靠性高，性能较低

MySQL：FOR UPDATE / 唯一索引，简单但性能差

  

推荐：Redis 分布式锁（Redisson）

```

  

### Q5：如何保证接口的幂等性？

```

1. 数据库唯一约束

2. Redis SETNX 去重

3. 状态机（订单状态单向流转）

4. Token 机制（获取 token → 提交时校验并删除）

5. MVCC 版本号

```

  

### Q6：分布式事务怎么处理？

```

强一致：2PC / Seata AT 模式

最终一致：MQ 消息 + 本地消息表（推荐大部分场景）

TCC：资金等强一致场景

  

实际选择：

  优先避免分布式事务（合理的服务拆分）

  无法避免时：消息最终一致性 > Seata AT > TCC

```

  

### Q7：限流算法有哪些？

```

固定窗口：简单但有边界问题

滑动窗口：解决边界问题（Sentinel 使用）

令牌桶：允许突发流量（Guava RateLimiter）

漏桶：严格匀速

  

令牌桶 vs 漏桶：

  令牌桶：固定速率生成令牌，允许攒令牌应对突发

  漏桶：固定速率处理请求，完全平滑

```

  

### Q8：HTTP 和 RPC 的区别？

```

HTTP：通用协议，跨语言，RESTful 风格（OpenFeign 使用）

RPC：远程过程调用，二进制协议，性能更高（Dubbo 使用）

  

对比：

  HTTP 更通用 / 调试方便 / 跨语言

  RPC 性能更高 / 更像本地调用 / 但耦合度更高

  

微服务内部：RPC 更高效（Dubbo）

对外暴露：HTTP 更通用（OpenFeign / Gateway）

```

## 四、常见误区

  
| 误区 | 正确理解 |
|------|---------|
| 微服务一定比单体好 | 小团队/小项目用单体更合适 |
| 分布式事务要强一致 | 大部分场景最终一致性即可 |
| Eureka 还在用 | 已停更，新项目推荐 Nacos |
| 限流只用一种算法 | 不同场景用不同算法 |
| 微服务越多越好 | 服务越多，运维和治理成本越高 |
