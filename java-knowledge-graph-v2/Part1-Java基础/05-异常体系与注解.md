## 一、异常体系

### 1.1 异常层次结构

```
                    Throwable
                   /         \
              Error          Exception
             /    \         /         \
      StackOverflow   IOException   RuntimeException
      OutOfMemoryError  SQLException  NullPointerException
                                      ArrayIndexOutOfBounds
                                      ClassCastException
                                      NumberFormatException
                                      IllegalArgumentException
```

### 1.2 分类详解

| 分类                                    | 特点         | 处理要求               | 示例                                    | 场景                           |
| ------------------------------------- | ---------- | ------------------ | ------------------------------------- | ---------------------------- |
| Error                                 | JVM 级别严重错误 | 不需要捕获              | OutOfMemoryError / StackOverflowError | 系统级的严重错误（JVM内存溢出，栈溢出）        |
| Checked Exception                     | 编译器强制处理    | try-catch 或 throws | IOException / SQLException            | 大多有外部环境因素导致（文件不存在，网络连接失败...） |
| RuntimeException（unChecked Exception） | 编程错误导致     | 不强制                | NPE / ArrayIndexOutOfBounds           | 大多是代码逻辑缺陷（数组越界，空指针调用....）    |


### 1.3 try-catch-finally 执行顺序（必考）

```java
public static int test() {
    try {
        return 1;
    } finally {
        return 2;  // 最终返回 2！finally 的 return 覆盖了 try 的
    }
}

// 规则：
// 1. finally 总是在 try/catch 的 return 之前执行
// 2. 如果 finally 中有 return，会覆盖 try/catch 的返回值
// 3. 如果 finally 修改了引用类型的属性，会影响返回值
// 4. 如果 finally 修改了基本类型的局部变量，不影响返回值（已压栈）

// 证明：finally 在 return 之前但值已压栈
public static int test2() {
    int a = 1;
    try {
        return a;     // a=1 已压入操作数栈
    } finally {
        a = 2;        // 修改了变量但不影响已压栈的值
    }
}
// 返回 1，不是 2
```

### 1.4 try-with-resources

```java
// JDK7+ 自动资源管理（实现 AutoCloseable 接口）
try (FileInputStream fis = new FileInputStream("test.txt");
     BufferedReader br = new BufferedReader(new FileReader("test.txt"))) {
    // 使用资源
} catch (IOException e) {
    // 异常处理
} // 自动调用 fis.close() 和 br.close()

// 编译后等价于：
try {
    // 使用资源
} finally {
    if (fis != null) fis.close();
    if (br != null) br.close();
}

// 自定义资源类
public class MyResource implements AutoCloseable {
    @Override
    public void close() {
        // 清理逻辑
    }
}
```

### 1.5 面试易错点

```
Q：finally 一定会执行吗？
A：不一定。
  1. System.exit() → JVM 直接退出
  2. 执行 try 的线程被杀死（interrupt / daemon 线程 JVM 退出）
  3. 无限循环卡在 try 块中

Q：throws 和 throw 的区别？
A：throws 声明在方法签名上，表示可能抛出的异常类型
   throw 在方法体内，实际抛出异常对象

Q：受检异常 vs 非受检异常的设计争议？
A：Spring 体系认为 Checked Exception 是设计失误：
  - 强制 catch 或 throws 增加代码耦合
  - Spring 统一将异常转为 RuntimeException（@Transactional 默认只回滚 RuntimeException）
```

## 二、注解

### 2.1 内置注解

| 注解 | 作用 |
|------|------|
| @Override | 标记方法重写，编译器检查是否正确重写 |
| @Deprecated | 标记已过时，编译器警告 |
| @SuppressWarnings | 抑制编译器警告 |
| @FunctionalInterface | 标记函数式接口（只有一个抽象方法） |

### 2.2 元注解（定义注解的注解）

```java
@Retention(RetentionPolicy.RUNTIME)   // 保留策略（最重要）
@Target(ElementType.FIELD)            // 作用目标
@Documented                           // 生成文档时包含
@Inherited                            // 子类继承该注解
public @interface MyColumn {
    String name();
    String type() default "VARCHAR";
    boolean nullable() default true;
}
```

**@Retention 三种策略：**

| 策略 | 保留到 | 用途 |
|------|--------|------|
| SOURCE | 源码阶段 | 编译时检查（@Override / @SuppressWarnings） |
| CLASS | 字节码阶段 | 字节码工具（ASM / ByteBuddy） |
| **RUNTIME** | 运行时 | **反射读取**（框架核心：@Autowired / @RequestMapping） |

**@Target 可选值：**

| ElementType | 含义 |
|-------------|------|
| TYPE | 类/接口/枚举 |
| FIELD | 字段 |
| METHOD | 方法 |
| PARAMETER | 方法参数 |
| CONSTRUCTOR | 构造器 |
| ANNOTATION_TYPE | 注解类型 |
| PACKAGE | 包 |

### 2.3 注解 + 反射 = 框架基石

```java
// 自定义 ORM 映射注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Column {
    String name();
    String type() default "VARCHAR(255)";
}

// 实体类
public class User {
    @Column(name = "id", type = "BIGINT")
    private Long id;

    @Column(name = "user_name")
    private String username;
}

// 运行时通过反射读取注解 → 生成 SQL（这是 MyBatis/Hibernate 的原理）
public static String generateSQL(Class<?> clazz) {
    String tableName = clazz.getSimpleName().toLowerCase();
    StringBuilder sql = new StringBuilder("CREATE TABLE " + tableName + " (");

    for (Field field : clazz.getDeclaredFields()) {
        Column col = field.getAnnotation(Column.class);
        if (col != null) {
            sql.append(col.name()).append(" ").append(col.type()).append(", ");
        }
    }
    sql.setLength(sql.length() - 2);
    sql.append(")");
    return sql.toString();
}
// 输出: CREATE TABLE user (id BIGINT, user_name VARCHAR(255))
```

### 2.4 Spring 常用注解分类

```
组件注册：@Component / @Service / @Repository / @Controller / @Configuration
依赖注入：@Autowired / @Qualifier / @Resource / @Value
Web 层：@RequestMapping / @GetMapping / @PostMapping / @RequestBody / @ResponseBody
配置：@ConfigurationProperties / @Conditional / @Profile
事务：@Transactional
Boot：@SpringBootApplication / @EnableAutoConfiguration
```

## 三、面试题精选

### Q1：Java 的异常体系是怎样的？
```
Throwable → Error + Exception
Exception → Checked Exception + RuntimeException

Error：程序不应捕获（OutOfMemoryError 等）
Checked：编译器强制处理（IOException）
Runtime：编程错误，不强制处理（NullPointerException）
```

### Q2：finally 和 finalize 的区别？
```
finally：异常处理中总是执行的代码块（释放资源）
finalize：Object 的方法，GC 回收前调用（JDK9 已废弃，不推荐使用）

为什么废弃 finalize？
  1. 执行时间不确定（GC 时间不确定）
  2. 可能导致对象复活（finalize 中重新建立引用）
  3. 性能问题
  替代：try-with-resources / Cleaner（JDK9+）
```

### Q3：注解的生命周期？
```
SOURCE < CLASS < RUNTIME

SOURCE：编译时（@Override / @SuppressWarnings / @Getter[Lombok]）
CLASS：字节码工具处理
RUNTIME：运行时反射读取（框架用）

Spring 的注解几乎都是 RUNTIME 策略
Lombok 的注解是 SOURCE 策略（编译时生成代码）
```

### Q4：Lombok 的原理是什么？
```
Lombok 注解的 @Retention 是 SOURCE
通过 JSR 269 API（Pluggable Annotation Processing API）
在编译期（javac）读取注解 → 修改抽象语法树（AST）→ 生成代码

例如 @Getter → 编译期在 AST 中插入 getter 方法
最终 .class 文件中包含生成的 getter 方法（源码中看不到）
```
