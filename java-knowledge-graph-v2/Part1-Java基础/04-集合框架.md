## 二、ArrayList 深度解析

### 扩容机制

```java
// 默认初始容量：10
private static final int DEFAULT_CAPACITY = 10;

// add 时的扩容逻辑
public boolean add(E e) {
    ensureCapacityInternal(size + 1);  // 检查是否需要扩容
    elementData[size++] = e;
    return true;
}

// 扩容为原来的 1.5 倍
int newCapacity = oldCapacity + (oldCapacity >> 1);

// 底层用 Arrays.copyOf 复制数组（O(n)）
elementData = Arrays.copyOf(elementData, newCapacity);
```

**面试关键点：**

```
Q：ArrayList 的扩容策略？
A：首次 add 时初始化为 10，之后每次扩容为 1.5 倍（位运算 >> 1）

Q：ArrayList 线程安全吗？
A：不安全。多线程同时 add 可能：
  1. 数据覆盖（两个线程写同一个位置）
   2. 数组越界（size++ 不是原子操作）
  解决：Vector（已淘汰）/ Collections.synchronizedList / CopyOnWriteArrayList
```

## 三、HashMap 深度解析（最高频考点）

### 3.1 数据结构演进

```
JDK7：数组 + 链表（头插法）
JDK8：数组 + 链表 + 红黑树（尾插法）

为什么 JDK8 改为尾插法？
  JDK7 头插法在多线程扩容时会导致链表成环 → 死循环
  尾插法保持了链表的相对顺序，避免了成环问题

注意：HashMap 仍然不是线程安全的（数据丢失等问题仍存在）
```

### 3.2 hash 计算与扰动函数

```java
// JDK8 hash 方法
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// 定位桶：(n - 1) & hash  （等价于 hash % n，但位运算更快）

// 为什么要扰动（高 16 位异或低 16 位）？
// 默认容量 16 → n-1 = 0000 0000 0000 0000 0000 0000 0000 1111
// 如果不扰动，只有低 4 位参与计算 → 哈希冲突概率高
// 扰动后高位也参与计算 → 分布更均匀
```

### 3.3 put 流程（必背）

```
1. 计算 hash → 定位桶 (n-1) & hash
2. 桶为空 → 直接插入 Node
3. 桶非空 → 比较 key
   ├── hash 相同且 equals 相等 → 覆盖 value
   ├── 桶头是 TreeNode → 红黑树插入
   └── 桶头是 Node → 遍历链表
       ├── 找到相同 key → 覆盖 value
       └── 到达尾部 → 尾插新节点
           └── 链表长度 >= 8
               ├── 数组长度 >= 64 → 转红黑树
               └── 数组长度 < 64 → 先扩容（不转树）
4. 检查是否需要扩容（size > threshold）
```

### 3.4 扩容机制

```
触发条件：size > capacity * loadFactor（默认 16 * 0.75 = 12）

扩容过程：
1. 新数组容量 = 旧容量 * 2
2. 遍历旧数组每个桶
3. 每个节点的 hash & oldCap 判断新位置：
   = 0 → 原位置
   ≠ 0 → 原位置 + oldCap
4. 不需要重新计算 hash（利用位运算特性）

为什么容量必须是 2 的幂？
  1. (n-1) & hash 等价于 hash % n（位运算更快）
  2. 扩容时只需判断高位是 0 还是 1，高效迁移
```

### 3.5 链表转红黑树的条件

```
条件 1：链表长度 >= 8（TREEIFY_THRESHOLD）
条件 2：数组长度 >= 64（MIN_TREEIFY_CAPACITY）
两个条件同时满足才转红黑树

为什么阈值是 8？
  泊松分布计算，hash 良好时链表长度达到 8 的概率极低（0.00000006%）
  如果频繁达到 8 → hash 函数有问题，应该优化 hash 而不是调阈值

退化条件：红黑树节点 <= 6（UNTREEIFY_THRESHOLD）→ 退化为链表
中间差值 7 → 避免频繁转换（链表 7-8-7-8 抖动）
```

### 3.6 为什么用红黑树不用 B+ 树 / AVL 树？

```
vs AVL 树：
  红黑树插入/删除时旋转次数更少（AVL 严格平衡，旋转多）
  查询略慢但综合性能更好

vs B+ 树：
  B+ 树适合磁盘 IO 场景（一个节点存多个元素减少 IO）
  内存中数据量小，红黑树足够

vs 跳表：
  跳表实现更简单但内存占用更大（每层都要指针）
```

### 3.7 加载因子为什么是 0.75？

```
0.75 是时间和空间的折中：
  太小（如 0.5）→ 空间浪费（频繁扩容但利用率低）
  太大（如 1.0）→ 哈希冲突增多（链表变长，查询变慢）
  0.75 → 泊松分布下桶中链表长度 >= 8 的概率极低

  且 0.75 = 3/4，capacity 是 2 的幂，threshold = capacity * 3/4 始终是整数
```

## 四、LinkedHashMap 与 LRU

```java
// LinkedHashMap = HashMap + 双向链表（维护插入顺序 / 访问顺序）
// 构造参数 accessOrder=true → 按访问顺序排序（最近访问的在尾部）

// 实现 LRU 缓存
public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LRUCache(int capacity) {
        super(capacity, 0.75f, true);  // accessOrder=true
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;  // 超过容量删除最老的（链表头部）
    }
}
```

## 五、面试题精选

### Q1：HashMap 的底层数据结构？
```
JDK7：数组 + 链表
JDK8：数组 + 链表 + 红黑树

数组：主体结构，通过 hash 定位桶
链表：解决哈希冲突（拉链法）
红黑树：链表过长时优化查询性能（O(n) → O(log n)）
```

### Q2：HashMap 和 Hashtable 的区别？
```
HashMap：允许 null key/value，非线程安全，默认容量 16
Hashtable：不允许 null，线程安全（synchronized 方法），默认容量 11

Hashtable 已淘汰，多线程用 ConcurrentHashMap
```

### Q3：HashMap 的 key 可以是 null 吗？
```
可以，null 的 hash 值为 0，放在第 0 个桶
但只能有一个 null key（再次 put 会覆盖）

value 也允许为 null，且可以有多个
```

### Q4：ArrayList 和 LinkedList 的区别？
```
底层数据结构：数组 vs 双向链表
随机访问：O(1) vs O(n)
头部插入：O(n) vs O(1)
内存占用：数组紧凑 vs 每个节点额外两个指针

实际开发中 ArrayList 性能通常更好（CPU 缓存友好 / 连续内存）
LinkedList 唯一优势：大量头部插入/删除
```

### Q5：HashSet 怎么保证不重复？
```
HashSet 底层是 HashMap（value 固定为 PRESENT 常量）

add(e) → map.put(e, PRESENT)
  1. 计算 hash
  2. 查找桶
  3. 遍历链表/树，调用 equals 比较
  4. 相同则不添加

所以要正确实现 hashCode 和 equals
```

### Q6：HashMap 多线程操作会导致什么问题？
```
1. JDK7 扩容时链表成环 → 死循环（CPU 100%）
2. 数据覆盖（两个线程同时 put 到同一个位置）
3. size 不准确
4. ConcurrentModificationException（遍历时修改）

结论：多线程必须用 ConcurrentHashMap
```

### Q7：HashMap的负载因子的作用
```
**负载因子**就是用来决定HashMap何时扩容的。
1. 负载因子设置得越大，HashMap在扩容前能容纳的元素就越多，空间利用率高，但哈希冲突的概率也会增加，因为链表会更长。
2. 如果设置得小，哈希冲突概率低，但会更早扩容，占用更多内存。
0.75是一个平衡空间和时间效率的默认值。
```

### Q8：ava 中提供了哪些线程安全的 List 实现？它们的底层实现和性能有什么区别？
```
Java 里常见的线程安全 List 有三个：
1. Vector，它是 ArrayList 的线程安全版本，几乎所有方法都加了 synchronized，性能比较差；
2. Collections.synchronizedList ()，传入一个普通 List 就能返回线程安全的 List，底层也是用同步代码块给所有操作加锁，性能和 Vector 差不多；
3. CopyOnWriteArrayList，它的底层是写时复制机制，读操作完全无锁，写操作会复制整个数组，虽然写性能差，但读多写少的场景下性能非常好。
```

## 六、集合选型速查

| 需求 | 选择 |
|------|------|
| 有序可重复 | ArrayList |
| 频繁头插/删除 | LinkedList |
| 去重 | HashSet |
| 去重 + 有序 | LinkedHashSet |
| 去重 + 排序 | TreeSet |
| KV 存储 | HashMap |
| KV + 有序 | LinkedHashMap |
| KV + 排序 | TreeMap |
| 优先级 | PriorityQueue |
| 栈操作 | ArrayDeque |
| 多线程 KV | ConcurrentHashMap |
