## 一、InnoDB vs MyISAM 详细对比

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事务支持 | ✅ 支持 ACID | ❌ 不支持 |
| 锁粒度 | 行级锁（默认） | 表级锁 |
| 外键 | ✅ 支持 | ❌ 不支持 |
| 崩溃恢复 | ✅ Redo Log 保证 | ❌ 需手动修复 |
| MVCC | ✅ 支持 | ❌ 不支持 |
| 全文索引 | ✅ 5.6+ 支持 | ✅ 支持 |
| 聚簇索引 | ✅ 数据和主键索引一体 | ❌ 非聚簇 |
| COUNT(*) | 需要遍历 | 有存储行数（无 WHERE 时） |
| 存储文件 | .ibd（数据+索引） | .MYD（数据）+.MYI（索引） |
| AUTO_INCREMENT | 聚簇索引中有序存储 | 独立自增 |

### 为什么默认选 InnoDB？

1. **事务支持**：现代应用几乎都需要事务保证
2. **行级锁**：高并发下性能远优于表级锁
3. **崩溃恢复**：通过 Redo Log 保证数据不丢失
4. **MVCC**：非锁定读，提升并发性能
5. MySQL 5.5 起默认引擎改为 InnoDB

## 二、B+ 树为什么适合数据库索引

### B+ 树 vs 其他数据结构

| 数据结构 | 磁盘 IO | 范围查询 | 树高度 | 适合场景 |
|----------|---------|---------|--------|---------|
| B+ 树 | 少（3-4次） | 极优（叶子链表） | 低（扇出大） | **数据库索引** |
| B 树 | 中等 | 差（需中序遍历） | 较低 | 文件系统 |
| 红黑树 | 多（树高） | 差 | 高 | 内存数据结构 |
| Hash | 1次 | ❌ 不支持 | - | 等值查询/内存表 |
| 跳表 | 中等 | 一般 | - | Redis ZSet |

### B+ 树的核心优势

1. **扇出大，树矮**：每个节点可存 hundreds 个 key，3层 B+ 树可存 2000万+ 行
2. **范围查询极快**：叶子节点双向链表连接，范围扫描无需回溯
3. **查询稳定**：所有数据都在叶子节点，每次查询路径长度相同
4. **磁盘友好**：一个节点 = 一页（16KB），减少 IO 次数

### B+ 树详细结构

```
                    [根节点: 10 | 20 | 30]
                   /       |        |        \
        [5|10]  [15|20]  [25|30]  [35|40]     ← 非叶节点（只存key）
        ↓        ↓        ↓        ↓
   [1,5]→[5,10]→[10,15]→[15,20]→[20,25]→...  ← 叶子节点（key+数据）
    ←──── 双向链表 ────→
```

- **根节点/非叶节点**：只存 key，不存数据，一个页能放更多 key
- **叶子节点**：存 key + 完整数据（聚簇索引）或 key + 主键值（二级索引）
- **双向链表**：支持顺序扫描和范围查询

**一页 16KB，假设 key+指针 = 12B：**
- 非叶节点可存：16KB / 12B ≈ 1365 个指针
- 3 层 B+ 树可存：1365 × 1365 × 16（叶子存数据行） ≈ **2190 万行**

## 三、聚簇索引 vs 二级索引

### 聚簇索引（Clustered Index）

```
B+ 树叶子节点结构：
┌──────┬─────────────────────────┐
│ 主键  │ 完整行数据              │
└──────┴─────────────────────────┘
```

- **数据和索引在一起**，一张表只有一个聚簇索引
- 默认用主键；没有主键用唯一索引；都没有则生成隐藏 row_id
- 主键最好自增，避免页分裂

### 二级索引（Secondary Index）

```
二级索引 B+ 树叶子节点：
┌──────────┬──────────┐
│ 索引列值  │ 主键值    │
└──────────┴──────────┘
```

- 叶子节点存的是**主键值**而非数据地址（保证数据移动时索引不用更新）

### 回表查询完整流程

```sql
SELECT * FROM user WHERE name = '张三';
-- name 上有二级索引
```

```
1. 在 name 二级索引 B+ 树中查找 '张三' → 得到主键 id=5
2. 拿 id=5 去聚簇索引 B+ 树中查找 → 得到完整行数据
3. 返回结果

流程：二级索引 → 主键值 → 聚簇索引 → 完整数据（回表）
```

**回表代价**：每次回表就是一次 B+ 树查找，扫描大量行时效率很低。

## 四、索引覆盖（Covering Index）

```sql
-- 联合索引：(name, age)

-- ❌ 需要回表：SELECT 的列不在索引中
SELECT * FROM user WHERE name = '张三';

-- ✅ 索引覆盖：所需列全在索引中，不用回表
SELECT name, age FROM user WHERE name = '张三';
```

**EXPLAIN 中 Extra 列显示 `Using index` = 命中索引覆盖。**

索引覆盖是**避免回表**的利器，也是联合索引设计的重要考量。

## 五、联合索引与最左匹配原则

联合索引 `(a, b, c)` 在 B+ 树中的排序规则：
- 先按 a 排序，a 相同按 b 排序，b 相同按 c 排序

```sql
-- 联合索引 idx_abc (a, b, c)

-- ✅ 命中索引
WHERE a = 1                          -- 用到 a
WHERE a = 1 AND b = 2               -- 用到 a, b
WHERE a = 1 AND b = 2 AND c = 3    -- 用到 a, b, c
WHERE a = 1 AND c = 3               -- 用到 a（c 无法用索引）

-- ❌ 不命中索引
WHERE b = 2                          -- 跳过了 a
WHERE c = 3                          -- 跳过了 a, b
WHERE b = 2 AND c = 3               -- 跳过了 a
```

**关键理解**：遇到范围查询（>、<、BETWEEN、LIKE）后，后面的列无法用索引：

```sql
WHERE a = 1 AND b > 2 AND c = 3
-- a ✅ | b ✅ | c ❌（b 是范围查询，c 无法走索引）
```

## 六、索引下推（ICP，Index Condition Pushdown）

MySQL 5.6+ 引入，在**存储引擎层**提前过滤，减少回表次数。

```sql
-- 联合索引 (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
```

**无 ICP（5.6 之前）**：
1. 存储引擎通过 name 找到所有 '张%' 的记录 → 拿到主键
2. 回表取出完整行 → 返回 Server 层
3. Server 层再判断 age = 25（大量无效回表）

**有 ICP（5.6+）**：
1. 存储引擎通过 name 找到 '张%' 的记录
2. **在存储引擎层直接判断 age = 25**，不满足的直接跳过
3. 只对满足条件的记录回表 → 大幅减少回表次数

**EXPLAIN 中 Extra 列显示 `Using index condition`。**

## 七、索引设计原则

### 列的选择

| 原则 | 说明 |
|------|------|
| 区分度高 | 选择区分度高的列（如手机号 > 性别） |
| 频繁查询 | WHERE/ORDER BY/GROUP BY 的列 |
| 数据量小 | 索引列尽量短（前缀索引） |
| NOT NULL | NULL 值影响索引统计 |

### 联合索引顺序

- **区分度高的列放前面**
- **等值查询列放前面**，范围查询列放后面
- **覆盖常用查询**，减少索引数量

### 避免索引失效

```sql
-- ❌ 索引失效场景
WHERE LEFT(name, 1) = '张'    -- 函数计算
WHERE name + '' = '张三'      -- 隐式转换
WHERE name LIKE '%张'         -- 前缀模糊
WHERE a = 1 OR b = 2          -- OR（除非两列都有索引）
-- 使用 != 或 NOT IN（部分场景）
```

### 避免冗余索引

```sql
-- 已有索引 (a, b)
-- ❌ 再建索引 (a)   → 冗余，(a,b) 已覆盖
-- ✅ 再建索引 (b)   → 不冗余
```

## 面试题精选

### 1. 为什么 MySQL 用 B+ 树而不是 B 树做索引？
> B+ 树非叶节点只存 key 不存数据，扇出更大树更矮；叶子节点有双向链表，范围查询效率高；查询路径长度固定，性能稳定。

### 2. 什么是回表？怎么避免？
> 二级索引查到主键值后再去聚簇索引查完整数据叫回表。避免方法：索引覆盖（所需列全在索引中）。

### 3. 联合索引 (a,b,c)，WHERE a=1 AND c=3 能用到索引吗？
> 能用到 a，c 无法使用索引。最左匹配原则要求从左到右连续使用，中间不能跳过。但 MySQL 8.0 的索引跳跃扫描可以部分优化。

### 4. 什么是索引下推？
> ICP 是 MySQL 5.6 的优化，将索引条件过滤下推到存储引擎层执行，减少回表次数。EXPLAIN 中 Extra 显示 Using index condition。

### 5. 主键为什么要自增？
> 自增主键保证数据顺序插入，避免页分裂。随机主键（如 UUID）会导致频繁页分裂和页空间浪费。

### 6. InnoDB 为什么默认选作存储引擎？
> 支持事务、行级锁、MVCC、崩溃恢复、外键，综合能力最强，适合大多数 OLTP 场景。

### 7. 聚簇索引和非聚簇索引有什么区别？
> 聚簇索引的叶子节点存完整数据，一张表只有一个；非聚簇索引叶子节点存主键值，需要回表。InnoDB 是聚簇索引组织表。

### 8. 唯一索引和普通索引怎么选？
> 如果业务上要求唯一，必须用唯一索引；如果仅为了查询优化，普通索引更好（唯一索引在插入时需要额外判断唯一性，change buffer 对唯一索引无效）。

### 9. 索引建多了有什么坏处？
> 空间占用增加；INSERT/UPDATE/DELETE 时需要维护索引，写入变慢；优化器选择执行计划时可能选错索引。

### 10. 什么是索引覆盖？
> 查询所需的列全部包含在索引中，不需要回表读取聚簇索引的数据。EXPLAIN 中 Extra 显示 Using index。

### 11. 多表联查
>**1. inner join取交集**
>**2. left join保留左表全部**
>**3. right join保留右表全部，**
>**4. 多表就链式 join**

## 常见误区

| 误区 | 正解 |
|------|------|
| 索引越多越好 | 索引有维护成本，影响写入性能 |
| WHERE 条件写对就行 | 顺序不影响优化器，但联合索引有最左匹配 |
| 有索引就一定走索引 | 优化器可能判断全表扫描更快而不走索引 |
| 联合索引任意列都能用 | 必须满足最左匹配原则 |
| 主键用 UUID 更安全 | UUID 导致页分裂，性能差，建议自增 |

## 实战场景

**场景 1：慢查询优化**
```sql
-- 慢查询
SELECT * FROM order WHERE user_id = 100 AND status = 1 ORDER BY create_time LIMIT 10;
-- 优化：建立联合索引 (user_id, status, create_time)
```

**场景 2：避免回表的覆盖索引设计**
```sql
-- 高频查询
SELECT user_id, nickname, avatar FROM user WHERE user_id = 100;
-- 联合索引 (user_id, nickname, avatar) 可实现索引覆盖
```
