## 一、RDB 持久化

RDB（Redis Database）是将内存数据以二进制快照形式保存到磁盘。

### 触发方式

| 方式 | 命令/配置 | 说明 |
|------|----------|------|
| 手动 | `SAVE` | 阻塞主进程，**生产禁用** |
| 手动 | `BGSAVE` | fork 子进程，不阻塞（推荐） |
| 自动 | `save 900 1` | 900秒内至少1个key变化 |
| 自动 | `save 300 10` | 300秒内至少10个key变化 |
| 自动 | `save 60 10000` | 60秒内至少10000个key变化 |

### BGSAVE 流程

```
主进程 ──── fork() ────→ 子进程
  │                        │
  │ 继续处理请求            │ 遍历内存生成 RDB 文件
  │                        │ 写入临时文件
  │                        │ 原子替换 dump.rdb
  │                        │ 退出
  │◄───────────────────────┘
```

**fork() 使用写时复制（COW）**：子进程共享父进程内存页，主进程修改某页时才复制该页。

### 优缺点

| 优点 | 缺点 |
|------|------|
| 文件紧凑，恢复速度快 | 非实时，两次快照间数据可能丢失 |
| 对性能影响小（子进程干活） | fork() 大内存实例时可能卡顿 |
| 适合备份和容灾 | 无法保存两次快照之间的数据 |

## 二、AOF 持久化

AOF（Append Only File）记录每条写命令到日志文件。

### 三种同步策略

| 策略 | 说明 | 性能 | 数据安全 |
|------|------|------|---------|
| always | 每条命令都 fsync | 最差 | 最高（最多丢一条） |
| **everysec** | 每秒 fsync | 折中 | 折中（最多丢1秒） |
| no | 由 OS 决定何时 fsync | 最好 | 最低 |

**生产环境推荐 everysec。**

### AOF 重写机制

AOF 文件会越来越大，重写可以压缩。

**重写原理**：不是读取旧 AOF 文件，而是直接读取当前数据库状态，用最少的命令记录。

```
原始 AOF：
SET key1 a
SET key1 b
SET key1 c          → 重写后：SET key1 c
LPUSH list 1
LPUSH list 2
LPUSH list 3        → 重写后：LPUSH list 3 2 1
DEL key2            → 重写后：（不记录已删除的key）
```

### AOF 重写流程

```
1. 主进程收到 BGREWRITEAOF 命令
2. fork() 子进程进行重写
3. 主进程继续处理请求：
   - 新写命令同时追加到【旧 AOF 缓冲区】和【重写缓冲区】
4. 子进程完成重写，生成新 AOF 文件
5. 子进程通知主进程
6. 主进程将【重写缓冲区】的命令追加到新 AOF 文件
7. 原子替换旧 AOF 文件
```

## 三、混合持久化（RDB + AOF）

Redis 4.0+ 支持，AOF 重写时前半部分用 RDB 格式，后半部分用 AOF 格式。

```
混合 AOF 文件结构：
┌────────────────────┬─────────────────────┐
│   RDB 格式（快照）   │  AOF 格式（增量命令）  │
│   历史全量数据       │  重写期间的新命令      │
└────────────────────┴─────────────────────┘
```

- 加载快：先加载 RDB 部分（快），再回放 AOF 部分（少）
- 文件小：RDB 压缩率高

```bash
# 开启混合持久化
aof-use-rdb-preamble yes
```

## 四、RDB vs AOF 对比

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 持久化方式 | 二进制快照 | 写命令日志 |
| 数据安全 | 可能丢几分钟数据 | 最多丢1秒（everysec） |
| 文件大小 | 小（二进制压缩） | 大（命令文本，重写后减小） |
| 恢复速度 | 快 | 慢（回放命令） |
| 性能影响 | fork 时可能有卡顿 | 写入 AOF 有开销 |
| 适用场景 | 备份/容灾 | 实时持久化 |

### 生产环境建议

- **数据不能丢**：AOF（everysec）+ RDB（定时备份）
- **可以接受分钟级丢失**：仅 RDB
- **最佳方案**：混合持久化（AOF + RDB 混合格式）

## 五、主从复制

### 全量复制流程

```
从节点                        主节点
  │                            │
  ├── PSYNC ? -1 ────────────→│  （第一次复制，发送psync）
  │                            │
  │←──── FULLRESYNC <runid> <offset> ──  （回复需要全量复制）
  │                            │
  │                            ├── BGSAVE 生成 RDB
  │                            │
  │←──── RDB 文件 ────────────┤  （发送 RDB）
  │                            │
  │←──── 复制缓冲区数据 ───────┤  （发送期间的写命令）
  │                            │
  ├── 加载 RDB + 回放缓冲区     │
```

### 增量复制（psync）

主从断连后重连，不需要全量复制：

```
从节点 ── PSYNC <runid> <offset> ──→ 主节点

主节点判断：
- offset 在 replication backlog 中 → 增量复制（发送差异数据）
- offset 不在 backlog 中 → 全量复制
```

**`repl_backlog_size`** 默认 1MB，建议调大到 256MB+，避免频繁全量复制。

## 六、哨兵模式（Sentinel）

哨兵是 Redis 的高可用方案：监控主从节点，自动故障转移。

### 四大功能

| 功能 | 说明 |
|------|------|
| 监控 | 定期向主从节点和其他 Sentinel 发送 PING |
| 通知 | 节点故障时通知管理员或应用 |
| 自动故障转移 | 主节点下线时自动将从节点升为主节点 |
| 配置提供者 | 客户端通过 Sentinel 获取当前主节点地址 |

### 故障转移流程

```
1. Sentinel 每秒向主节点发 PING
2. 主节点超过 down-after-milliseconds 未响应 → 标记 SDOWN（主观下线）
3. 多数 Sentinel 确认 → 标记 ODOWN（客观下线）
4. Sentinel 领导选举（Raft 算法）
5. 选中从节点升为主节点：
   - 排除不健康的从节点
   - 优先选复制偏移量最大的（数据最新）
   - runid 最小的
6. 通知其他从节点复制新主节点
7. 通知客户端新主节点地址
```

## 七、Cluster 模式

Redis Cluster 是 Redis 官方的分布式方案。

### 核心机制

**16384 个槽位**：整个数据空间分为 16384 个哈希槽，分配到不同节点。

```
key → CRC16(key) % 16384 → 槽位 → 节点

例：key = "user:1001"
CRC16("user:1001") = 12345
12345 % 16384 = 12345 → 假设槽 12345 在节点A
```

### 节点通信（Gossip 协议）

- 每个节点定期向其他节点发送 PING（携带自身和部分其他节点信息）
- 收到 PING 回复 PONG
- 通过 Gossip 传播集群状态

**通信端口 = 业务端口 + 10000**（如 6379 → 16379）

### 故障检测和转移

```
1. 节点A向节点B发 PING，超时无响应 → 标记 PFAIL（疑似故障）
2. 半数以上主节点标记 B 为 PFAIL → 标记 FAIL（确认故障）
3. B 的从节点发起选举（类似 Raft）
4. 选中从节点升为主节点，接管 B 的槽位
```

### 为什么是 16384 个槽？

- 槽越多，Gossip 消息越大（每个节点需要携带所有槽的位图）
- 16384 个槽 = 2KB 位图，传输效率合适
- 集群节点数一般不超过 1000，16384 足够均匀分配

## 八、三种集群方案对比

| 方案 | 数据分片 | 高可用 | 扩缩容 | 适用场景 |
|------|---------|--------|--------|---------|
| 主从复制 | ❌ 不分片 | ❌ 需手动切换 | - | 读多写少 |
| Sentinel | ❌ 不分片 | ✅ 自动故障转移 | - | 高可用但不需分片 |
| **Cluster** | ✅ 自动分片 | ✅ 自动故障转移 | ✅ 支持 | 大规模、高并发 |

## 面试题精选

### 1. RDB 和 AOF 的区别？
> RDB 是二进制快照，恢复快但可能丢数据；AOF 是写命令日志，数据安全但恢复慢。生产建议混合持久化。

### 2. AOF 重写是什么？流程是什么？
> AOF 重写是压缩 AOF 文件。fork 子进程根据当前数据状态生成最小命令集。主进程继续处理请求，新命令同时写入重写缓冲区。子进程完成后，主进程将缓冲区追加到新文件，原子替换。

### 3. Redis 主从复制怎么实现的？
> 首次连接全量复制（BGSAVE 生成 RDB 发送给从节点）；断连后增量复制（通过 replication backlog 中的偏移量找到差异）。从节点默认只读。

### 4. Sentinel 是怎么工作的？
> Sentinel 通过 PING 监控节点，主节点超时后先标记主观下线，多数确认后标记客观下线，然后通过 Raft 选举 Sentinel 领导者，由其选出最优从节点升为主节点，并通知其他从节点和客户端。

### 5. Redis Cluster 的路由算法是什么？
> CRC16(key) % 16384 得到槽位号，每个节点负责一部分槽。客户端先访问任意节点，如果 key 不在该节点，返回 MOVED 重定向。

### 6. 为什么 Redis Cluster 用 16384 个槽而不是更多？
> 槽位越多，节点间 Gossip 消息越大。16384 槽的位图只有 2KB，在节点间传输效率合适。而且集群节点一般不超过 1000 个，16384 足够均匀分配。

### 7. 混合持久化是什么？
> Redis 4.0+ 的特性，AOF 重写时前半部分用 RDB 二进制格式（快），后半部分用 AOF 命令格式（增量），兼顾恢复速度和数据安全。

### 8. 从节点选举规则是什么？
> 排除不健康的从节点 → 选复制偏移量最大的（数据最新）→ 选优先级最高的 → 选 runid 最小的。

## 常见误区

| 误区 | 正解 |
|------|------|
| AOF 比RDB 好 | 各有优劣，生产建议混合持久化 |
| Sentinel 做数据分片 | Sentinel 只做高可用，不做分片 |
| Cluster 支持多 key 操作 | 跨槽的多 key 操作需要 hash tag 确保 key 在同一槽 |
| 主从复制是同步的 | 默认异步复制，主节点不等从节点确认 |
| RDB 的 BGSAVE 完全不阻塞 | fork() 大内存实例时可能耗时 |

## 实战场景

**场景 1：生产环境持久化配置**
```bash
# redis.conf
appendonly yes                  # 开启 AOF
appendfsync everysec            # 每秒刷盘
aof-use-rdb-preamble yes       # 混合持久化
save 900 1                      # RDB 作为备份
save 300 10
save 60 10000
```

**场景 2：Cluster 扩容**
```bash
# 添加新节点
redis-cli --cluster add-node new_host:6379 existing_host:6379
# 重新分配槽位
redis-cli --cluster reshard existing_host:6379
```
