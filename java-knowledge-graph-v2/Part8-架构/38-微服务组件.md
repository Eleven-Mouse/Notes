## 二、架构演进历程

### 单体 → SOA → 微服务

```
单体架构：
  ┌──────────────────────────┐
  │ 用户模块 │ 商品模块 │ 订单模块│
  │ ──────── 共享数据库 ────────│
  └──────────────────────────┘
  优势：开发简单、部署简单、测试方便
  劣势：代码膨胀、牵一发动全身、扩展困难、团队协作冲突

SOA 架构：
  ┌──────┐  ┌──────┐  ┌──────┐
  │服务A │  │服务B │  │服务C │
  └──┬───┘  └──┬───┘  └──┬───┘
     └─────ESB─────┘        （企业服务总线）
  特点：通过 ESB 集成，强调服务复用
  劣势：ESB 成为单点和瓶颈

微服务架构：
  ┌──────┐  ┌──────┐  ┌──────┐
  │用户服务│ │商品服务│ │订单服务│  各自独立部署、独立数据库
  └──┬───┘  └──┬───┘  └──┬───┘
     └─── API Gateway ───┘   通过网关统一入口
```

### 微服务优缺点

| 优势 | 劣势 |
|------|------|
| 独立部署、独立扩展 | 分布式系统复杂度高 |
| 技术栈可异构 | 服务间调用增加延迟 |
| 故障隔离 | 数据一致性难保证 |
| 团队独立开发 | 运维成本增加（监控、日志、链路追踪） |

## 三、服务注册与发现

### 核心原理

```
服务注册：服务启动时将自己的地址（IP:Port）注册到注册中心
服务发现：消费者从注册中心获取提供者地址列表
心跳检测：注册中心通过心跳检测服务是否存活

Provider → 注册 → Registry（注册中心）
Consumer → 订阅 → Registry → 获取 Provider 列表 → 调用 Provider
```

### 注册中心对比

| 维度 | Nacos | Eureka | ZooKeeper | Consul |
|------|-------|--------|-----------|--------|
| **CAP 模型** | AP/CP 可切换 | AP（最终一致） | CP（强一致） | CP |
| **健康检查** | 心跳 + TCP/HTTP | 心跳（客户端） | 会话保持 | TCP/HTTP/Script |
| **配置中心** | 内置 | 无 | 无 | 内置 |
| **一致性协议** | Raft（CP）/ Distro（AP） | 无（Peer-to-Peer） | ZAB | Raft |
| **临时/持久实例** | 支持 | 仅临时 | 仅持久 | 仅临时 |
| **雪崩保护** | 有 | 有 | 无 | 无 |
| **维护方** | 阿里（活跃） | Netflix（停更） | Apache | HashiCorp |

**选型建议：** Spring Cloud Alibaba 生态首选 Nacos（同时提供注册中心 + 配置中心）。

## 四、配置中心

| 配置中心 | 特点 |
|---------|------|
| **Nacos Config** | 内置在 Nacos 中，开箱即用，支持灰度发布、回滚 |
| **Apollo** | 携程开源，功能丰富（多环境/多集群/灰度/权限），适合大型项目 |
| **Spring Cloud Config** | 需要配合 Git/SVN，功能较少，需要额外组件（Bus）实现热刷新 |

```yaml
# Nacos Config 配置示例
spring:
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
        namespace: dev
        group: DEFAULT_GROUP
        file-extension: yaml
        refresh-enabled: true  # 自动刷新
```

## 五、服务调用

### OpenFeign（声明式 HTTP）

```java
// 声明式调用：像调用本地方法一样调用远程接口
@FeignClient(name = "order-service", fallback = OrderFallback.class)
public interface OrderClient {
    @GetMapping("/order/{id}")
    Order getOrder(@PathVariable("id") Long id);
}

// 使用
@Autowired
private OrderClient orderClient;
Order order = orderClient.getOrder(1L);
```

### Dubbo（RPC 框架）

```java
// 服务提供者
@DubboService
public class OrderServiceImpl implements OrderService {
    public Order getOrder(Long id) { ... }
}

// 服务消费者
@DubboReference
private OrderService orderService;
Order order = orderService.getOrder(1L);
```

### HTTP vs RPC 区别

| 维度 | HTTP（OpenFeign） | RPC（Dubbo） |
|------|-------------------|--------------|
| **协议** | HTTP/1.1 / HTTP2 | 自定义 TCP 协议 |
| **序列化** | JSON（文本） | Hessian / Protobuf（二进制） |
| **性能** | 较低（文本序列化 + HTTP 头开销） | 较高（二进制 + 自定义协议） |
| **跨语言** | 天然支持 | 需要各语言 SDK |
| **服务治理** | 依赖 Spring Cloud 生态 | 内置（路由/熔断/限流） |
| **适用场景** | 对外 API、前后端通信 | 内部服务间高性能调用 |

## 六、网关（Spring Cloud Gateway）

### 核心功能

```
客户端 → Spring Cloud Gateway → 微服务
          ├── 路由（Route）：根据路径/域名/Header 路由到后端服务
          ├── 过滤器链（Filter Chain）：前置/后置处理
          ├── 限流（Rate Limiter）：Redis 令牌桶限流
          ├── 鉴权（Authentication）：JWT / OAuth2 校验
          ├── 熔断（Circuit Breaker）：集成 Sentinel / Resilience4j
          └── 日志/监控：请求日志、链路追踪
```

```yaml
# Gateway 路由配置示例
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service          # lb 表示负载均衡
          predicates:
            - Path=/api/order/**           # 路径匹配
          filters:
            - StripPrefix=1                # 去掉路径前缀
            - name: RequestRateLimiter     # 限流
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
```

## 七、负载均衡

### 客户端 vs 服务端

| 类型 | 代表 | 特点 |
|------|------|------|
| **客户端负载均衡** | Ribbon / Spring Cloud LoadBalancer | 消费者从注册中心获取服务列表，自行选择实例 |
| **服务端负载均衡** | Nginx / F5 | 请求先到 LB，由 LB 转发到后端 |

### 负载均衡策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **轮询（Round Robin）** | 依次分配 | 服务器性能相近 |
| **随机（Random）** | 随机选择 | 简单场景 |
| **加权轮询** | 按权重分配 | 服务器性能不均 |
| **最少连接（Least Connections）** | 选当前连接数最少的 | 长连接场景 |
| **一致性哈希（Consistent Hash）** | 相同请求参数路由到同一实例 | 有状态需求（Session） |
| **加权响应时间** | 响应越快权重越高 | 对延迟敏感的场景 |

## 九、面试题

### Q1：微服务和单体架构的区别？什么时候用微服务？🔥🔥🔥🔥

单体架构适合小团队/项目初期，开发部署简单。微服务适合大团队/复杂业务，独立部署扩展但增加分布式复杂度。不要为了微服务而微服务，团队 < 10 人优先单体。

### Q2：Nacos 和 Eureka 的区别？🔥🔥🔥🔥

Nacos 支持 AP/CP 切换（临时实例 AP，持久实例 CP），内置配置中心，有雪崩保护。Eureka 只有 AP 模式，已停止维护。Nacos 是更好的选择。

### Q3：HTTP 和 RPC 的区别？Dubbo 和 Feign 怎么选？🔥🔥🔥🔥

HTTP 协议通用但性能较低，RPC 自定义协议性能高但需要 SDK。对外用 HTTP/Feign，内部高性能调用用 Dubbo。

### Q4：Spring Cloud Gateway 的作用？🔥🔥🔥

统一入口、路由转发、鉴权、限流、熔断、日志监控。所有外部请求经过网关，后端服务不需要对外暴露。

### Q5：负载均衡有哪些策略？一致性哈希是什么？🔥🔥🔥

轮询/随机/加权/最少连接/一致性哈希。一致性哈希将服务和请求都映射到哈希环上，同一请求参数路由到同一实例，增加/减少节点只影响相邻节点。

### Q6：服务注册与发现的原理？🔥🔥🔥

服务启动时注册到注册中心（IP:Port），消费者从注册中心拉取服务列表并缓存，注册中心通过心跳检测剔除不健康实例，服务变更时推送通知消费者更新。

### Q7：什么是服务雪崩？如何预防？🔥🔥🔥🔥

一个服务故障导致调用链上游全部故障。预防：熔断（Sentinel/Hystrix）、超时设置、降级策略、限流、隔离（线程池/信号量）。

### Q8：Nacos 的 AP 和 CP 模式怎么切换？🔥🔥

临时实例（ephemeral=true）使用 AP 模式（Distro 协议），持久实例（ephemeral=false）使用 CP 模式（Raft 协议）。默认临时实例。注册的服务实例用 AP（可用性优先），配置信息用 CP（一致性优先）。

## 十、常见误区

| 误区 | 正确理解 |
|------|----------|
| 微服务一定比单体好 | 微服务增加分布式复杂度，小团队/初期阶段单体更合适 |
| Eureka 还在维护 | Netflix 已停止维护 2.x 版本 |
| RPC 总是比 HTTP 快 | 局域网内差距明显，跨网络差距缩小 |
| 网关能处理所有安全问题 | 网关做粗粒度鉴权，服务内部仍需细粒度权限控制 |
| 注册中心数据必须强一致 | AP 模式（最终一致）对大多数场景够用，且可用性更好 |
