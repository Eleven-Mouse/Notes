## 二、限流算法详解

### 1. 固定窗口计数器

```
将时间划分为固定窗口（如每分钟），每个窗口内维护一个计数器

0s                60s               120s
├────── 100 ──────┤────── 100 ──────┤
                  ↑ 窗口切换时计数器清零

问题：临界点突发流量
  第 59 秒来了 100 个请求，第 61 秒又来了 100 个请求
  窗口内都合法，但 2 秒内实际通过了 200 个请求（2 倍突发）
```

### 2. 滑动窗口计数器

```
将窗口细分为多个小格子，滑动统计

  [0-20s] [20-40s] [40-60s] [60-80s] [80-100s]
                              ◀── 当前窗口 ──▶
  每次统计最近 60 秒内的请求总数

优势：解决了固定窗口的临界突发问题
Sentinel 使用滑动窗口（LeapArray）实现
```

### 3. 令牌桶算法

```
               令牌桶（容量 = burst）
              ┌──────────────────┐
  固定速率 ──▶ │  ○ ○ ○ ○ ○ ○ ○   │  ──▶ 请求拿走一个令牌则通过
  放入令牌     │  （桶满则丢弃）    │      没有令牌则拒绝/等待
              └──────────────────┘

特点：
  - 允许突发流量（桶内有积累的令牌）
  - 平均速率由令牌生成速率控制
  - Sentinel 的 GCRA 算法是令牌桶的变体
```

### 4. 漏桶算法

```
              漏桶
          ┌──────────┐
  请求 ──▶│ ▓▓▓▓▓▓▓▓ │──▶ 固定速率流出（匀速处理）
          │ （队列）  │    桶满则拒绝新请求
          └──────────┘

特点：
  - 严格匀速输出，削峰填谷
  - 不允许突发流量（即使后端空闲也按固定速率处理）
  - 适合需要严格控制处理速率的场景
```

### 令牌桶 vs 漏桶

| 维度 | 令牌桶 | 漏桶 |
|------|--------|------|
| **突发流量** | 允许（桶内有积累令牌） | 不允许（匀速输出） |
| **速率** | 平均速率限制，允许突发 | 严格固定速率 |
| **场景** | API 网关限流（允许突发） | 消息队列消费（匀速处理） |
| **主流实现** | Sentinel / Guava RateLimiter | MQ 消费端 |

## 三、Sentinel 核心

### 核心概念

| 概念 | 说明 |
|------|------|
| **资源** | 需要保护的内容（接口/方法/代码块） |
| **规则** | 限流/熔断/降级/系统保护规则 |
| **插槽链（Slot Chain）** | 请求处理的流水线（统计 → 规则检查 → 熔断判断） |

### Sentinel 限流规则

| 规则类型 | 说明 |
|---------|------|
| **QPS 限流** | 每秒请求数超阈值则拒绝 |
| **线程数限流** | 并发线程数超阈值则拒绝（隔离手段） |
| **关联限流** | 关联资源达到阈值时，限流当前资源 |
| **链路限流** | 只统计从指定入口进来的流量 |

### Sentinel 熔断模式

| 模式 | 说明 | 触发条件 |
|------|------|---------|
| **慢调用比例** | 响应时间超过阈值的请求比例过高 | RT > maxRT 的比例 > 比例阈值 |
| **异常比例** | 异常请求比例过高 | 异常数 / 总请求数 > 比例阈值 |
| **异常数** | 异常请求数超过阈值 | 异常数 > 阈值 |

### 熔断状态机

```
         慢调用比例/异常比例/异常数
         超过阈值
  CLOSED ──────────────▶ OPEN
    ▲                      │
    │    探测请求成功        │ 熔断时长结束
    │                      ▼
    └──── HALF_OPEN ◀─────┘
              │
              │ 探测请求失败
              ▼
            OPEN（重新计时）

CLOSED：正常放行请求，同时统计指标
OPEN：直接拒绝请求（快速失败），不调用下游
HALF_OPEN：放行少量探测请求，成功则恢复 CLOSED，失败则回到 OPEN
```

## 四、降级策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **返回默认值** | 返回预设的兜底数据 | 推荐列表、默认配置 |
| **读缓存** | 从本地/Redis 缓存读取旧数据 | 商品详情、文章内容 |
| **写 MQ 转异步** | 将请求写入 MQ，异步处理 | 下单、发券 |
| **关闭非核心功能** | 关闭推荐/评论等非核心模块 | 大促期间保核心 |

```java
// Sentinel 降级示例
@SentinelResource(value = "getOrder",
    blockHandler = "getOrderBlock",    // 限流/降级处理
    fallback = "getOrderFallback")     // 异常处理
public Order getOrder(Long id) {
    return orderService.getById(id);
}

// 限流降级：返回默认值
public Order getOrderBlock(Long id, BlockException e) {
    return new Order(-1L, "系统繁忙，请稍后重试");
}

// 异常降级：读缓存
public Order getOrderFallback(Long id, Throwable t) {
    return redisTemplate.opsForValue().get("order:cache:" + id);
}
```

## 五、限流 / 熔断 / 降级三者关系

```
三者都是保护系统的手段，但触发条件和处理方式不同：

限流：入口处控制流量（QPS 超阈值 → 拒绝）
  → "排队买票，票卖完就不卖了"

熔断：检测到下游故障时切断调用（错误率超阈值 → 快速失败）
  → "发现路断了，不再走了，等路修好再走"

降级：系统压力大或部分功能不可用时的兜底方案（返回默认值/缓存）
  → "高级功能用不了，给个基础版本先用着"

协作关系：
  限流（预防）→ 熔断（检测故障）→ 降级（兜底方案）
```

## 六、常用限流组件对比

| 维度 | Sentinel | Hystrix | Resilience4j |
|------|----------|---------|--------------|
| **维护状态** | 阿里活跃维护 | Netflix 停更 | 社区活跃 |
| **限流** | 支持（QPS/线程数） | 不支持（需外部） | 限流器模块 |
| **熔断** | 支持（3 种模式） | 支持 | 支持 |
| **实时监控** | 控制台（Dashboard） | Dashboard | Micrometer |
| **规则配置** | 动态（控制台/API） | 静态（配置文件） | 静态 |
| **扩展性** | SPI 扩展 | 插件机制 | 函数式 |
| **适用框架** | Spring Cloud Alibaba | Spring Cloud Netflix | Spring Boot/Cloud |

**选型建议：** Spring Cloud Alibaba 项目用 Sentinel；轻量级项目用 Resilience4j。

## 七、接口幂等性（5 种方案）

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| **Token 机制** | 请求前获取 Token，提交时校验并删除 | 表单提交 |
| **数据库唯一约束** | 唯一索引防重插入 | 创建类操作 |
| **Redis SETNX** | SETNX 请求ID 过期时间 | 通用 |
| **乐观锁（版本号）** | UPDATE ... SET version=version+1 WHERE version=old | 更新类操作 |
| **状态机** | 状态只能单向流转 | 订单/工单流转 |

```java
// Token 幂等方案
// 1. 获取 Token
@GetMapping("/token")
public String getToken() {
    String token = UUID.randomUUID().toString();
    redis.set("idempotent:" + token, "1", 10, TimeUnit.MINUTES);
    return token;
}

// 2. 提交时校验 Token
@PostMapping("/order")
public Result createOrder(@RequestHeader("X-Token") String token, ...) {
    //原子操作：删除成功=首次提交，删除失败=重复提交
    Boolean deleted = redis.delete("idempotent:" + token);
    if (Boolean.FALSE.equals(deleted)) {
        return Result.fail("请勿重复提交");
    }
    return orderService.create(...);
}
```

## 八、面试题

### Q1：限流算法有哪些？令牌桶和漏桶的区别？🔥🔥🔥🔥🔥

固定窗口（简单但有临界突发）、滑动窗口（解决临界问题）、令牌桶（允许突发）、漏桶（匀速输出）。令牌桶允许突发流量（桶内积累的令牌），漏桶严格匀速。

### Q2：Sentinel 和 Hystrix 的区别？🔥🔥🔥🔥

Sentinel 活跃维护，支持限流 + 熔断 + 降级 + 热点参数限流，有可视化控制台，规则动态配置。Hystrix 已停更，只支持熔断降级不支持限流，配置静态。

### Q3：熔断的三种模式？状态机怎么流转？🔥🔥🔥🔥

慢调用比例、异常比例、异常数。状态机：CLOSED（正常）→ OPEN（熔断，快速失败）→ HALF_OPEN（探测）→ 成功回 CLOSED / 失败回 OPEN。

### Q4：限流、熔断、降级三者的区别？🔥🔥🔥🔥

限流是入口控制流量（预防）；熔断是检测到下游故障时切断调用（保护）；降级是功能不可用时的兜底方案（兜底）。三者的关系：限流预防 → 熔断保护 → 降级兜底。

### Q5：如何保证接口幂等性？🔥🔥🔥

Token 机制（表单）、数据库唯一约束（创建）、Redis SETNX（通用）、乐观锁/版本号（更新）、状态机（流转）。根据业务场景选择合适的方案。

### Q6：Sentinel 的限流规则有哪些？🔥🔥

QPS 限流（每秒请求数）、线程数限流（并发线程数）、关联限流（关联资源达到阈值时限流当前资源）、链路限流（只统计指定入口）。

### Q7：如何设计一个接口限流方案？🔥🔥🔥

方案：网关层（Spring Cloud Gateway + Redis 令牌桶限流，粗粒度）+ 服务层（Sentinel 细粒度限流）+ 自定义注解（AOP + Redis 分布式限流）。分层限流，网关挡大流量，服务层精细控制。

### Q8：什么是服务雪崩？如何防止？🔥🔥🔥🔥

一个服务故障导致调用链上所有服务不可用。防止：超时设置（快速失败）、熔断（切断故障调用）、降级（兜底方案）、限流（控制入口流量）、隔离（线程池/信号量隔离）。

## 九、常见误区

| 误区 | 正确理解 |
|------|----------|
| 限流就是熔断 | 限流是预防（控制流量），熔断是保护（检测故障后切断） |
| 熔断打开后就不恢复 | HALF_OPEN 状态会放行探测请求，成功则恢复 |
| Hystrix 和 Sentinel 二选一 | Sentinel 是更好的选择（功能全 + 活跃维护） |
| 幂等只需要去重 | 幂等是保证多次操作结果一致，去重是其中一种手段 |
| 限流阈值越大越好 | 过大保护不了系统，过小影响用户体验，需要压测确定 |

## 十、实战场景

### 多级限流架构

```
请求 → CDN 限流 → Nginx 限流（漏桶） → Gateway 限流（令牌桶）
      → Sentinel（QPS + 线程数） → 业务层（Redis 分布式限流）
```

### 大促降级预案

```
1. 关闭非核心功能（评论/推荐/积分）
2. 降级写操作为异步（下单 → MQ → 异步处理）
3. 读操作走缓存（Redis + 本地缓存二级）
4. 限流阈值调低（保护核心链路）
5. 熔断超时时间调短（快速失败，不拖垮上游）
```
