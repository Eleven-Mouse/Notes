## 二、CAP 定理

### 三要素

```
C（Consistency）一致性：所有节点在同一时刻看到相同的数据
A（Availability）可用性：每个请求都能在合理时间内收到非错误响应
P（Partition Tolerance）分区容错性：网络分区时系统仍能运行

CAP 定理：分布式系统中，C/A/P 三者最多同时满足两个
由于网络分区（P）不可避免，实际上只能在 CP 和 AP 之间选择
```

### CP 系统与 AP 系统

| 类型 | 代表 | 特点 | 适用场景 |
|------|------|------|---------|
| **CP** | ZooKeeper / Etcd / Consul | 保证一致性，牺牲可用性（Leader 选举期间不可用） | 配置中心、分布式锁、 Leader 选举 |
| **AP** | Eureka / Nacos（临时实例） | 保证可用性，牺牲一致性（最终一致） | 服务注册发现 |

### Nacos 的特殊之处

```
Nacos 支持 AP/CP 切换：
  临时实例（ephemeral=true）→ AP 模式（Distro 协议）
  持久实例（ephemeral=false）→ CP 模式（Raft 协议）

服务注册用 AP（可用性优先，偶尔不一致可接受）
配置管理用 CP（一致性优先，配置不能出错）
```

## 三、BASE 理论

```
BASE 是 CAP 中 AP 的延伸，是对大规模分布式系统的实践总结

BA（Basically Available）基本可用：
  系统出现故障时，允许损失部分功能（如降级），但核心功能可用

S（Soft State）软状态：
  允许系统中的数据存在中间状态（如复制延迟），不要求时刻一致

E（Eventually Consistent）最终一致性：
  系统保证在没有新的更新操作后，数据最终达到一致状态

核心思想：既然强一致性做不到，就退而求其次，保证最终一致性
```

## 四、一致性哈希

### 原理

```
普通哈希的问题：
  hash(key) % N → 当 N 变化时（扩容/缩容），几乎所有数据都要迁移

一致性哈希：
  将哈希值空间组织为虚拟环（0 ~ 2^32-1）
  节点和数据都映射到环上
  数据顺时针找到的第一个节点就是其归属节点

         Node A
        /      \
    data1      data4
      /          \
  Node D        Node B
      \          /
    data3      data2
        \      /
         Node C

扩容：新增 Node E，只需要迁移 Node A 和 Node D 之间的数据
缩容：移除 Node B，只需要将 Node B 的数据迁移到 Node C
```

### 虚拟节点解决数据倾斜

```
问题：节点少时，数据分布不均匀（某节点负载远大于其他）
解决：每个物理节点映射多个虚拟节点

Node A → VA_1, VA_2, VA_3, ..., VA_100
Node B → VB_1, VB_2, VB_3, ..., VB_100
Node C → VC_1, VC_2, VC_3, ..., VC_100

虚拟节点均匀分布在环上 → 数据均匀分布
```

## 五、分布式 ID

### 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **UUID** | 128 bit 随机值 | 简单、无依赖 | 无序、索引效率低、长度长 |
| **数据库自增** | AUTO_INCREMENT | 简单有序 | 单点、性能瓶颈 |
| **数据库号段模式** | 批量取一段 ID 缓存本地 | 减少数据库压力 | 依赖数据库 |
| **Redis incr** | INCR 原子自增 | 高性能 | 依赖 Redis、持久化风险 |
| **雪花算法** | 时间+机器+序列号 | 有序、高性能、不依赖外部 | 时钟回拨问题 |
| **Leaf** | 美团方案（号段+Snowflake） | 综合方案 | 需要部署 Leaf 服务 |

### 雪花算法详细结构

```
64 bit（8 字节）Long 型 ID：

 0 | 00000000 00000000 00000000 00000000 00000000 0 | 00000 | 00000 | 000000000000
 │  │                   41 bit 时间戳                │       │       │
 │  └───────────────────────────────────────────────┘       │       │
 符                                                      数据中心ID  序列号
 号                                           5 bit 机器ID   5 bit   12 bit
 位                                           （32个）     （32个） （4096个）

 1 bit：符号位，永远为 0
41 bit：时间戳（毫秒级），可用约 69 年
 5 bit：数据中心 ID（0-31）
 5 bit：机器 ID（0-31）
12 bit：序列号（同一毫秒内 0-4095）

每台机器每毫秒最多生成 4096 个 ID
单机 QPS = 4096 × 1000 = 409.6 万/秒
```

### 时钟回拨问题

```
问题：NTP 时间同步导致系统时钟回退，可能生成重复 ID

解决方案：
  1. 回拨 < 5ms：等待回拨时间过去再生成
  2. 回拨 > 5ms：抛异常拒绝生成（保守策略）
  3. 采用历史最大时间戳（Leaf 的方案）
  4. 使用多余的钱来借未来时间（百度 UidGenerator）
```

## 六、分布式事务方案

### 1. 2PC（两阶段提交）

```
第一阶段：Prepare（准备）
  协调者 ──▶ 参与者1：请准备好提交
           ──▶ 参与者2：请准备好提交
  参与者执行事务但不提交，锁定资源

第二阶段：Commit / Rollback
  所有参与者都准备好 → 协调者发送 Commit
  任一参与者未准备好 → 协调者发送 Rollback

     协调者
    /       \
  参与者1  参与者2

  问题：
  1. 同步阻塞：资源锁定期间其他事务等待
  2. 单点故障：协调者宕机，参与者永远阻塞
  3. 脑裂：第二阶段只有部分参与者收到 Commit → 数据不一致
```

### 2. TCC（Try-Confirm-Cancel）

```
Try：预留资源（冻结库存、冻结余额）
Confirm：确认操作（扣减冻结的库存/余额）
Cancel：取消操作（释放冻结的资源）

示例：下单扣库存
  Try：    UPDATE stock SET frozen = frozen + 1 WHERE goods_id = ?
  Confirm：UPDATE stock SET total = total - 1, frozen = frozen - 1 WHERE goods_id = ?
  Cancel： UPDATE stock SET frozen = frozen - 1 WHERE goods_id = ?

优点：无锁、高性能、最终一致
缺点：业务侵入大（每个操作要写 Try/Confirm/Cancel 三个方法）
适用：对一致性要求高的资金类业务
```

### 3. Saga 模式

```
长事务拆分为多个本地事务，每个本地事务有对应的补偿操作

正向执行：T1 → T2 → T3 → T4（全部成功则完成）
补偿回滚：T1 → T2 → T3 失败 → C3 → C2 → C1（逆序补偿）

优点：无锁、适合长事务
缺点：缺乏隔离性（脏读问题）
适用：跨公司的业务编排（如旅游预订：机票+酒店+租车）

Seata 的 Saga 模式：基于状态机引擎，通过 JSON 定义状态流转和补偿逻辑
```

### 4. 消息最终一致性

```
方案 A：本地消息表
  1. 业务操作 + 写消息到本地消息表（同一本地事务）
  2. 后台线程轮询消息表，发送到 MQ
  3. 消费者消费消息，执行下游业务
  4. 消费成功后 ACK，更新消息表状态

方案 B：事务消息（RocketMQ）
  1. 发送半消息（Half Message）
  2. 执行本地事务
  3. 本地事务成功 → Commit（消息可见）
     本地事务失败 → Rollback（消息删除）
  4. 如果长时间未 Commit/Rollback，Broker 回查本地事务状态

优点：异步解耦、性能高
缺点：有延迟（最终一致，非实时一致）
```

### 5. Seata

| 模式 | 原理 | 侵入性 | 性能 | 适用场景 |
|------|------|--------|------|---------|
| **AT** | 自动拦截 SQL，生成回滚日志（undo_log） | 低（只需加注解） | 中 | 大多数业务场景 |
| **TCC** | 手写 Try/Confirm/Cancel | 高 | 高 | 资金类高一致性场景 |
| **Saga** | 状态机编排 + 补偿 | 中 | 高 | 长事务编排 |
| **XA** | 数据库 XA 协议（2PC） | 低 | 低 | 已有 XA 数据库 |

```java
// Seata AT 模式示例（最常用）
@GlobalTransactional  // 只需加一个注解
public void purchase(String userId, String commodityCode, int count) {
    // 扣减库存（远程服务）
    stockService.deduct(commodityCode, count);
    // 扣减余额（远程服务）
    accountService.debit(userId, totalAmount);
    // 创建订单（本地事务）
    orderService.create(userId, commodityCode, count);
}
// 任一步骤失败，Seata 自动回滚所有已执行的分支事务
```

### 方案选型建议

```
强一致 + 高性能 → TCC
最终一致 + 低侵入 → Seata AT / 消息最终一致性
长事务编排 → Saga
已有 XA 数据库 + 简单场景 → XA
绝大多数业务 → Seata AT（推荐首选）
```

## 七、面试题

### Q1：CAP 定理是什么？为什么只能三选二？🔥🔥🔥🔥🔥

C（一致性）、A（可用性）、P（分区容错性）。网络分区不可避免，所以 P 必选。在分区发生时，要么选择一致性（CP，牺牲可用性），要么选择可用性（AP，牺牲一致性）。

### Q2：BASE 理论是什么？和 CAP 的关系？🔥🔥🔥

BA（基本可用）+ S（软状态）+ E（最终一致性）。是 CAP 中 AP 方案的延伸，核心思想是放弃强一致性，保证最终一致性，是大多数互联网系统的设计原则。

### Q3：雪花算法的原理？时钟回拨怎么处理？🔥🔥🔥🔥

64 bit：1 符号位 + 41 时间戳 + 5 数据中心 + 5 机器 + 12 序列号。时钟回拨处理：小幅回拨等待、大幅回拨拒绝或借用未来时间。

### Q4：2PC 有什么问题？🔥🔥🔥

同步阻塞（资源锁定期间其他事务等待）、单点故障（协调者宕机导致参与者阻塞）、脑裂（部分参与者未收到 Commit 导致数据不一致）。

### Q5：TCC 和 Saga 的区别？🔥🔥🔥

TCC 每个 操作要写 Try/Confirm/Cancel，实时性强但侵入大。Saga 将长事务拆为多个本地事务 + 补偿操作，适合跨系统长事务但缺乏隔离性。

### Q6：消息最终一致性怎么实现？🔥🔥🔥🔥

本地消息表：业务操作和消息写入同一本地事务，后台线程异步发送 MQ。事务消息（RocketMQ）：半消息 + 本地事务 + Commit/Rollback。消费者幂等处理保证不重复。

### Q7：Seata AT 模式的原理？🔥🔥🔥

拦截 SQL，自动生成前镜像（修改前数据）和后镜像（修改后数据）写入 undo_log。事务回滚时根据 undo_log 的前镜像反向补偿。一阶段提交（不等待所有分支），二阶段异步清理 undo_log。

### Q8：一致性哈希是什么？为什么要虚拟节点？🔥🔥

将节点和数据映射到哈希环上，数据顺时针找最近的节点。新增/删除节点只影响相邻节点的数据。虚拟节点解决节点少时数据分布不均匀的问题。

### Q9：分布式 ID 有哪些方案？你们用的什么？🔥🔥🔥

UUID / 数据库自增 / 号段模式 / Redis incr / 雪花算法 / Leaf。常用雪花算法（有序、高性能），大规模用 Leaf（号段 + Snowflake）。

### Q10：如何选择分布式事务方案？🔥🔥🔥

看一致性要求和性能需求。强一致 → TCC；最终一致 + 低侵入 → Seata AT；长事务 → Saga；简单场景 → 消息最终一致性。大多数互联网业务用 Seata AT 或消息最终一致性。

## 八、常见误区

| 误区 | 正确理解 |
|------|----------|
| CAP 可以三者兼顾 | 网络分区不可避免，P 必选，只能在 CP 和 AP 间选择 |
| 最终一致性 = 不一致 | 最终一致性保证一段时间后数据一致，是 CAP 的工程折中 |
| 雪花算法没有缺点 | 时钟回拨问题需要额外处理 |
| 2PC 能保证分布式事务 | 2PC 有单点故障和脑裂问题，不能保证 100% 一致 |
| 分布式事务应该到处用 | 引入分布式事务会增加复杂度，应尽量用本地事务 + 消息 |

## 九、实战场景

### 电商下单的分布式事务方案

```
场景：下单 → 扣库存 → 扣余额 → 创建订单（涉及3个服务）

方案一：Seata AT（推荐）
  @GlobalTransactional 注解，自动回滚

方案二：RocketMQ 事务消息
  订单服务发送半消息 → 创建订单 → Commit → 库存服务消费扣库存

方案三：本地消息表
  订单创建 + 消息写入本地表 → 发 MQ → 库存/账户服务消费

选型：初创/中小项目用 Seata AT，大规模/微服务拆分细的用消息最终一致性
```
