## 二、核心知识点

### 1. 判断对象存活

#### 1.1 引用计数法（已淘汰）

- 给对象加一个引用计数器，每被引用一次 +1，引用失效 -1，为 0 时回收
- **淘汰原因**: 无法解决循环引用问题（A 引用 B，B 引用 A，计数器永远不为 0）

#### 1.2 可达性分析（当前方案）

- 从 GC Roots 出发，沿引用链向下搜索，不可达的对象即为可回收对象

**GC Roots 可以是谁（4 类）**:

| GC Root | 说明 |
|---------|------|
| 虚拟机栈中引用的对象 | 各栈帧的局部变量表中引用的对象 |
| 方法区中类静态属性引用的对象 | static 变量引用的对象 |
| 方法区中常量引用的对象 | 常量池中的引用 |
| 本地方法栈中 JNI 引用的对象 | Native 方法引用的对象 |

> 面试口诀: "栈中引用、静态属性、常量引用、JNI 引用"

---

### 2. 四种引用类型

| 引用类型 | 回收时机 | 典型使用场景 |
|----------|----------|--------------|
| 强引用（Strong） | 永远不回收（只要引用存在） | 普通变量赋值 `Object o = new Object()` |
| 软引用（SoftReference） | 内存不足时才回收 | **缓存**（如图片缓存） |
| 弱引用（WeakReference） | 下次 GC 时一定回收 | **WeakHashMap**、ThreadLocal 的 Entry |
| 虚引用（PhantomReference） | 随时可能回收，无法获取对象 | 跟踪 GC 回收、管理堆外内存（Cleaner） |

```java
// 软引用示例
SoftReference<byte[]> cache = new SoftReference<>(new byte[1024 * 1024]);

// 弱引用示例
WeakReference<Object> ref = new WeakReference<>(new Object());
```

> **面试高频**: ThreadLocal 为什么内存泄漏？—— ThreadLocalMap 的 Entry 是弱引用指向 ThreadLocal，但 Value 是强引用。ThreadLocal 被 GC 后，Entry 的 key 为 null，但 value 仍被引用无法回收。解决方案：用完后调用 `remove()`。

---

### 3. GC 算法

| 算法 | 原理 | 优点 | 缺点 | 适用区域 |
|------|------|------|------|----------|
| 标记-清除 | 标记可回收对象，统一清除 | 简单 | 内存碎片化；分配慢 | 老年代（CMS） |
| 标记-复制 | 将存活对象复制到另一块空间 | 无碎片；分配快（指针碰撞） | 空间利用率低（50%） | 新生代 |
| 标记-整理 | 标记后将存活对象向一端移动 | 无碎片 | 移动对象成本高 | 老年代 |

> **面试要点**: 新生代用标记-复制（因为 98% 对象朝生夕死，只需复制少量存活对象）；老年代用标记-清除或标记-整理。

---

### 4. 垃圾收集器对比表

| 收集器 | 作用区域 | 线程 | 算法 | 特点 | 适用场景 |
|--------|----------|------|------|------|----------|
| Serial | 新生代 | 单线程 | 标记-复制 | 简单高效，STW | 客户端模式 |
| Serial Old | 老年代 | 单线程 | 标记-整理 | 简单 | 客户端模式 |
| ParNew | 新生代 | 多线程 | 标记-复制 | Serial 多线程版 | 配合 CMS 使用 |
| Parallel Scavenge | 新生代 | 多线程 | 标记-复制 | **吞吐量优先** | 后台计算型任务 |
| Parallel Old | 老年代 | 多线程 | 标记-整理 | 配合 PS | 吞吐量优先 |
| CMS | 老年代 | 并发 | 标记-清除 | **低延迟**，4个阶段 | 对延迟敏感 |
| **G1** | 全堆 | 并发 | 标记-整理+复制 | **可预测停顿** | 服务端默认（JDK 9+） |
| **ZGC** | 全堆 | 并发 | 着色指针 | **<10ms 停顿** | 超低延迟需求 |

> **组合关系**: Serial + Serial Old / ParNew + CMS / Parallel Scavenge + Parallel Old / G1（独自管理全堆）

---

### 5. G1 核心原理（重点）

**核心思想: Region 化 + 混合回收**

```
堆内存被划分为等大的 Region（默认 2048 个）
每个 Region 可以是: Eden / Survivor / Old / Humongous（大对象）
```

**三个关键特性**:

| 特性 | 说明 |
|------|------|
| Region 化 | 不再物理分代，逻辑分代。每个 Region 动态角色切换 |
| 混合回收（Mixed GC） | 同时回收新生代和部分老年代，优先回收垃圾最多的 Region |
| 可预测停顿 | 用户设定目标停顿时间（`-XX:MaxGCPauseMillis=200`），G1 根据历史数据选择回收哪些 Region |

**G1 回收流程**:
1. **Young GC**: 回收所有 Eden 和 Survivor Region
2. **并发标记**: 标记老年代中的垃圾（类似 CMS 但不产生碎片）
3. **Mixed GC**: 回收所有新生代 + 垃圾最多的部分老年代 Region
4. 如果 Mixed GC 回收速度跟不上分配速度 → **Full GC**（退化为串行收集，很慢）

> **记忆集（RSet）**: 每个 Region 维护一个 RSet，记录其他 Region 指向自己的引用，避免全堆扫描。

---

### 6. ZGC 核心（了解加分）

**目标**: 停顿时间 < 10ms，且不随堆大小增加而增加。

| 核心技术 | 说明                                           |
| ---- | -------------------------------------------- |
| 着色指针 | 在指针的 4 个 bit 中存储 GC 相关的标记信息（标记、重映射、最终izable） |
| 读屏障  | 在对象引用被读取时检查指针颜色，如果指向旧地址则自动修正（自愈）             |
| 并发整理 | 对象移动与业务线程并发执行，只有短暂的 STW 做根节点扫描               |

**ZGC vs G1 对比**:

|  对比项   |     G1     |           ZGC            |
| :----: | :--------: | :----------------------: |
| STW 时间 |  200ms 左右  |          < 10ms          |
| 堆大小影响  | 堆越大 STW 越长 |         不受堆大小影响          |
| JDK 版本 | JDK 9+ 默认  | JDK 11+ 可用（JDK 15+ 生产可用） |
|  适用场景  |   通用服务端    |       超低延迟（金融/交易）        |


---

### 7. GC 类型

| GC 类型 | 回收区域 | 触发条件 | 频率 |
|---------|----------|----------|------|
| Minor GC（Young GC） | 新生代（Eden + S0/S1） | Eden 区满 | 频繁，速度快 |
| Major GC | 老年代 | 老年代空间不足 | 较少（注意：Major GC 定义不统一，有时等同于 Full GC） |
| Full GC | 全堆 + 元空间 | System.gc() / 老年代满 / 元空间满 | 尽量避免，速度慢 |
| Mixed GC | 新生代 + 部分老年代 | G1 特有，并发标记后触发 | G1 中替代 Full GC |

---

### 8. 内存分配策略

| 策略 | 说明 | 相关参数 |
|------|------|----------|
| Eden 优先分配 | 新对象优先在 Eden 区分配 | — |
| 大对象直接老年代 | 超过阈值的对象直接进入老年代 | `-XX:PretenureSizeThreshold` |
| 长期存活进老年代 | 对象年龄达到阈值晋升老年代 | `-XX:MaxTenuringThreshold=15` |
| 动态年龄判断 | Survivor 中同龄对象超空间一半，直接晋升 | — |
| 空间分配担保 | Minor GC 后存活对象太多，Survivor 放不下，用老年代担保 | `-XX:-HandlePromotionFailure` |

**对象年龄**: 对象每经历一次 Minor GC 且在 Survivor 中存活，年龄 +1。达到阈值（默认 15）晋升老年代。

---

### 9. 安全点（Safepoint）和安全区域

**安全点**: GC 时需要所有线程停在这几个"安全点"才能开始回收。
- 典型安全点：方法调用、循环跳转、异常跳转
- 抢占式中断（已弃用） vs 主动式中断（当前方案：设置标志位，线程轮询）

**安全区域**: 解决线程处于 Blocked/Sleeping 状态无法走到安全点的问题。
- 线程进入安全区域时标记自己，GC 不用等这些线程
- 离开安全区域前，检查 GC 是否完成

## 三、面试题

### Q1: 如何判断一个对象是否可以被回收？

**答**: 使用可达性分析算法。从 GC Roots 出发沿引用链向下搜索，如果一个对象到所有 GC Roots 都没有引用链，则该对象不可达，可以被回收。GC Roots 包括虚拟机栈中引用的对象、方法区静态属性引用的对象、方法区常量引用的对象、本地方法栈 JNI 引用的对象。

### Q2: 四种引用类型的区别和使用场景？

**答**: 强引用不回收（宁可 OOM）；软引用内存不足时回收（适合缓存）；弱引用下次 GC 就回收（ThreadLocal、WeakHashMap）；虚引用无法获取对象，仅用于跟踪 GC（管理堆外内存）。

### Q3: CMS 收集器有什么问题？

**答**: 四个问题——(1) 标记-清除算法导致内存碎片；(2) 并发阶段占用 CPU 资源，影响吞吐量；(3) 浮动垃圾：并发清理阶段新产生的垃圾要等下次 GC；(4) Concurrent Mode Failure：预留空间不够时退化为 Serial Old，停顿很长。JDK 9 已标记为 Deprecated，JDK 14 正式移除。

### Q4: G1 和 CMS 相比有什么改进？

**答**: (1) G1 使用 Region 化管理，不再是固定分代；(2) G1 优先回收垃圾最多的 Region（Garbage First 的含义），回收效率高；(3) G1 整体使用标记-整理，不产生碎片；(4) G1 支持可预测停顿时间；(5) G1 用 Mixed GC 替代 Full GC，减少全堆回收频率。

### Q5: ZGC 是如何做到 <10ms 停顿的？

**答**: 两个核心技术——(1) 着色指针：在指针中存储 GC 标记信息，不需要修改对象头；(2) 读屏障：业务线程读取引用时自行修正指针（自愈能力），让对象移动与业务并发执行。ZGC 的 STW 只在初始标记和最终标记的根节点扫描阶段，非常短暂。

### Q6: 什么时候会触发 Full GC？如何避免？

**答**: 触发条件：老年代空间不足、元空间不足、System.gc() 调用、Minor GC 后存活对象太多导致老年代放不下、CMS 的 Concurrent Mode Failure。避免方法：增大堆/老年代空间、选择合适的收集器（G1）、减少大对象分配、避免 System.gc()、调整 Survivor 区大小让对象在新生代多待一会。

### Q7: 为什么新生代用复制算法，老年代不用？

**答**: 新生代对象朝生夕死（约 98% 会被回收），每次只需复制少量存活对象到 Survivor 区，效率高。Eden : S0 : S1 = 8:1:1，只浪费 10% 空间。老年代对象存活率高，如果用复制算法需要复制大量对象，效率低且浪费一半空间，所以用标记-清除或标记-整理。

### Q8: 什么是空间分配担保？

**答**: Minor GC 时，Survivor 区可能放不下所有存活对象，此时需要老年代进行"担保"——把放不下的对象直接晋升到老年代。JDK 6 Update 24 之后，只要老年代的连续空间大于新生代所有对象总大小或大于历次晋升对象的平均大小，就进行 Minor GC，否则改为 Full GC。

### Q9: ThreadLocal 为什么可能内存泄漏？怎么解决？

**答**: ThreadLocalMap 的 Entry 继承了 WeakReference，key 是 ThreadLocal 的弱引用。当 ThreadLocal 被回收后，key 变为 null，但 value 仍然是强引用无法回收。如果线程长期存活（如线程池中的线程），这些 key 为 null 的 value 就会一直占用内存。解决方案：使用完后及时调用 `threadLocal.remove()`。

### Q10: 说一下 Minor GC → Full GC 的完整过程？

**答**: (1) 新对象分配在 Eden 区；(2) Eden 满触发 Minor GC，通过可达性分析标记存活对象；(3) 存活对象复制到 Survivor 区并年龄 +1；(4) 年龄达到阈值的对象晋升老年代；(5) 如果老年代空间不足触发 Full GC；(6) Full GC 回收整个堆和方法区，所有应用线程暂停（STW）。

## 四、常见误区

| 误区 | 正确理解 |
|------|----------|
| 引用计数法可以判断对象存活 | 已淘汰，无法解决循环引用 |
| GC 会回收所有垃圾 | 浮动垃圾需要等下次 GC |
| G1 不会 Full GC | 回收跟不上分配时会退化为 Full GC（Serial Old） |
| 对象一定在堆上分配 | 逃逸分析后未逃逸的对象可能栈上分配 |
| Survivor 区越大越好 | 太大会降低 GC 效率，默认 8:1:1 是经过验证的比例 |
| GC 次数越少越好 | 应该关注 GC 停顿时间和吞吐量的平衡 |

## 五、实战场景

1. **频繁 Full GC**: 排查是否有大对象频繁分配、内存泄漏、或 Metaspace 不足
2. **GC 停顿过长**: 考虑从 CMS/Parallel 切换到 G1 或 ZGC
3. **OOM 前的 GC**: `-XX:+HeapDumpOnOutOfMemoryError` 在 OOM 时自动导出堆转储
4. **选择收集器**: 延迟敏感选 G1/ZGC，吞吐量优先选 Parallel Scavenge
