## 二、什么是循环依赖

```java
// A 依赖 B，B 依赖 A → 循环依赖
@Component
public class ServiceA {
    @Autowired
    private ServiceB serviceB;
}

@Component
public class ServiceB {
    @Autowired
    private ServiceA serviceA;
}
```

```
创建 ServiceA → 发现需要 ServiceB → 创建 ServiceB → 发现需要 ServiceA
      ↑                                                        │
      └──────────────────── 循环！ ────────────────────────────┘
```

如果不处理，会无限递归或死锁。Spring 通过**三级缓存**解决 setter/字段注入的循环依赖。

---

## 三、三级缓存的完整内容

| 缓存 | 名称 | 存储内容 | 作用 |
|-----|------|---------|------|
| **一级** | singletonObjects | 完整的 Bean（已初始化） | 单例池，存放最终可用的 Bean |
| **二级** | earlySingletonObjects | 早期 Bean 引用（可能是代理） | 存放提前暴露的 Bean，避免重复创建 |
| **三级** | singletonFactories | ObjectFactory（Bean 工厂） | 延迟决定是否需要创建代理 |

```java
// Spring 源码中的三级缓存（DefaultSingletonBeanRegistry）

/** 一级缓存：完整的 Bean */
private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>();

/** 二级缓存：早期 Bean 引用（可能是代理对象） */
private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>();

/** 三级缓存：ObjectFactory，用于生成早期引用 */
private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>();

/** 正在创建中的 Bean 集合 */
private final Set<String> singletonsCurrentlyInCreation = Collections.newSetFromMap(new ConcurrentHashMap<>());
```

## 四、解决循环依赖的完整流程（源码级分析）

### 场景：ServiceA 字段注入 ServiceB，ServiceB 字段注入 ServiceA

```
步骤1: 创建 ServiceA（实例化）
  │ getBean("serviceA")
  │ → singletonObjects 无 → singletonsCurrentlyInCreation 加入 "serviceA"
  │ → createBeanInstance() → 反射创建 ServiceA 实例（属性为 null）
  │ → 将 ObjectFactory 放入三级缓存
  │   singletonFactories.put("serviceA", () -> getEarlyBeanReference("serviceA", bean))
  │
步骤2: 填充 ServiceA 的属性
  │ populateBean()
  │ → 发现需要 ServiceB → getBean("serviceB")
  │
步骤3: 创建 ServiceB（实例化）
  │ singletonObjects 无 → singletonsCurrentlyInCreation 加入 "serviceB"
  │ → createBeanInstance() → 反射创建 ServiceB 实例
  │ → 将 ObjectFactory 放入三级缓存
  │   singletonFactories.put("serviceB", () -> getEarlyBeanReference("serviceB", bean))
  │
步骤4: 填充 ServiceB 的属性
  │ populateBean()
  │ → 发现需要 ServiceA → getBean("serviceA")
  │
步骤5: 获取 ServiceA 的早期引用
  │ → singletonObjects 无（一级）
  │ → earlySingletonObjects 无（二级）
  │ → singletonFactories 有！（三级）
  │ → 调用 ObjectFactory.getObject() → 获取 ServiceA 的早期引用
  │   （如果需要 AOP 代理，这里返回代理对象；否则返回原始对象）
  │ → 从三级缓存移除，放入二级缓存
  │   singletonFactories.remove("serviceA")
  │   earlySingletonObjects.put("serviceA", earlyReference)
  │
步骤6: ServiceB 属性注入完成
  │ → ServiceB.serviceA = earlyReference（ServiceA 的早期引用）
  │ → ServiceB 初始化完成（afterPropertiesSet / init-method）
  │ → ServiceB 放入一级缓存
  │   singletonObjects.put("serviceB", serviceB)
  │ → 从二级/三级缓存中移除 ServiceB
  │
步骤7: 回到 ServiceA
  │ → ServiceA.serviceB = serviceB（完整的 ServiceB）
  │ → ServiceA 初始化完成
  │ → ServiceA 放入一级缓存
  │   singletonObjects.put("serviceA", serviceA)
  │ → 从二级/三级缓存中移除 ServiceA
```

### 关键源码（getSingleton 获取早期引用）

先查一级 → 再查二级 → 最后查三级（调用 ObjectFactory.getObject()，可能返回代理对象），从三级移到二级缓存。使用 Double-check + synchronized 保证线程安全。

## 五、为什么需要三级缓存而不是两级？

**核心原因：处理 AOP 代理。**

### 5.1 如果只有两级缓存会怎样？

假设只有 singletonObjects 和 earlySingletonObjects：

```
问题场景：ServiceA 需要 AOP 代理

步骤1: 创建 ServiceA 实例
步骤2: 提前创建 ServiceA 的代理对象，放入二级缓存
  问题：Spring 的设计原则是 AOP 代理应该在初始化后创建（postProcessAfterInitialization）
       提前创建代理打破了这一原则
```

### 5.2 三级缓存的巧妙设计

**三级缓存存储的是 ObjectFactory（工厂），而不是直接存储对象：**

```java
// 三级缓存中存的是工厂
singletonFactories.put(beanName, () -> getEarlyBeanReference(beanName, beanDefinition, rawBean));

// getEarlyBeanReference 内部逻辑：
// 1. 检查是否需要 AOP 代理
// 2. 如果需要 → 创建代理对象并返回
// 3. 如果不需要 → 返回原始对象
```

**设计哲学：**

| 设计点 | 说明 |
|-------|------|
| **延迟决策** | ObjectFactory 延迟到被实际获取时才决定是否创建代理 |
| **无循环依赖时** | 三级缓存中的 ObjectFactory 不会被调用，代理在初始化后正常创建 |
| **有循环依赖时** | ObjectFactory 被调用，提前创建代理，保证注入的是代理对象 |
| **保证单例** | 二级缓存确保多次获取返回同一个代理对象（不会重复创建代理） |

### 5.3 二级缓存不够的具体证明

```
场景：A 依赖 B 和 C，B 依赖 A，C 也依赖 A，A 需要 AOP 代理

1. 创建 A → 放入三级缓存（ObjectFactory）
2. 创建 B → 需要 A → 调用 ObjectFactory → 创建 A 的代理 A_proxy
   → 如果没有二级缓存，A_proxy 存哪里？
3. 创建 C → 需要 A → 再次调用 ObjectFactory → 又创建一个 A_proxy2！
   → 违反单例原则！

有二级缓存后：
2. 创建 B → 需要 A → 调用 ObjectFactory → A_proxy 放入二级缓存
3. 创建 C → 需要 A → 直接从二级缓存取 A_proxy → 单例保证
```

## 六、构造器注入为什么不能解决

```java
@Component
public class ServiceA {
    private final ServiceB serviceB;

    public ServiceA(ServiceB serviceB) {  // 构造器注入
        this.serviceB = serviceB;
    }
}

@Component
public class ServiceB {
    private final ServiceA serviceA;

    public ServiceB(ServiceA serviceA) {  // 构造器注入
        this.serviceA = serviceA;
    }
}
```

**原因分析：**

```
Spring 创建 Bean 的步骤：
1. 实例化（调用构造函数）
2. 属性注入（populateBean）
3. 初始化（afterPropertiesSet）

三级缓存在步骤1之后放入，但构造器注入需要在步骤1就获取依赖：
创建 ServiceA → 调用构造函数 → 需要 ServiceB → 此时 ServiceA 还没实例化完成
→ 三级缓存中还没有 ServiceA 的 ObjectFactory！
→ 无法提前暴露 → 报错 BeanCurrentlyInCreationException
```

**总结：** 三级缓存解决的是**属性注入**的循环依赖，构造器注入在实例化阶段就卡住了。

## 七、prototype 为什么不能解决

```java
@Component
@Scope("prototype")
public class ServiceA {
    @Autowired
    private ServiceB serviceB;
}

@Component
@Scope("prototype")
public class ServiceB {
    @Autowired
    private ServiceA serviceA;
}
```

**原因：** Spring 不缓存 prototype 作用域的 Bean（每次获取都创建新实例），三级缓存只对 singleton 生效。

## 八、@Lazy 解决构造器注入的循环依赖

```java
@Component
public class ServiceA {
    private final ServiceB serviceB;

    public ServiceA(@Lazy ServiceB serviceB) {
        this.serviceB = serviceB;  // 注入的是代理对象
    }
}
```

**@Lazy 原理：**

```
1. Spring 发现构造函数参数有 @Lazy
2. 不立即创建 ServiceB，而是生成一个 ServiceB 的代理对象注入
3. 只有在首次调用代理对象的方法时，才会真正创建 ServiceB
4. 此时 ServiceA 已经创建完成，打破了循环
```

## 九、多级缓存的设计哲学

| 设计原则 | 体现 |
|---------|------|
| **单一职责** | 一级存成品、二级存半成品、三级存工厂 |
| **延迟计算** | ObjectFactory 延迟到需要时才执行 |
| **保证单例** | 二级缓存防止重复创建代理 |
| **最小侵入** | 无循环依赖时，三级缓存不影响正常 Bean 创建流程 |
| **前后一致** | 有无 AOP，最终放入一级缓存的始终是同一个对象引用 |

## 十、常见误区

| 误区 | 正解 |
|-----|------|
| 三级缓存是为了性能 | 主要是为了正确处理 AOP 代理，保证单例 |
| 两级缓存就够了 | 没有二级缓存，多个 Bean 依赖同一个早期引用时会创建多个代理 |
| 所有循环依赖都能解决 | 构造器注入和 prototype 作用域不能解决 |
| SpringBoot 默认禁止循环依赖 | SpringBoot 2.6+ 默认禁止，但可配置 spring.main.allow-circular-references=true |
| @Lazy 是最佳实践 | @Lazy 只是权宜之计，最佳实践是重构消除循环依赖 |

## 十一、面试题

### Q1：Spring 是怎么解决循环依赖的？
**答：** 通过三级缓存。singletonObjects（完整 Bean）、earlySingletonObjects（早期引用）、singletonFactories（ObjectFactory 工厂）。实例化后将 ObjectFactory 放入三级缓存，当其他 Bean 需要提前引用时，调用 ObjectFactory 获取早期引用并升级到二级缓存，从而打破循环。

### Q2：为什么需要三级缓存，两级不行吗？
**答：** 两级缓存无法正确处理 AOP 代理。三级缓存的 ObjectFactory 实现了延迟决策：只在真正出现循环依赖时才提前创建代理对象。二级缓存保证多次获取返回同一个代理对象，避免重复创建代理违反单例原则。

### Q3：构造器注入的循环依赖为什么不能解决？
**答：** 因为三级缓存在构造函数执行之后才放入，而构造器注入在构造函数执行时就需要依赖。此时三级缓存中还没有该 Bean 的 ObjectFactory，无法提前暴露，所以报错。解决方案是使用 @Lazy 注入代理对象。

### Q4：@Lazy 是怎么解决循环依赖的？
**答：** @Lazy 让 Spring 在遇到构造器参数时，不立即创建真实的 Bean，而是生成一个代理对象注入。只有在首次调用代理方法时才真正创建 Bean，此时原来的 Bean 已经创建完成，打破了循环。

### Q5：SpringBoot 2.6+ 对循环依赖做了什么改变？
**答：** 默认禁止循环依赖，启动时检测到循环依赖直接报错。可通过 spring.main.allow-circular-references=true 开启。这是 Spring 团队推荐的做法：从设计上消除循环依赖。

### Q6：prototype 作用域的循环依赖能解决吗？
**答：** 不能。三级缓存只缓存 singleton 作用域的 Bean。prototype 每次获取都创建新实例，Spring 不缓存它们，因此无法提前暴露引用来打破循环。
