## 二、为什么需要分布式锁

**场景：** 多个服务实例（JVM）需要互斥地访问共享资源。

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 服务实例A │     │ 服务实例B │     │ 服务实例C │
└────┬─────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     └────────────────┼────────────────┘
                      │
              ┌───────▼───────┐
              │  共享资源/数据库 │
              │ (库存/余额/...) │
              └───────────────┘
```

单机 synchronized/ReentrantLock 只能在**同一个 JVM** 内互斥，跨 JVM 无效。

## 三、Redis 分布式锁

### 3.1 基础实现（SET NX EX）

```bash
# 原子操作：加锁 + 设置过期时间
SET lock_key unique_value NX EX 30
# NX：只有 key 不存在时才设置（保证互斥）
# EX 30：30 秒后自动过期（防止死锁）
```

```java
// Java 实现
public boolean tryLock(String key, String value, long expireSeconds) {
    return "OK".equals(jedis.set(key, value, "NX", "EX", expireSeconds));
}
```

**关键：** 必须使用 `SET NX EX` 一条命令保证原子性，不能用 `SETNX` + `EXPIRE` 两条命令（中间崩溃会导致死锁）。

### 3.2 解锁的原子性（Lua 脚本）

```lua
-- 解锁必须用 Lua 脚本保证原子性
-- 先检查 value 是否是自己设置的，再删除
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**为什么用 Lua 脚本？** 因为 GET + DEL 不是原子操作，可能：
1. 线程 A GET 发现是自己的锁
2. 锁刚好过期，线程 B 获取了锁
3. 线程 A DEL 误删了线程 B 的锁

### 3.3 锁过期但业务未完成的问题

```
线程A: 获取锁(T=30s) → 执行业务(40s) → 锁已过期！ → 误删线程B的锁
线程B:                        获取锁 → 执行业务
```

**解决方案：Redisson 看门狗机制**

### 3.4 Redisson 实现

#### 3.4.1 可重入锁（Hash 结构）

```java
// Redisson 使用 Hash 结构存储锁
// key: lock_name
// field: thread_id (客户端UUID + 线程ID)
// value: 重入次数

RLock lock = redisson.getLock("myLock");
lock.lock();
try {
    // 业务代码
    lock.lock();  // 可重入，value +1
    try {
        // 嵌套业务
    } finally {
        lock.unlock();  // value -1
    }
} finally {
    lock.unlock();  // value 减到 0 才删除 key
}
```

**加锁 Lua 脚本（简化版）：**

```lua
-- Redisson 加锁 Lua 脚本
if (redis.call('exists', KEYS[1]) == 0) then
    -- 锁不存在，加锁
    redis.call('hset', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    -- 同一线程重入
    redis.call('hincrby', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
-- 锁被其他线程持有，返回剩余 TTL
return redis.call('pttl', KEYS[1]);
```

#### 3.4.2 看门狗续期机制

```
看门狗流程：
1. 加锁成功后启动 Watchdog 定时任务
2. 每隔 lockWatchdogTimeout/3（默认 10s）检查一次
3. 如果锁还被持有，自动续期为 lockWatchdogTimeout（默认 30s）
4. 持有锁的客户端宕机 → Watchdog 停止 → 锁自动过期
```

```java
// 使用看门狗（不指定 leaseTime）
RLock lock = redisson.getLock("myLock");
lock.lock();  // 自动续期
// 等价于 lock.lock(-1, TimeUnit.SECONDS) → -1 表示启动看门狗

// 指定 leaseTime 则不会启动看门狗！
lock.lock(30, TimeUnit.SECONDS);  // 30s 后必定过期，不续期
```

### 3.5 RedLock 算法（防单点故障）

**问题：** Redis 主从架构中，主节点加锁成功后未同步到从节点就宕机，从节点升为主后锁丢失。

**RedLock 方案：** 向 N 个（通常 5 个）独立的 Redis 节点加锁，超过半数（N/2+1）加锁成功才算获取锁。

```java
// RedLock 使用示例
RLock lock1 = redisson1.getLock("lock");
RLock lock2 = redisson2.getLock("lock");
RLock lock3 = redisson3.getLock("lock");

RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
try {
    // 业务
} finally {
    redLock.unlock();
}
```

**RedLock 流程：**
1. 记录当前时间 T1
2. 依次向 5 个节点请求加锁（超时时间远小于锁过期时间）
3. 计算加锁耗时 T = 当前时间 - T1
4. 如果超过半数节点加锁成功，且 T < 锁过期时间 → 获取锁成功
5. 否则向所有节点释放锁

## 四、ZooKeeper 分布式锁

### 4.1 实现原理（临时顺序节点 + Watch）

```
锁节点: /locks/resource
├── /locks/resource/lock-0000000001  → 客户端A（序号最小，获取锁）
├── /locks/resource/lock-0000000002  → 客户端B（Watch 前一个节点）
└── /locks/resource/lock-0000000003  → 客户端C（Watch 前一个节点）
```

**流程：**
1. 在锁节点下创建**临时顺序节点**（EPHEMERAL_SEQUENTIAL）
2. 获取所有子节点，判断自己是否为最小序号
3. 是 → 获取锁成功
4. 否 → 对前一个节点注册 Watch，前一个节点删除时被唤醒
5. 业务完成后删除自己的节点（释放锁）
6. 客户端宕机 → 临时节点自动删除 → 自动释放锁

### 4.2 羊群效应优化

**旧方案（问题）：** 所有客户端 Watch 同一个节点，节点删除时所有客户端被唤醒竞争（羊群效应）。

**优化方案：** 每个客户端只 Watch 自己前面的一个节点，形成链式通知，只有前一个释放锁时才唤醒下一个。

### 4.3 Curator 实现

```java
// Curator 框架封装了 ZooKeeper 分布式锁
InterProcessMutex lock = new InterProcessMutex(client, "/locks/resource");
lock.acquire();  // 获取锁
try {
    // 业务代码
} finally {
    lock.release();  // 释放锁
}
```

## 五、MySQL 分布式锁

### 5.1 悲观锁（FOR UPDATE）

```sql
BEGIN;
SELECT * FROM stock WHERE product_id = 1001 FOR UPDATE;  -- 加行锁
UPDATE stock SET count = count - 1 WHERE product_id = 1001;
COMMIT;
```

**注意：** 必须在事务中，且需要索引（否则锁表）。

### 5.2 乐观锁（唯一索引/版本号）

```sql
-- 方式1：唯一索引（防重）
INSERT INTO distributed_lock (lock_key, holder) VALUES ('order_123', 'server1');

-- 方式2：版本号
UPDATE stock SET count = count - 1, version = version + 1
WHERE product_id = 1001 AND version = 5;
-- affected rows = 0 则说明被其他线程修改了
```

## 六、三种方案对比

| 对比维度 | Redis | ZooKeeper | MySQL |
|---------|-------|-----------|-------|
| **性能** | 高（内存操作） | 中（集群通信） | 低（磁盘IO） |
| **可靠性** | 中（主从切换可能丢锁） | 高（ZAB 一致性协议） | 中（依赖事务） |
| **实现复杂度** | 低 | 中 | 低 |
| **自动续期** | 需要自己实现/Redisson | 不需要（临时节点） | 不需要（事务内） |
| **可重入** | 需自己实现/Redisson | 需自己实现/Curator | 需自己实现 |
| **适用场景** | 高并发、性能优先 | 一致性要求高 | 并发量不大、简单场景 |

## 七、分布式锁的注意事项

| 注意事项 | 说明 |
|---------|------|
| **锁超时** | 必须设置过期时间，防止客户端宕机导致死锁 |
| **解锁原子性** | 解锁必须用 Lua 脚本，先判断再删除 |
| **可重入** | 多层调用需要支持重入，否则会死锁 |
| **唯一标识** | value 必须是线程唯一标识，防止误删别人的锁 |
| **续期问题** | 长任务需要续期机制，否则锁过期后并发失控 |
| **时钟问题** | Redis 依赖系统时钟，时钟跳跃可能导致锁提前过期 |
| **锁粒度** | 锁粒度尽量细，不要锁住不相关的业务 |

## 八、常见误区

| 误区 | 正解 |
|-----|------|
| SETNX + EXPIRE 就是安全的 | 两条命令非原子，中间崩溃会死锁，要用 SET NX EX |
| Redis 主从架构下分布式锁安全 | 主从切换可能丢锁，需要 RedLock |
| 业务执行完锁过期没关系 | 锁过期后其他线程能获取锁，并发失控 |
| ZooKeeper 性能比 Redis 好 | ZooKeeper 每次写操作需要集群过半确认，延迟更高 |
| MySQL 不适合做分布式锁 | 并发不高时 MySQL 方案最简单可靠 |

## 九、面试题

### Q1：Redis 分布式锁怎么实现？需要注意什么？
**答：** 使用 `SET key value NX EX timeout` 原子命令加锁，解锁使用 Lua 脚本保证原子性（先判断 value 是否匹配再删除）。注意必须设置过期时间防死锁，value 必须唯一防止误删，长任务需要续期机制。

### Q2：Redisson 的看门狗机制是什么？
**答：** 加锁时不指定过期时间，Redisson 会启动一个定时任务（Watchdog），每隔 lockWatchdogTimeout/3（默认 10s）检查锁是否还被持有，如果是则自动续期到 30s。客户端宕机后 Watchdog 停止，锁自动过期。注意指定 leaseTime 后不会启动看门狗。

### Q3：RedLock 算法是什么？解决什么问题？
**答：** 解决 Redis 主从切换丢锁问题。向 5 个独立 Redis 节点加锁，超过半数成功且耗时小于锁过期时间才算成功。任何一步失败则向所有节点释放锁。

### Q4：ZooKeeper 分布式锁的原理是什么？
**答：** 创建临时顺序节点，判断自己是否为最小序号节点，是则获取锁。否则 Watch 前一个节点，前一个删除时被唤醒再判断。客户端宕机时临时节点自动删除，自动释放锁。

### Q5：Redis 和 ZooKeeper 分布式锁怎么选？
**答：** 性能优先选 Redis（内存操作，QPS 高）；一致性优先选 ZooKeeper（ZAB 协议保证一致性，临时节点自动释放不需要续期）。实际项目中 Redis + Redisson 使用更广泛。

### Q6：分布式锁解锁为什么用 Lua 脚本？
**答：** 因为 GET + DEL 不是原子操作。线程 A GET 判断 value 匹配后，锁可能刚好过期被线程 B 获取，此时线程 A 的 DEL 会误删线程 B 的锁。Lua 脚本在 Redis 中原子执行，避免这个问题。

### Q7：MySQL 怎么实现分布式锁？
**答：** 悲观锁用 `SELECT ... FOR UPDATE` 在事务中加行锁；乐观锁用版本号字段 `UPDATE ... SET version = version + 1 WHERE version = ?`。适合并发量不大、简单场景。

### Q8：锁过期但业务还没执行完怎么办？
**答：** 使用 Redisson 的看门狗机制自动续期；或将过期时间设长一些但可能导致宕机后等待太久；或在业务层面做幂等校验，即使锁过期也不影响正确性。
