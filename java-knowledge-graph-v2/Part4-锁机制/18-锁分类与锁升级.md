
> **一句话总结：** synchronized 的锁升级机制是 JVM 对悲观锁的终极优化，理解 Mark Word 是理解锁机制的地基。

## 三、对象头 Mark Word（64 bit）

HotSpot 虚拟机中，对象头 Mark Word 在 **64 位 JVM** 下的布局：

```
|-----------------------------------------|--------------------|----------|
|              Mark Word (64 bit)          |       状态         | 锁标志位 |
|-----------------------------------------|--------------------|----------|
| unused:25 | identity_hashcode:31 | unused:1 | age:4 | biased_lock:1 | lock:2 | 无锁      | 001 |
|-----------------------------------------|--------------------|----------|
| thread:54 |       epoch:2        | unused:1 | age:4 | biased_lock:1 | lock:2 | 偏向锁    | 101 |
|-----------------------------------------|--------------------|----------|
|               ptr_to_lock_record:62              | lock:2 | 轻量级锁  | 00  |
|-----------------------------------------|--------------------|----------|
|               ptr_to_heavyweight_monitor:62       | lock:2 | 重量级锁  | 10  |
|-----------------------------------------|--------------------|----------|
|                                                   | lock:2 | GC 标记   | 11  |
|-----------------------------------------|--------------------|----------|
```

**关键字段说明：**
- `thread`：持有偏向锁的线程 ID
- `epoch`：偏向锁时间戳（批量重偏向用）
- `ptr_to_lock_record`：指向栈中 Lock Record 的指针
- `ptr_to_heavyweight_monitor`：指向 ObjectMonitor 的指针
- `age`：GC 分代年龄
- `biased_lock`：是否启用偏向锁（1=启用）

## 四、synchronized 锁升级完整流程

```
无锁
  │  首次被线程访问
  ▼
偏向锁（Biased Locking）
  │  出现第二个线程竞争
  ▼  等待全局安全点（STW），撤销偏向锁
轻量级锁（Lightweight Lock）
  │  CAS 自旋失败超过阈值（自适应自旋）
  ▼ 膨胀为重量级锁
重量级锁（Heavyweight Lock）
  │  依赖 Monitor，线程阻塞/唤醒
  ▼
线程阻塞，交由操作系统调度
```

### 4.1 偏向锁

**核心思想：** 如果一个锁始终只被同一个线程获取，就把锁"偏向"给这个线程，后续加锁/解锁无需任何 CAS 操作。

```java
// 偏向锁获取流程（伪代码）
if (mark_word.thread_id == current_thread_id) {
    // 直接成功，无需任何同步操作
    return;
}
if (mark_word.is_biased()) {
    // 需要撤销偏向（在安全点执行）
    revoke_bias();
}
// 尝试 CAS 将线程 ID 写入 Mark Word
if (CAS(mark_word, current_thread_id)) {
    // 偏向成功
}
```

### 4.2 偏向锁撤销的条件

- 当**第二个线程**尝试获取该偏向锁时
- 调用对象的 `hashCode()` 方法（identity hashcode 只能存一次，偏向锁没有空间存）
- 发生 GC 时的批量撤销

**撤销流程：**
1. 等待全局安全点（STW，所有线程暂停）
2. 检查持有偏向锁的线程是否存活
3. 如果线程不活动 → 恢复为无锁状态（锁标志位 001）
4. 如果线程仍在同步块内 → 升级为轻量级锁
5. 恢复线程，退出安全点

### 4.3 批量重偏向与批量撤销

JVM 维护了 `epoch` 时间戳来优化偏向锁撤销的开销：

- **批量重偏向（Bulk Rebias）：** 当一个类的偏向锁撤销次数达到阈值（默认 20），对该类的所有新对象重新偏向新的线程
- **批量撤销（Bulk Revocation）：** 当撤销次数继续达到更高阈值（默认 40），直接禁用该类的偏向锁，新对象直接从轻量级锁开始

```bash
# JVM 参数
-XX:BiasedLockingBulkRebiasThreshold=20    # 批量重偏向阈值
-XX:BiasedLockingBulkRevokeThreshold=40    # 批量撤销阈值
-XX:BiasedLockingStartupDelay=4000         # 偏向锁启动延迟（ms）
```

### 4.4 轻量级锁（Lightweight Lock）

**核心思想：** 使用 CAS 自旋替代线程阻塞，适用于**线程交替执行**或**持锁时间极短**的场景。

```
获取轻量级锁流程：
1. 在当前栈帧创建 Lock Record
2. 将对象头 Mark Word 拷贝到 Lock Record（Displaced Mark Word）
3. CAS 尝试将对象头替换为指向 Lock Record 的指针
4. 成功 → 获取锁
5. 失败 → 自旋重试（自适应自旋）
6. 自旋超过阈值 → 膨胀为重量级锁
```

**自适应自旋：** JVM 根据上一次自旋是否成功来动态调整自旋次数，如果上次成功 → 增加自旋次数；如果上次失败 → 减少甚至跳过自旋。

### 4.5 重量级锁（Heavyweight Lock）

**核心思想：** 依赖操作系统的 Mutex（互斥量）实现线程阻塞和唤醒。

**ObjectMonitor 核心结构：**

```
ObjectMonitor
├── _owner       → 持有锁的线程
├── _count       → 重入计数
├── _EntryList   → 阻塞等待获取锁的线程队列（Blocked）
├── _WaitSet     → 调用 wait() 后等待的线程队列（Waiting）
└── _recursions  → 重入次数
```

**线程获取重量级锁流程：**
1. 线程进入 `_EntryList` 排队（Blocked 状态）
2. 持有锁的线程释放锁 → 唤醒 `_EntryList` 中的线程
3. 竞争成功的线程成为 `_owner`
4. 调用 `wait()` → 线程进入 `_WaitSet`（Waiting 状态）
5. 调用 `notify()` → 从 `_WaitSet` 移到 `_EntryList`

### 4.6 锁升级为什么不可降级？

**原因：** 一旦膨胀为重量级锁，说明该锁的竞争已经非常激烈，如果降级回去，很快又要膨胀，反复膨胀/降级的开销比保持重量级锁更大。JVM 选择"就高不就低"的策略。

## 五、各级锁对比表

| 特性 | 偏向锁 | 轻量级锁 | 重量级锁 |
|-----|-------|---------|---------|
| **适用场景** | 只有一个线程访问 | 线程交替执行/短时间持有 | 竞争激烈/持锁时间长 |
| **获取方式** | 检查 thread_id，无 CAS | CAS 自旋 | OS Mutex 阻塞 |
| **性能** | 最高（几乎零开销） | 高（少量 CAS 开销） | 低（涉及用户态/内核态切换） |
| **线程状态** | 无变化 | 活跃（自旋） | 阻塞 |
| **是否有 STW** | 撤销时有 | 无 | 无 |
| **锁标志位** | 101 | 00 | 10 |

## 六、常见误区

| 误区 | 正解 |
|-----|------|
| synchronized 始终是重量级锁 | JDK6 以后引入了锁升级机制，大部分场景不会到重量级 |
| 偏向锁一定比轻量级锁好 | 多线程交替执行时偏向锁反而有撤销开销 |
| 锁可以降级 | 锁只能升级不能降级 |
| 调用 hashCode 会升级锁 | 调用 identity hashCode 会使偏向锁失效（因为 Mark Word 没有空间存 hashcode） |
| 所有对象都从偏向锁开始 | 有 4 秒启动延迟，且类被批量撤销后直接从轻量级锁开始 |

## 七、实战场景

**场景：高并发计数器选择锁策略**

```java
// 场景1：单线程访问 → 偏向锁就够
private synchronized void singleThreadAccess() {
    counter++;
}

// 场景2：低竞争 → 使用轻量级锁或 Atomic
private final AtomicInteger atomicCounter = new AtomicInteger();
public void lowContention() {
    atomicCounter.incrementAndGet(); // CAS 自旋，类似轻量级锁
}

// 场景3：高竞争 → 使用 LongAdder（分散热点）
private final LongAdder longAdder = new LongAdder();
public void highContention() {
    longAdder.increment(); // Cell 分散，避免单点竞争
}
```

## 八、面试题

### Q1：synchronized 的锁升级过程是怎样的？
**答：** JDK6 引入了锁升级机制：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。单线程访问时使用偏向锁（记录线程 ID，无需同步操作）；出现竞争时撤销偏向锁，升级为轻量级锁（CAS 自旋）；自旋失败后膨胀为重量级锁（OS Mutex 阻塞）。锁只能升级不能降级。

### Q2：偏向锁什么时候会撤销？
**答：** 当第二个线程尝试获取偏向锁时，JVM 会等待全局安全点（STW），检查原持有线程的状态，决定是恢复为无锁还是升级为轻量级锁。此外，调用 identity hashCode 和达到批量撤销阈值也会触发撤销。

### Q3：为什么锁升级不能降级？
**答：** 因为能升级到重量级锁说明竞争已经很激烈，降级后很快又需要膨胀，反复操作的开销比保持重量级锁更大。JVM 选择了"就高不就低"的策略。

### Q4：对象头的 Mark Word 在 64 位 JVM 下是怎样存储的？
**答：** 64 bit 的 Mark Word 在不同锁状态下存储不同内容。无锁状态存 hashcode 和 GC 年龄；偏向锁状态存线程 ID 和 epoch；轻量级锁存指向栈中 Lock Record 的指针；重量级锁存指向 ObjectMonitor 的指针。最后 2 bit 是锁标志位，倒数第 3 bit 是偏向锁标志。

### Q5：什么是自适应自旋？
**答：** JVM 根据上一次在同一个锁上的自旋是否成功来动态调整自旋次数。如果上次自旋成功获取了锁，JVM 会认为这次也有很大概率成功，允许更多自旋次数；反之则减少自旋次数甚至直接跳过自旋进入阻塞。

### Q6：批量重偏向和批量撤销是什么？
**答：** 当某个类的偏向锁撤销次数达到 20 次时触发批量重偏向，该类的新对象会偏向新线程。达到 40 次时触发批量撤销，该类的所有对象禁用偏向锁，直接从轻量级锁开始。

### Q7：重量级锁的 Monitor 是怎样工作的？
**答：** ObjectMonitor 有 `_owner`（持有者）、`_EntryList`（阻塞队列）、`_WaitSet`（等待队列）。获取锁失败的线程进入 `_EntryList` 阻塞；调用 wait() 的线程进入 `_WaitSet`；notify() 将线程从 `_WaitSet` 移到 `_EntryList`。涉及操作系统用户态到内核态的切换，开销大。

### Q8：调用对象的 hashCode() 对锁有什么影响？
**答：** 如果对象处于偏向锁状态，调用 `hashCode()` 会使偏向锁失效（因为 identity hashcode 需要占据 Mark Word 的空间，而偏向锁状态下这部分被线程 ID 占用）。对象会直接升级为轻量级锁或重量级锁。
